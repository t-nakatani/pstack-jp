# 結果を確認し、PR を開きます

「コンパイルできます」は証拠ではありません。 [Prove It Works 原則](../../skills/principle-prove-it-works/SKILL.md) では、エージェントが成功を報告する前に実際の成果物をチェックするようにしており、あなたの仕事は「実際の成果物」をチェック可能にすることです。このページでは、終了条件の指定、測定された数値の精査、アプリの検証スキルの生成、PR のオープン、マージへの推進について説明します。

検証は、通常は人間を待つステップであるため、ほとんどのエージェントの作業の中で最も時間がかかるステップです。エージェントがそれを実行できるようにすれば、あなたがボトルネックになることはなくなります。これをスキップすると、より多くのエージェントを実行しても、レビューすべき未チェックの作業が増えるだけです。

![プロトタイプの飛行機が実際のテストコースを飛行しながら、ストップウォッチとロボットのフィルムで時間を計測し、走行をチェックリストに記録します。端末は検証: 合格、証拠: 捕捉を読み取ります。](./images/verification.jpg)

<a id="state-the-finish-condition-up-front"></a>

## 仕上がり状態を事前に明記する

完了の意味を最初のプロンプトに、適切な言葉で入力します。

```text
/poteto-mode add json output to this command. text output stays byte-identical, the json parses, both run against the sample project. show me the evidence.
```

現在、エージェントには実行できるチェックが 3 つありますが、満足する気分はありません。応答が返されると、正確なコマンドと出力が返されるはずです。チェックが実行できなかった場合、適切な返信には「決定的ではない」と表示されるため、証拠のない自信に満ちた返信は危険信号として扱う必要があります。

チェックを変更に一致させます:

- CLI を変更すると、実際のコマンドが実行されます。
- UI の変更により、実行中のアプリで変更されたフローが追跡されます。参照ピクセルとピクセルごとに一致する必要がある場合、[ビジュアル パリティ プレイブック](../../skills/poteto-mode/playbooks/visual-parity.md) は、目で判断するのではなく、フリーズしたベースラインとスクリーンショットを比較します。
- パーサーまたは移行は、保存された入力を再生します。
- パフォーマンス変更の前後のプロファイルを比較します。
- ストレージの変更により、書き込まれた値が読み戻されます。

自分で検査できる成果物として証拠を求めてください。失敗したテストと合格したテスト、前後のビデオ、トレース、スクリーンショットなどです。修正がすでにマージされている場合は、メインで同じチェックを再度要求します。アーティファクトは、実行全体をリプレイしなくても挑戦できるため、もっともらしい説明に勝ります。

完全に信頼できない小さな差分については、[`/blast-radius`](../../skills/blast-radius/SKILL.md) が他の場所で壊れる可能性のあるものを見つけます。変更が安全であるという事実を 1 つ選び出し、それについてエッセイを書く代わりにコードを実行することでそれを証明します。

<a id="vet-a-measured-number-with-benchmark-checklist"></a>

## `/benchmark-checklist` で測定された数値を精査します

前後の数字は、うっかり間違える最も簡単な証拠です。ウォーム キャッシュ、片側のデバッグ ビルド、または時間指定された領域内で実行されなかった作業は、それぞれ納得のいく高速化を生み出すことができます。数値を報告したり、数値に基づいて行動したりする前に、次のように入力します。

```text
/benchmark-checklist vet the export speedup before it goes in the pr
```

[`/benchmark-checklist`](../../skills/benchmark-checklist/SKILL.md) は 7 つの質問をし、それぞれの実行からの証拠を求めています。

1. この数を制限するものは何ですか? なぜ 2 倍にしないのですか?
2. すべての側が本番環境に合わせて調整されましたか?
3. 結果は、ディスク帯域幅やコア数などの物理的な制限を超えていますか?
4. 何かエラーが発生したか、間違った出力が返されましたか?
5. 中央値と範囲を使用して、交互の実行で再現されますか?
6. ユーザーが待機するパス上のエンドツーエンドは重要ですか?
7. 作業は実際に時間領域内で発生しましたか?

実行回数、範囲、リミッターに関して、速い、遅い、測定可能な差がない、または決定的ではないという評決が返されます。リミッターの名前がわからない場合や、サイドが調整されていない場合は、「決定的ではない」と表示されます。 `/poteto-mode` は、Perf 問題と Hillclimb プレイブック内でチェックリストをすでに実行しているため、それらの外で何かを測定した場合、または他の人の数値が良すぎると思われる場合は、自分でチェックリストを入力します。これは、[数値の原則の説明](../../skills/principle-explain-the-number/SKILL.md) の実用的な形式です。

<a id="create-a-project-verification-skill"></a>

## プロジェクト検証スキルの作成

上記の UI の箇条書きには、実際の要件が隠されています。エージェントには、アプリを操作するためのスクリプト化された方法が必要です。あなたのプロジェクトにそれがあれば、それは素晴らしいことです。そうでない場合は、次を実行します。

```text
/create-verification-skill
```

[`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md) はあなたではなくリポジトリにインタビューします。ユーザーが触れたもの、アプリがローカルでどのように起動されるか、アプリを駆動できるもの (最初は既存のハーネス、それ以外の場合はブラウザーと CDP、PTY、またはプレーン HTTP)、動作を証明する証拠は何か、2 つのインスタンスを並行して実行できるかどうかを調べます。コードでは答えられないことだけを尋ねます。

これは、正確な Launch、Doctor、Drive、Evidence、Cleanup セクションを含むエージェント向けの指示である `.cursor/skills/verify-<app>/` に加えて、アプリの動作と各機能の動作を証明する結果をインデックスする `features/` の下の機能マップを書き込みます。このスキルには、必要な 4 つの H2 を使用して、README インデックスと機能ごとに 1 つのファイルを含む [機能マップの例](../../skills/create-verification-skill/references/feature-map-example/) が同梱されます。引き渡す前に、ジェネレーターは、打ち上げ、ドクターチェック、1 つの機能の駆動、証拠のキャプチャ、クリーンアップなど、エンドツーエンドでスキルを証明します。その証明が失敗した場合は、出力を使用しないでください。

それ以降、「アプリで確認する」は、このリポジトリ内で、設定会話なしでエージェントが実行できるステップになります。特定の形式で証明が必要な場合は、プロンプトで名前を付けます。

```text
/poteto-mode build the bulk-archive action. use /verify-<app> to verify your changes and show me a video and screenshots as proof.
```

```text
/poteto-mode repro this with /verify-<app>. if it repros on main, fix it and show me a video as proof.
```

検証スキルが機能すると、[`/swarm`](../../skills/swarm/SKILL.md) は機能マップ エントリごとに完全なパスを分割し、結果を集計できます。また、検証者の群れは、十分な大きさのサンプルに対してパフォーマンスが優れていることを確認したり、PR がリリースされる前にアプリの回帰をファジングしたりすることもできます。

検証スキルを 1 回限りのものではなく、インフラストラクチャとして扱います。これをコミットすると、チーム内のすべてのユーザーとすべてのエージェントが同じ方法でアプリを操作できるようになります。次に、[レバーを構築](../../skills/principle-build-the-lever/SKILL.md) します。エージェントがアプリをクリックスルーするための使い捨てスクリプトを書き続ける場合は、代わりにスキルが呼び出す小さな制御 CLI を要求します。エージェントが消費するトークンが少なくなり、すべての実行が再現可能になります。エージェントがよく使用する CLI には次の特徴があります。

- いくつかの構成可能なコマンド。それぞれが多くの単純なコマンドではなく、実際の作業を実行します。
- 破壊的なものに対する `--dry-run` オプション。
- 機能を一度にではなく徐々に明らかにするサブコマンド。
- 代わりに何をすべきかを示すエラー メッセージ。
- リッチ `--help` テキスト。
- 機械可読出力 (JSON など)。

その間に、開発セットアップも繰り返し可能にします。つまり、シードされたデータ、テスト ユーザー、および毎回同じ方法で環境を起動する 1 つのコマンドです。

<a id="keep-the-verification-skill-honest"></a>

## 検証スキルを正直に保つ

アプリは変更され、機能マップは腐ります。これを少なくとも 1 日に 1 回実行します。理想的には、スケジュールされた自動化から実行して、誰も覚えなくて済むようにします。

```text
/maintain-verification-skill
```

[`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md) は、生成されたスキルを監査します。機能ごとに 1 つの読み取り専用ソース リーダーを並行して実行し、マップされたすべての機能を駆動する 1 つのライブ パスを監査します。それは 3 つの結果のうちの 1 つで終了します。 `clean` は完全にカバーされ、何もリリースされないことを意味します。 `changed` は、検証スキル独自のディレクトリに限定された、証明された修正の 1 つの PR を意味します。 `blocked` はブロッカーに名前を付けます。製品コードを編集することはありません。ライブパスが製品のリグレッションを検出した場合、ドキュメントで報告するのではなく、リグレッションを報告します。

<a id="open-the-pr"></a>

## PR を開く

```text
/poteto-mode open the pr. small ordered commits, evidence in the description.
```

[PR プレイブックを開く](../../skills/poteto-mode/playbooks/opening-a-pr.md) はワークツリーから動作し、作業を小さな順序付けされたコミットにリベースし、差分をクリーンアップし、文章を取り除き、PR リンクを返します。 5 つの幅の狭い PR が 1 つの太い PR に勝ち、積み重ねられたフォローアップが成長するブランチに勝ちます。

<a id="drive-the-pr-to-merge-ready-with-babysit"></a>

## PR を Babysit とのマージ準備を整える

オープン PR はすぐにブロッカーの収集を開始します。チェックが失敗し、レビュー担当者がコメントし、トランクが移動します。チャーンを [ベビーシット プレイブック](../../skills/poteto-mode/playbooks/babysit.md) に渡します。

```text
/poteto-mode babysit this pr. get it green.
```

Babysit はバンドルされたウォッチャーで PR を監視し、競合、スレッドのレビュー、CI の順にブロッカーを検出します。既知の修正はすべて 1 回のプッシュにまとめられるため、チェックは修正ごとではなく 1 回再開されます。人間とボットは実際のキャッチとノイズを同じリストに登録するため、コメントのトリアージには懐疑的です。実際の発見は修正され、スレッドに投稿された反証によってノイズは無視されます。ステータスだけが必要な場合は、ループを開始せずに、より小さな質問をして、ベビーシッターの答えを返します。

```text
/poteto-mode check on pr 123. anything outstanding?
```

ベビーシットはマージ準備完了で停止します。たとえすべてが緑色であっても、マージは別の決定であるため、決してマージされません。

<a id="land-the-stack-with-shipping"></a>

## 配送付きでスタックを着陸させる

緑は安全というわけではありません。着陸の準備ができたら、次のように言います。

```text
/poteto-mode land the stack.
```

[リリースプレイブック](../../skills/poteto-mode/playbooks/shipping.md) は、何かを準備する前に各 PR を個別に検証します。 PR ごとに 1 人の新しいエージェントが動作をライブで証明します。変更を判断するエージェントは、変更を作成したエージェントではありません。次に、 Shipping は、デフォルトでは GitHub 経由で、または CLI が利用可能な場合は Origin 経由で一度に 1 つの PR ずつ、連続した検証済みの実行のみを下位から取得し、チェーンを切断する最初の PR を報告します。未検証の PR の上にある検証済みの PR は待機します。これは、それをマージすると下にギャップができるためです。
