# 自分のものにしましょう

ポテトモードはお一人様スタイルです。その下の機構、プレイブック、ルーティング、モデルの役割は、あなたのものを身に着けても同様に機能します。このページでは、個人モードの生成、セッションからのレッスンの取得、エージェントが間違いを繰り返さないようにリポジトリを修正すること、焦点を絞ったスキルの作成、信頼する前にスキルの変更をテストすることについて説明します。

思っているよりも小さなことから始めましょう。初日には多くのスキルは必要ありませんし、このプラグイン全体さえも必要ありません。明確にプロンプトを表示し、エージェントが失敗する箇所を監視し、同じ失敗が 2 回発生した場合にはスキルまたはチェックを追加します。

<a id="generate-your-own-mode-with-automate-me"></a>

## `/automate-me` を使用して独自のモードを生成します

```text
/automate-me
```

[`/automate-me`](../../skills/automate-me/SKILL.md) が履歴からスタイルを読み取るため、スタイルを説明しません。アクティブなワークスペース内の最近のトランスクリプトをマイニングして、返信、委任、検証、コード、文章、プロセスの好みなど、繰り返しの好みを調べ、どのパターンが実際にあなたであるかを尋ねます。 Cursor の組み込み `create-skill` フローを通じて `.cursor/skills/<your-name>-mode/SKILL.md` をドラフトし、[`/unslop`](../../skills/unslop/SKILL.md) を通じてドラフトを実行し、ワークツリーから PR を開くので、他の変更と同様にレビューできます。

習慣が変わるたびに、もう一度実行してください。

```text
/automate-me update my mode skill with everything since its last edit
```

更新モードでは、スキルが最後に変更されてからの履歴のみがマイニングされます。矛盾していないルールを保持し、新しい証拠でルールを改訂し、真に新しいパターンのみセクションを追加します。

<a id="capture-a-sessions-lessons-with-reflect"></a>

## `/reflect` を使用してセッションのレッスンをキャプチャします

何かを学んだタスクの直後に、次のコマンドを実行します。

```text
/reflect that took way too long. capture what we learned so the next run doesn't repeat it.
```

[`/reflect`](../../skills/reflect/SKILL.md) はトランスクリプトを 3 人の並行レビュー担当者に送信し、その後、合成装置が提案を `Accepted`、`Rejected`、`Backlog` に分類し、スキルが変更される前に承認を待ちます。提案は、将来の決定を変更する場合にのみ承認してください。奇妙なセッションの 1 つは逸話であり、ルールではありません。

<a id="fix-the-environment-with-correct"></a>

## `/correct` で環境を修正します

同じ間違いについてエージェントを何度も修正すると、修正は次のプロンプトではなくリポジトリに属します。どれだけ保持されているかによってオプションをランク付けします。

1. アーキテクチャまたはより優れたデータ構造を使用して、間違いを不可能にします。
2. タイプを使用するか、エラー名を修正する lint または CI チェックを使用してブロックします。
3. テストで捕まえてください。
4. ドキュメントまたはエージェント ルールとして書き留めます。エージェントがルールをスキップしても何も失敗しないため、これは最後に配置されます。

人間によるレビューはリストにありません。すべての PR で同じ間違いを見つけなければならないレビュー担当者の問題は、これによって解決されます。 [`/correct`](../../skills/correct/SKILL.md) は次の作業を行います。

```text
/correct agents keep calling the database client directly instead of going through the repository layer
```

最近のコミット、取り消し、コメントのレビュー、回避策を説明するコメントを読み取り、間違いをクラスにグループ化します。クラスは 2 回発生するとカウントされます。これは、最も頻繁にコミットされるクラスを、機能する最高レベルで修正し、実際の過去の間違いで新しいチェックが失敗することを証明します。また、各ルールとそれを強制するものを組み合わせたテーブルをエージェント指示ファイルに保持するため、何も強制しないルールは繰り返しとして表示されます。応答には、各クラスとその証拠、選択されたレベル、およびより高いレベルが機能しなかった理由がリストされます。

引数なしで実行すると、履歴からクラスが自動的に検索されます。 `/reflect` と `/correct` は作業を分割します。 `/reflect` は 1 回のセッションでスキルを向上させます。 `/correct` は、間違ったクラスが戻らないようにリポジトリを変更します。修正が新しい境界である場合は、`/architect` と組み合わせます。 [多くのプロジェクトを並行して実行する](./07-overnight.md#run-many-projects-in-parallel) には、リポジトリ全体で両方を実行するプロンプトがあります。

<a id="author-a-focused-skill"></a>

## 焦点を絞ったスキルを作成する

キャプチャしたいワークフローがすでにわかっている場合:

```text
/poteto-mode write a skill for verifying database migrations in this repo
```

スキルの作成は、[スキル プレイブックの作成または変更](../../skills/poteto-mode/playbooks/authoring-a-skill.md) と一致します。これは、Cursor の組み込み `create-skill` を介してルーティングされ、フロントマターとリンクを検証し、Open a PR プレイブックを通じて結果を送信します。役に立たない文章は、将来のエージェントが従う指示になるため、エージェントに向けた文章は人間の文章よりもハードルが高くなります。 `SKILL.md` をフリーハンドで記述するのではなく、プレイブックにそのバーを保持させます。

1 つの特殊なケースには独自のジェネレーターがあります。アプリを駆動し、動作を証明する必要があるスキルは検証スキルであるため、代わりに [`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md) および [`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md) を使用してください。 [確認してリリース](./06-verify-and-ship.md#create-a-project-verification-skill) は両方をカバーします。

<a id="write-docs-to-a-standard-with-technical-writing"></a>

## `/technical-writing` を使用してドキュメントを標準に書き込みます

提供する文章はスキルだけではありません。ドキュメント、RFC、readme、PR の説明、およびコミット メッセージの場合:

```text
/technical-writing review the readme changes
```

[`/technical-writing`](../../skills/technical-writing/SKILL.md) は、疲れたエンジニアでも最初に読むだけで理解できる、1 つの目標を持つ多層標準を適用します。まずドキュメントのモード (チュートリアル、ハウツー、リファレンス、または説明) を選択し、次に文ごとに動作します。誰が何をするか、文ごとに 1 つの考え、双方向で読めるものはありません。これを使用して、あなたまたはエージェントが書いた内容を確認したり、ドキュメントを求めるときに最初に名前を付けたりすることができます。

<a id="test-a-skill-change-blind"></a>

## ブラインドでスキル変更をテストする

スキルの編集は今後のすべてのセッションに影響するため、実験と同じようにテストしてください。他人のスキルを採用する場合も同様です。エージェントを保持する前に、エージェントの作業が改善されるかどうかを確認してください。

```text
/poteto-mode run the eval playbook on this skill change. same task for both variants, candidates stay blind.
```

スキルが欠落し続けていて、何をすべきかがわかっている場合は、1 つのタスクで変更してテストします。

```text
/poteto-mode update the review skill so it flags missing migrations, and eval the change.
```

事前に評価を要求すると、編集が正直に保たれます。 1 つの悪いセッションから作成された修正は、そのセッションに過剰に適合する傾向があり、何度も編集するとスキルが変動します。 eval はリリース前にドリフトを検出します。

[評価プレイブック](../../skills/poteto-mode/playbooks/eval.md) は、1 つの障害モードであるオブザーバー効果を中心に構築されています。自分が評価されていることを知っているエージェントは、異なる動作をします。したがって、候補エージェントは、サニタイズされたディレクトリ内で有機的に見えるタスクを取得します。「評価」や「候補」という言葉は決して表示されず、互いの存在も表示されません。 1 人の審査員が中立的なラベルの下ですべての出力を採点し、チェーンフォローでは、主張する内容ではなく、各受験者が実際に読んだファイルに基づいて採点されます。

評決を受け入れる前に、すべての出力を自分で読んでください。裁判官の意見に同意できない場合は、自分の判断を疑う前に、ルーブリックを疑ってください。

<a id="build-a-bot-ui-with-make-bot-ui"></a>

## `/make-bot-ui` を使用してボット UI を構築する

状況に応じたスキルの 1 つは、Grok Bot ユーザー向けです。 [`/make-bot-ui`](../../skills/make-bot-ui/SKILL.md) は、Webhook ルーチンを介してボットを起動するボタンを持つ小さなページを構築します。たとえば、レビュー キューをスワイプし、スワイプするたびにボットにそのアイテムに対応するよう依頼することができます。マシン上のサーバーが Webhook の送信者キーを保持するため、キーがブラウザーやチャットに到達することはありません。このスキルには、Tailscale でのページの公開も含まれます。

**落とし穴:** 動作が正しくないため、タスクの途中でスキルを編集しないでください。独自の PR で修正し、タスクを進め続けます。機能作品に組み込まれたスキル編集は目に見えず、評価することもできません。
