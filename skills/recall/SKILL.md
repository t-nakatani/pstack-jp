# リコール

**作業を開始または再開する前に、ユーザーの最近の作業コンテキストを再構築し、現在の状況と次に何をすべきかについての緊密なカプセルを返します。**

話題をしっかりと押さえておきましょう。スコープ内のスレッドに必要なものだけを読み取り、停止します。

コンテキストは 2 つのレコードに存在します。あなた自身のチャット履歴には、あなたが行ったこと、決定したことが記録されます。共有レコードには、別の名前で同じコードに関して発生したすべてが保存されます。ユーザーが報告し続ける症状、リリースされて元に戻された修正、本番環境で引き続き発生するエラーなどです。 2 番目のレコードは、**why** スキルがソース管理、問題トラッカー、チャットおよび問題チャネル、長文ドキュメント、エラー追跡全体にわたって検索するものです。長いバグテールを持つ機能には、ストーリーの大部分がそこに保持されているため、トランスクリプトのみから再構築しないでください。

トランスクリプトは `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl` にあります。ここで、`<slug>` は、先頭のスラッシュが削除され、各 "/" が "-" に変換されたワークスペース パスです (したがって、`/Users/you/proj` は `Users-you-proj` になります)。すべての行が 1 つのチャット メッセージです。

1. 分類してからルーティングします。再開する特定の以前のチャットの 1 つは、これではなく `session-pickup` プレイブックです。習慣を永続的なスキルに変えるのは `automate-me` です。人間が読める形式の作業内容の要約は別の作業です。 Recall は、行動する前に最近のチャット全体で作業コンテキストを読み込みます。ユーザーがすでに完全な状態カプセル (パス、ブランチ、変更) を提供している場合は、それを使用してマイニングをスキップします。
2. 検索する前にスコープをロックします。ウィンドウ (「最近」は実際の範囲で、デフォルトは過去 7 日間)、名前が付いている場合はトピック、およびワークスペース (デフォルトはアクティブなものです。尋ねられない限り、他のプロジェクトのトランスクリプトを決して読まないでください) を固定します。範囲を明記します。 「すべて」を黙って「最近の N」に変えないでください。
3. チャット履歴全体に広がります。高速で安価なモデル上で並列サブエージェントを生成し、それぞれがコーパスのスライスを取得します。すべてのサブエージェントに、UUID 名ではなく実際の変更時間 (`ls -t`) で候補を並べ替えるよう指示します。最初にトピックを grep してから、一致するチャットとその関連領域のみを読み取り、現在のチャットと明らかなノイズ (サブエージェント、評価、テスト チャット) をスキップします。それぞれが同じスキーマを返し、チャットごとに 1 ブロック: トピック、ユーザーの目標、決定、オープン スレッド、問題と修正、成果物 (PR、チケット、ブランチ) を返し、それぞれがチャット UUID を引用します。 1 つまたは 2 つのチャットの場合は、ファンアウトをスキップして直接検索します。生のトランスクリプトはサブエージェントに残ります。メインスレッドは結果のみを取得します。
4. トピックが機能、ファイル、サブシステム、領域、またはバグに名前を付けるたびに、共有レコードをスイープします。これはデフォルトであり、判断の余地はなく、「X に関する私の取り組み」がそれを免除するものではありません。それを **why** スキルのソース調査者に渡しますが、彼らの質問は「なぜこのように構築されたのか」から「現在の状態は何なのか、何が試行されても解決しなかったのか、そしてユーザーはまだ何を報告しているのか」へと方向転換してください。ソースごとのプレイブックを再利用し、チャット履歴マイニングと並行して調査員を実行し、その姿勢を継承します。つまり、ソースごとに 1 人の調査員、null 結果は結果、使用できない MCP はスキップしてその旨を伝えます。戻ってきたものをブリーフに折り込みます。このステップは、名前付きターゲットのない純粋なアクティビティの呼び出し (「今週何をしたのか」) の場合にのみスキップしてください。この場合、自分の履歴と現在の状態がすべての答えとなります。
5. ライブ状態に対して検証します。マイニングとスイープによって表面化された PR、ブランチ、チケットを取得し、`git` と `gh` で確認します。答えがエージェントが実際に行ったこと (実行したツール、読み取ったファイル、発生したエラー) に依存する場合は、トリミングされたローカル コピーだけでなく、完全なトランスクリプトを読んでください。
6. 以下に契約書の概要を記載します。スレッドごとにグループ化します。指定されたトピックに留まります。

<a id="output-contract"></a>

## 出力コントラクト

カプセルでリードし、次にスレッドのステータス、次に問題、そして次の動きに進みます。より深い詳細は以下に記載されるか、カットされます。

- **カプセル。** 最大 5 弾。この作品が何なのか、そして全体的にどのような位置にあるのか。
- **スレッド。** 各行に 1 つのステータス タグがプレフィックスとして付けられます: `[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]`、または `[planned, not started]`。タグのないスレッドはまだ完了していないのでタグを付けます。
- **問題。** 繰り返し発生する問題は最大 5 つです。ユーザーが報告し続ける症状と、リリースされて取り消された修正を含めて、次回の試行が最後の試行が失敗したところから開始されるようにします。
- **次の動き。** 最も有用な次のアクション、具体的です。

隣接するフィーチャまたはチケットは、これをブロックしない限りアウトのままになります。カプセルと糸のラインが画面を超える場合は、糸をカットする前に細部をカットしてください。 **unslop** スキルを使用して概要を作成し、UUID ごとにチャットの結果とソースごとに共有レコードの結果 (PR 番号、チケット ID、チャット パーマリンク、エラー トラッカーの問題) を引用し、公開出力の前にプライベート コンテキストをサニタイズします。

**返信:** 上記の契約書に対する概要。
