# 利用体験を優先する

実装の利便性がユーザーの喜びと矛盾する場合は、喜びを選択してください。

- すべての機能、コントロール、オプションは正当化される必要があります
- リリースを減らし、より良いリリースを実現 (3 つの機能で洗練された経験が、10 の機能で粗末な経験を上回ります)
- コミット前のプロトタイプ (製品コードよりも使い捨て HTML のほうが設計上の決定が安価です)
- 詳細を正確に把握します (トランジション、位置合わせ、間隔、フィードバック、エラー状態)
- コア ループを強化します (すべての機能が中央のワークフローに使用されるか、邪魔にならないようにする必要があります)

ユーザーとは、作品を消費する人です。エンドユーザーであるUIの場合。ライブラリまたは内部 API の場合、それをインポートするのは同僚です。次にコードを保守するエンジニアもユーザーです。彼らの経験を同じ方法で評価し、彼らの視点から影響を説明します。

財団はエクスペリエンスを提供する必要があります。基礎的な考え方が仕事の「順序」を決定します。この原則は *ターゲット* を支配します。
