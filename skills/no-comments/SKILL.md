<a id="no-comments"></a>

# コメントはありません

スポーンコメント シッコ。受け入れられた結果に基づいて行動します。

コメントは保留 シッコの新鮮な視点。

<a id="scope"></a>

## スコープ

呼び出し元のファイルまたは diff を使用します。それ以外の場合は、ベース ブランチに対する現在の diff (作業ツリーを含むデフォルト `main`) を使用します。

<a id="steps"></a>

## の手順

1. `Task` を `subagent_type: "Comment Sicko"` で生成します。スコープを通過します。そのルールを改めて述べないでください。
2. そのレポートと差分を調べます。アプリケーション コードの編集、スコープ エスケープ、例外保護された削除、`MUST KILL` の理由の誤り、および保持された意図的なコードを有罪として扱うフラグを拒否します。コードサプライズの Reshape フラグは引き続き実用的です。それらのコメントは復元しないでください。砦は、それが私たちには変えられないものであるという証拠がある場合にのみ存続します。スコープ指定された lint および TypeScript の抑制を監査します。正確性または安全性の抑制は、`MUST KILL`s まで実行可能のままです。完全な例外と範囲指定された証明を使用してのみ削除を復元します。シン `IMPORTANT` または `do not remove` のキルまたはキープを受け入れる前に、それらのシンボルに対して `/how` または `/why` を実行します。キルがあいまいな場合は復元しないでください。キープが反駁されている場合、または依然として曖昧な場合は、削除してください。失敗という名前の拒否されたレポートを 1 つ取り消して再実行します。 2 番目を拒否し、開いていることを報告し、`/no-comments` で失敗します。
3. 無効なパスを削除するか、パラメーターを削除するか、実際の API を使用して、些細な受け入れられたフラグを直接修正します。修正が必要な場合は、受け入れられたセットと周囲のコードに対して `/architect` を 1 回実行します。スケッチで停止します。建築家の形。ステップ 4 を実装します。
4. 範囲内の最小の根本原因の修正を実装します。名前付きの回避策をすべて削除します。根本原因が範囲外の場合は、範囲内の最小の修正を実行し、残りは未解決であることを報告します。 **principle-fix-root-causes** および **principle-redesign-from-first-principles** のスキル ガイドは目的のみです。フェンスを広げることも、フェンスの外側にあるインスタンスを固定することも許可しません。決して症状ガードをボルトで締めないでください。
5. 制約コメントには、`do not remove`、`do not change wording`、または `talk to X before changing` と表示されます。休暇は私たちが変えることができないものについて守り続けます。範囲内の最も安価なタイプ、ランタイム、テスト、または CI lint を提供します。インタラクティブな承認を待ちます。無人および評価には呼び出し側の事前承認が必要です。承認された場合は、エンコードしてから削除します。それ以外の場合は、削除し、拘束が開いていることを報告し、範囲外の作業をスケッチします。
6. 削除数、復元されたコメント、再実行、アーキテクト スケッチ、修正、エンコード オファー、エンコード、強制されていない制約、およびその他の未解決の作業をレポートします。
