<a id="figure-it-out"></a>

# それを理解してください

タスクがプレイブックに一致しない場合は、プレイブックをデザインします。コードの前の成果物はワークフローそのものです。つまり、タスクに合わせて厳密に調整し、科学的手法を実行し、人間が作業を終えた後に監査できる意思決定の証跡を残す一連のフェーズです。

<a id="start"></a>

## スタート

最初の項目が **poteto-mode** スキルの原則セクションを読むことである todolist を開きます。次に、以下のフェーズを Todo として追加します。

<a id="phase-a-frame"></a>

## フェーズ A: フレーム

最初に接地してからコミットします。次のことを言えるようになるまで、実行を開始しないでください。

- 反証可能な述語としての Done の定義 (**prove-it-works** 原則スキル)。
- 定量化されたスコープ: 大まかな単位と労力、および表面化したブロッカーの接地。
- 厳密さのレベルは高く偏っています。一方通行のドアと大きな爆発半径がさらに広がります。可逆的なローステークスのステップは少なくなります。厳密さは門や成果物であり、「もっと頑張ろう」ということではありません。

長期的な実行に取り組む前に、枠組みとトレードオフを提示します。可逆的な作業は進行します (**人間をブロックしない** 原則スキル) が、数時間の実行で 1 つのチェックポイントを獲得します。

<a id="phase-b-design-the-workflow"></a>

## フェーズ B: ワークフローの設計

独立して着陸可能な原子単位に分解します。最も危険なものから未知のものを順に並べます。足場と検証は機能 (**基礎的思考** の原則スキル) よりも優先されます。

- 変更前の状態から取得したベースラインを使用して、作業前に検証ハーネスを構築します。これにより、チェックで「古い値と新しい値」が読み取られます。
- 一方通行のドアの設計を決定するには、**architect** スキルを実行します (**arena** を実行します)。すでに形状が具体的な機械的な作業の場合はスキップしてください。確立された設計に関する 2 番目の領域は、オーバーエンジニアリング (**怠惰なプロトコル** の原則スキル) です。
- 何をファンアウトするかを決定します。シーム間でのみ並列化し、各ワーカーに独自のワークツリーまたはブランチを与えます (**共有状態をシリアル化する前に分離する** 原則スキル)。煽りすぎないでください。
- 設計されたフェーズのリストを書き留めます。そのリストは人間がレビューするものです。

次にデザインを実行します。フェーズ C のエントリの後、フェーズ D の前に、そのステップを具体的な項目として Todolist に追加します。フェーズ C のループ規律に基づいてそれぞれを実行し、最後までトレイル全体を保存するのではなく、各ステップが到達するたびにフェーズ D のログを 1 行織り込みます。

<a id="phase-c-run-the-loop"></a>

## フェーズ C: ループを実行する

各ユニットは実験です。仮説を述べ、最小限の変更を加え、実際の成果物の述語に照らして測定し、進んだ場合は保持し、進んでいない場合は元に戻します。
**sequence-verifiable-units** 原則スキルを適用し、最後にチェックをバッチ処理するのではなく、次のユニットを開始する前に各ユニットを検証します。

- 自己報告ではなく、アーティファクトを検査して検証してください。何かがあまりにも簡単に通過する場合は、システムの前に観察方法を疑ってください。
- 委任された作業を裁判官とペアにします。労働者がゲートを利用した場合は、契約をリセットして強化します。ゲート自体が間違っている場合は、ゲートを迂回して配線するのではなく、ゲート自体の変更を修正します。
- 評決は検証済み、未検証、または未定です。決定的でない場合は合格ではありません。ネガティブなことを隠さないでください。

<a id="phase-d-keep-the-audit-trail"></a>

## フェーズ D: 監査証跡を保存する

**show-me-your-work** スキルを使用して実行を記録します。通常、figure-it-out の作品は、査読者が PR で読めるようにトレイルをコミットするほど野心的なものです。痕跡と差分によって、人間は戻ってきてその作業を信頼できるようになります。

<a id="phase-e-verify-and-hand-back"></a>

## フェーズ E: 確認して差し戻す

ハーネスだけでなく、実際の製品のフェーズ A 述語と照らし合わせて全体をチェックします。繰り返し発生する修正をゲート、lint ルール、チェック、またはスクリプトとしてエンコードします (**encode-lessons-in-structure** 原則スキル)。

**返信:** 設計したプレイブック、厳密さのレベルとその理由、意思決定の軌跡、述語に対して検証された内容、および未解決の内容。
