<a id="automate-me"></a>

# 自動化してください

ユーザーの作業慣例をスキル エージェントに変えるためのガイド付きフローが続きます。出力は、それらに合わせて調整された 1 つの `-mode` スキル (例: `jay-mode`、`priya-mode`) です。

このスキルは、インライン マイニング パス (ステップ 1 を参照)、Cursorの組み込み `create-skill` (オーサリング)、**unslop** スキル (文章規律) という他の 3 つのスキルを調整します。それはそれらを順序付けします。それはそれらに代わるものではありません。

<a id="flow"></a>

## フロー

<a id="0-check-for-an-existing-skill"></a>

### 0. 既存のスキルを確認する

ユーザーのハンドルに一致する `.cursor/skills/**/*-mode/SKILL.md` および `~/.cursor/skills/*-mode/SKILL.md` を再帰的に検索します。モード スキルは、トップ レベルだけでなく、個人カテゴリ ディレクトリ (`.cursor/skills/<handle>/`) にも存在できます。存在する場合は、`AskQuestion` で意図を確認します (すでに「スキルを更新する」などと言われている場合を除く)。

- 既存のスキルを更新します (繰り返し実行のデフォルト)
- 新たに開始する (まれですが、実行する前に理由を尋ねます)

更新モードでは、フローの残りの部分が変更されます。
- ステップ 1 では、スキルが最後に編集された (`git log -1 --format=%cI <path>`) 以降の履歴のみがマイニングされます。
- ステップ 2 では、何をゼロからキャプチャするかではなく、何が変更され、何が欠落しているかを尋ねます。
- ステップ 4 では、既存のファイルをその場で編集します。ユーザーが矛盾していないセクションを保持します。新しい証拠を使って改訂します。新しいセクションは、真に新しいルールに対してのみ追加してください。

<a id="1-mine-their-history"></a>

### 1. 彼らの歴史を掘り起こす

ファンアウトする前に、アクティブなワークスペースのトランスクリプトを見つけます。システム プロンプトは、ワークスペースの `agent-transcripts/` ディレクトリに名前を付けます。そのパスのみを使用してください。 `~/.cursor/projects/*/` を越えてグロブしないでください。これにより、ワークスペースの境界を越えて、無関係なプロジェクトからプライベート チャットが読み取られます。

その範囲内での最近のエージェントの会話を調査して、繰り返し発生するパターンを調べます。履歴のスライスにわたって複数のサブエージェントを並行して実行します (たとえば、過去 2 ～ 4 週間、それぞれに十分なマテリアルが含まれるように 3 つのスライスに分割)。各スライス マイニング サブエージェントは、親が提供するワークスペース スコープのパスからトランスクリプトを読み取り、以下のシグナルを探し、証拠ポインタを使用して検出したパターンの短い構造化リストを返します。探す価値のあるデフォルトのシグナル:

- 応答の設定 (長さ、トーン、フォーマット、「馬鹿げた」修正)
- 委任の習慣 (サブエージェント、モデル、特殊なワークフロー、並列処理)
- 検証の姿勢 (「完了」の意味、単体テストとライブ再現、レビュー担当者)
- コードと文章の規律 (スタイル、引用された原則、lint/フォーマット ツール)
- プロセスの規則 (ワークツリー、コミット、PR、レビュー/マージ ツール)
- メタ設定 (タスク中のスキルの修正、新しいスキルの提案)

信号を上げる前にスライス全体をクロスチェックします。 2 つ以上のスライスで見られるパターンは信頼性が高くなります。単独の信号は弱く、通常はドロップされます。

<a id="2-ask-the-user-directly"></a>

### 2. ユーザーに直接質問する

マイニングは、まだ現れていない意図を見逃します。ユーザーに最初から入力するよう求めるのではなく、`AskQuestion` ツール (構造化された複数選択) を使用します。

形式: それぞれ 4 ～ 6 の選択肢を持つ 1 つまたは 2 つの質問、カテゴリの質問は `allow_multiple: true` です。まずは広範囲 (「どの分野が最も重要ですか?」) から始めて、次に特定のオプションを使用して選択した分野をフォローアップします。構造化されたラウンドの後、自由形式のチャットの質問が 1 つあり、選択肢で見逃したものがすべて見つかります。

20 個の質問を捨てないでください。

<a id="3-cluster-findings"></a>

### 3. クラスターの結果

結合された信号をセクションにグループ化します。一般的なもの (該当するもののみを使用してください):

- **応答スタイル**: 長さ、トーン、形式。
- **自律性**: 質問せずにどれだけ行うか、MCP ツールの使用。
- **最初に理解してください**: 変更の範囲を決めたり調査したりするときに、どのスキルに到達する必要があるかを理解してください。
- **サブエージェント**: デフォルト、並列処理、モデルからタスクへの特殊なワークフロー。
- **文章/コードの規律**: 原則、lint ツール、スタイル ガイド。
- **レビューと検証**: 再現姿勢、検証スキル、ライブ テスト ツール。
- **プロセス**: git ワークツリー、コミット、PR、レビュー/マージ ツール。
- **スキル**: スキルを作成する習慣、まずスキルを修正する、新しいスキルを提案する。

**poteto-mode** スキルがその形を示します。粒度を知るために読んでください。その内容をコピーしないでください。ユーザーのルールはポテトモードのルールとは異なります。

<a id="4-draft-the-skill"></a>

### 4. スキルのドラフト

Cursor の組み込み `create-skill` スキルを使用してスキルを作成します。配置:

- パス: 既存のモード スキルのカテゴリを保持します。新しいモードの場合、リポジトリにそのハンドルの個人カテゴリが確立されている場合は、`.cursor/skills/<handle>/<handle>-mode/SKILL.md` を使用します。それ以外の場合は、プロジェクトのデフォルトの `.cursor/skills/<handle>-mode/SKILL.md` (またはユーザーが個人スキルを好む場合は `~/.cursor/skills/<handle>-mode/`) になります。
- ハンドル: ユーザーの名または選択した識別子。
- フロントマター `description`: 「コードを書く」や「PR をレビューする」などの一般的なキーワードではなく、名前 + `/<handle>-mode` + 「彼らのスタイルで仕事をする」でトリガーします。
- フロントマターの書式設定: `create-skill` の YAML ルールに従います。 `description` を 1 つの YAML スカラーとして保持します。句読点や折り返しが必要な場合は、引用符で囲むか、継続行をインデントして `description: >-` を使用します。
- デフォルトではフロントマター `disable-model-invocation: true`。ユーザーがモードを毎ターン適用することを明示的に希望する場合にのみオプトアウトします。

<a id="5-iterate-on-prose"></a>

### 5. 文章を反復する

**unslop** スキルと `create-skill` の書き方ガイドラインをすべての行に適用します。

ドラフトをユーザーに見せてフィードバックを受け取ります。複数回の反復が予想されます。容赦なく斬る。モードスキルはマニュアルではありません。

<a id="6-land-it"></a>

### 6. 着地させよう

メインから離れたワークツリーで作業します。 PR をコミットして開きます。 main に直接プッシュしないでください。

<a id="guardrails"></a>

## ガードレール

- **1 つの会話に過度に適合しないでください。** 一度述べたものの、別の機会に矛盾した好みはノイズです。コード化する前に複数のインスタンスが必要です。
- **賢くならないでください。** 他のスキルの内容を言い換えたり、比喩を発明したり、エージェントの読者向けに「詩的な」文章を書いたりすることは、コストがかかりますが、利益はありません。稼働状態を維持してください。
- **参照、インライン化しないでください。** ユーザーが依存する他のスキルは、貼り付けられた抜粋ではなく、パス参照として表示される必要があります。他の場所で管理されている原則ドキュメントについても同様です。
- **セクションは最小限にしてください。** ユーザーがデフォルト以外の特定のルールを持っている場合にのみセクションを追加してください。 「わかりやすく伝える」はセクションではありません。 「短い段落。オプションを比較する場合は表。箇条書きは項目が完全に平行している場合のみ。」は。
- **一般的な命名規則** 命令文では、作成者の名ではなく、「ユーザー」または「人間」を使用します。
- **対称性を強制しないでください。** ユーザーに書き留める価値のあるプロセス ルールがない場合は、「プロセス」セクションを完全にスキップしてください。

<a id="evaluation"></a>

## の評価

`-mode` スキルは主観的な出力です。 `create-skill` スタイルのテスト/反復ベンチマーク ループは、ここでは役に立ちません。ユーザーに雰囲気をチェックしてください。ユーザーの好みに合っているかどうかを確認してください。何か見逃していましたか？それからリリースします。

スキルのトリガー精度が実際上問題であることが判明した場合にのみ、説明最適化ループを実行します。

<a id="when-not-to-use"></a>

## 使用しない場合

- ユーザーはタスク固有のスキル (作業規約ではない) を望んでいます: `create-skill` のみ、マイニングは必要ありません。
- ユーザーは 1 つの狭いワークフロー (例: 「コミット メッセージの書き方」) をキャプチャしたいと考えています。それはモードスキルではなく通常スキルです。
