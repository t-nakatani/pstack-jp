<a id="architect"></a>

# アーキテクト

実装前の設計。 `not implemented` 本体と疑似コードを使用して、型、関数シグネチャ、クラス形状、モジュール境界をスケッチします。複数のモデル パースペクティブを合成し、選択したスケッチに対してコードを入力します。実装によってスケッチが間違っていることが判明した場合は、スケッチを破棄して再設計します。

<a id="start"></a>

## スタート

開始する前に、フェーズごとに 1 つのエントリを含む todolist を開きます。

1. アース
2. スケッチ
3. 同意する
4. 実装
5. スクラップ

<a id="phase-a-ground-the-problem"></a>

## フェーズ A: 問題を接地する

新しいコードが触れるすべてのシステムの実際のメンタル モデルを構築します。関連するサブシステム上で **how** スキルを実行します。

ファイルに名前を付けるのは根拠がありません。 `how` が規定するトレースされたモデルを生成します。デザインで所有権や階層化が再定義されている場合は、既存の形状に対して **why** スキルも実行して、根拠が推測ではなく制約になるようにします。

作業が純粋にグリーンフィールドであり、統合する周囲のシステムがない場合にのみ、フェーズ A をスキップします。

<a id="phase-b-sketch"></a>

## フェーズ B: スケッチ

デザイン スケッチ タスクとフェーズ A 接地アーティファクトを使用して **arena** スキルを実行します。各ランナーのプロンプトとして `references/runner-prompt.md` を渡します。各候補者は、`references/rationale-template.md` に従って形成されたデザイン パッケージを作成します。

`arena runners` 行の代わりに、`pstack-models.mdc` ルールの `architect runners` 行からランナーを取得します。ルールまたはその行が欠落している場合は、`claude-opus-5-5-xhigh` および `grok-4.7-xhigh-fast` を使用してください。エイリアスと拒否されたエントリは、**arena** スキルのフェーズ A のランナー ルールに従います。

2 回デザインします。最初の候補で十分であるように見える場合でも、合成前に少なくとも 2 つの構造的に異なる候補が必要です。これは、**デザインスペースを徹底的に**するための基本的なスキルを具体化したものです。 1 つの形状内の点を修正するのではなく、形状全体の代替手段。

合成前に [`references/design-red-flags.md`](references/design-red-flags.md) に対してすべての候補をスクリーニングします。次の貢献者は、自分が開いたファイルのみを参照し、最も近いサンプルをコピーし、コンパイルする最短パスを取るエージェントであると仮定します。 1 つのファイルからの変更がリポジトリ全体に適切であるような設計を好みます。

インターフェイスの深さに関する実行可能な候補を比較します。より小さく、よりシンプルな公開表面の背後に、より複雑さを隠すデザインを好みます。豊富なインターフェイスは、機能をレイヤー間で分散させるのではなく集中させることで、呼び出しチェーンを短く保つことができます。

Arena は 1 つの合成されたデザイン パッケージを返します。合成の決定は、理論的根拠の「合成の決定」セクションに入力されます。

<a id="phase-c-agree-opt-in"></a>

## フェーズ C: 同意する (オプトイン)

デフォルト: 合成されたデザインを使用してインプリメンテーションに直接進みます。人間によるチェックポイントはありません。

実行者が「チェックポイント付きの/architect」、「実装する前に停止して表示」などの明示的な要求を行った場合に、チェックポイントにオプトインします。次に、合成されたデザインを表示し、承認のために一時停止します。

合成は、**基礎的思考** 原則スキルの「足場ファースト」モードとして、いずれの方法でも独自のコミットとしてリリースできます。 **結果重視の実行**の原則スキルに従って、フィルイン中に計画的かつ範囲を定めた中断は問題ありません。実装前に設計に敵対的な圧力がかかるようにするには、合成されたスケッチに対して **interrogate** スキルを実行します。

人間が (チェックポイント中または事後) 形状を押し返した場合、それをフェーズ A の証拠として扱います。さらにコードを記述する前に、フェーズ B を再接地して再実行します。

<a id="phase-d-implement-against-the-sketch"></a>

## フェーズ D: スケッチに対する実装

`not implemented` の本体をコードに置き換え、擬似コードをロジックに置き換えます。合成されたスケッチが契約書となります。

スケッチからの逸脱は、表面化する価値のある信号であり、静かに吸収すべき摩擦ではありません。スケッチが予期していなかったパラメーターが関数に必要な場合は、スケッチが間違っていたのか、要件が欠落していたか、または実装が行き過ぎていたのかを尋ねます。

<a id="phase-e-scrap-when-the-architecture-is-wrong"></a>

## フェーズ E: アーキテクチャが間違っている場合は廃棄する

実装でスケッチが吸収できない摩擦が発生し続ける場合は、スケッチを破棄してください。 **第一原則からの再設計**と**根本原因の修正**の原則スキルに従って、間違った設計に修正を加えないでください。

シグナルは *パターン* であり、単一のインスタンスではありません。伝える:

- 同じ形の回避策が無関係なコード全体で繰り返し表示されます。
- 特殊なケースの分岐を必要とする、無関係な複数のエッジ ケース。
- コンパイルにエスケープ ハッチング (`any`、キャスト、実際には常に設定されるオプションのフィールド) が必要な型。
- スケッチで状態が共有されていないと示されたときの「ロックが必要です」という反射。
- 呼び出し元は、抽象化を使用するためにその内部ルールを知っている必要があります。
- 実装全体で同じ形状の 2 つ以上の独立した位相 D 偏差。

判断を使用します。いくつかの特殊なケースでは、アーキテクチャが非難されることはありません。一部の問題は当然ながら複雑です。データの複雑さは設計の複雑さではありません。

廃棄する場合:

1. 構築されたものに対して **how** スキルを再実行します。
2. 第一原理からの再設計に従い、新しい制約が初日の仮定であったかのように再設計します。
3. **加算する前に減算する**原則スキルに従って、加算する前に減算します。新しいスケッチは、成長する前に古いスケッチよりも小さくなる必要があります。
4. フェーズ B に戻り、アリーナを再実行します。

<a id="outputs"></a>

## 出力

呼び出し元の使用法が最初に記述され、型スケッチはそこから派生します。小さな変更のための新しいタイプと署名を含む 1 つのファイル。より大規模な作業のためのモジュール マップと型定義。使用方法のスケッチや合成の決定など、`references/rationale-template.md` に従って形成された理論的根拠も同梱されています。
