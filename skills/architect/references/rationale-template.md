# 根拠テンプレート

タイプスケッチと一緒にリリースされる文章。 1ページ。文例の見出し、定型文なし。斜体の注を実際の内容に置き換えてください。

<a id="problem"></a>

## 問題

*1 段落。私たちがやろうとしていること、そして既存のシステムや制約が形状を不明確にしていることは何か。 [フェーズ A](../SKILL.md#phase-a-ground-the-problem) によって、設計が遵守する必要がある制約 (相互運用する既存の型、破ることができない呼び出し元、境界を越えた不変条件) が表面化した場合は、読者が見たものと同じ制約が見えるように、ここでそれらに名前を付けます。

<a id="usage-callers-view"></a>

## 使用法 (呼び出し側の視点)

*タイプスケッチの前にこれを最初に書きます。消費者が読む README またはクイックスタートに加えて、独自のコード内の 2 つまたは 3 つの現実的な呼び出しサイトを表示します。輸入するもの、呼び出すもの、戻ってくるもの。 [Shape](#shape) のタイプ スケッチはこれから派生しています。二人は同意する必要があります。相違がある場合は、その逆ではなく、スケッチを用途に合わせて調整します。発信者の経験が仕様です。タイプはそれを提供します。*

<a id="shape"></a>

## 形状

*推奨アーキテクチャ。まずデータ構造。次に、データが署名を介してどのように流れるか。負荷がかかる決定に名前を付けます。どの不変条件が型にエンコードされているか、検証が存在する場所、およびシステムが意図的に実行しないことを示します。インターフェースの深さを明示的に判断します。パブリック サーフェスがどのような複雑さを隠しているか、何が呼び出し元に公開されたままになっているか、およびインターフェイスが必要以上に大きくない理由を説明します。各決定の背後にある原則を引用します (例: `per boundary-discipline`)。再言しないでください。*

<a id="synthesis-decision"></a>

## 合成決定

*[アリーナ](../../arena/SKILL.md) によって入力されます。どの候補がベースになったのか、その理由、他の候補から何が採用されたのか、何が却下されたのか、そしてその理由を記録します。*

<a id="tradeoffs-accepted"></a>

## トレードオフは受け入れられました

*選択した形状によるトレードオフごとに 1 つの弾丸。形式: 「Y と引き換えに X を受け入れます。」時期尚早な最適化や時期尚早な単純化のように見えるものを含め、将来の読者が見落としと間違える可能性のあるものには名前を付けてください。*

<a id="alternatives-considered"></a>

## 検討された代替案

*必須。少なくとも 1 つの具体的な代替形状を挙げ、その形状が失われた理由を 1 行で説明します。実装の単純さだけではなく、インターフェースの深さに基づいて各選択肢を判断してください。呼び出し元に公開する複雑さと、非表示にする複雑さに名前を付けます。設計領域に実際の候補がある場合、ここには 2 つまたは 3 つの代替案が含まれます。制約によって答えが強制され、結論が「これが唯一の実行可能な形状でした。なぜなら...」という形で表現される場合は問題ありません。同じ形状のフレーバーをリストすることは避けてください。このセクションでは、他のランナー候補ではなく、選択された形状が検討され拒否された設計代替案について説明します。*

<a id="open-questions-and-risks"></a>

## 未解決の質問とリスク

*スケッチ中に人間が考慮する必要があることに気付いた点、および実装を開始する前にフラグを立てる価値のあるリスク。主張ではなく質問として表現するため、人間の答えはコメントではなく解決策になります。*
