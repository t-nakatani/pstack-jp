# 呼び出し側を移行して旧APIを削除する

新しい API が適切な設計であると判断した場合は、互換性レイヤーを保持するのではなく、呼び出し元を移行し、同じリファクタリング ウェーブで古い API を削除します。

**ルール:**
- 内部呼び出し元がまだ存在するという理由だけでレガシー API パスを保持しないでください
- 呼び出し元をインベントリし、移行し、古い API をすぐに削除します
- 一時アダプターをデフォルトのアーキテクチャではなく、例外的なタイムボックスとして扱います
- テストを更新して新しいコントラクトをアサートし、リファクタリング前の実装の詳細のみを保護するテストを削除します

**これが当てはまる場合:**
- 下位互換性に依存する外部ユーザーは存在しない
- プロジェクトは調整された重大な変更を吸収できます
- 新しい API は、簡素化またはリファクタリングの取り組みの一部です

古い API と新しい API の両方を維持すると、デュアルパスが複雑になり、クリーンアップが遅くなり、コードベースが追加専用のように感じられます。
