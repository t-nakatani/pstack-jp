# 型システムを厳密に使う

型チェッカーは証明を支援する道具です。不可能な状態、意味の異なるプリミティブの取り違え、未処理のバリアントをコンパイル時に排除するために使います。型が見逃せてしまうケースは、本来コンパイラが防げたはずの実行時エラーになります。ハンドラーを増やすより、エラーや例外的なケースが存在しない定義を選びます。その道具が、表現できない状態、全域関数、インターフェイスの再設計です。

型を持つあらゆる言語に適用します。`typescript-best-practices` のようなスキルは、この原則を具体的な構文に落とし込みます。

**パターン:**

- **不正な状態を表現できなくする。** バリアントを直和型で表します。TypeScriptの判別可能なユニオン、Rust・Swift・Kotlinの値を持つ列挙型、Scalaのsealedクラス、Haskell・OCamlの代数的データ型などです。矛盾した組み合わせでもコンパイルできる、任意フィールドの寄せ集めで状態を表してはいけません。例えば `{ completed: boolean; completedAt?: Date }` は、意味をなさない `completed: true; completedAt: undefined` を許します。`completedAt !== null` のような単一の情報源から真偽値を導くか、`{ kind: 'open' } | { kind: 'done'; at: Date }` として明示的に分けます。バグを見て「この組み合わせは本当に起こり得るのか」と考えるなら、型が緩すぎます。
- **型は制限ではなく、値の組み立て方である。** 緩い型からチェックで不要な値を除く代わりに、必要な値から型を組み立てます。絞り込み型が必要に見える不変条件も、構造を変えることで表せる場合があります。空でないリストは「先頭要素と残り」であり、長さチェック付きのリストではありません。有効な時間範囲は「開始時刻と期間」であり、順序を保つ必要のある2つの時刻ではありません。特定の表現を特別扱いしません。ペアのリストは偶数長のリストとして解釈できるので、不正な値を構築できない形を選び、その上に呼び出し側が必要なインターフェイスを公開します。
- **意味の異なるプリミティブをブランド型で区別する。** `UserId` と `OrderId` は内部的には文字列でも、取り違えられてはいけません。Rustのnewtype、Swiftの不透明型、Kotlinの値クラス、Haskellのファントム型、TypeScriptのブランド付き交差型などを使います。生成時に一度検証し、それ以降は型を信頼します。
- **外部データは解析するまで型の保証がない。** RPCのペイロード、JSON、IPCメッセージ、CLI引数、設定ファイル、環境変数、データベース行が該当します。各境界に、未構造化の入力を型付きモデルに変換する解析関数を置きます。検証する場所は **boundary-discipline** の原則スキルを参照してください。
- **型システムに嘘をつかない。** コンパイラを迂回するキャスト、安全でない変換、アサーション関数には、実行時クラッシュが潜んでいます。コンパイラが事実を証明できないなら、検証・型の絞り込み・モデルの改善で証明するか、そのキャストが危険だと認識します。
- **網羅性の確認はコンパイラに任せる。** 直和型をパターンマッチするとき、新しいバリアントが追加されて処理が漏れたら、コンパイルが失敗するようにします。TypeScriptの `never` 型の変数、Rustの型注釈なしの `match`、Haskellの `-Wincomplete-patterns`、Kotlinのsealedクラスの網羅性チェックなど、言語が用意する方法を使います。
- **正本となるスキーマから型を導出する。** Protocol Buffers、OpenAPI、GraphQLスキーマ、データベースのマイグレーション、デザインシステムのトークンファイルが構造を定義しているなら、別の型を手で作らず、そこから導出します。**encode-lessons-in-structure** の原則スキルを参照してください。
- **部分的にしか定義できない操作が現れたところだけ、型を強める。** 実行時アサーション、nullチェック、「絶対に起こらないはず」という例外は、型が弱すぎる場所を示します。そのチェックを型に移したら、それ以上は強めません。型システムの役割は、データを限界まで精密に記述することではなく、利用箇所で扱うべきケースを追跡することです。全域関数を優先します。空リストの `sum` は0なので、通常のリストを受け取れます。空リストの `head` には答えがないので、空でないリストを要求します。

**テスト:**

- 「このフィールドの組み合わせが有効になる条件を説明するコメントが書けるか」。書けるなら型が緩すぎます。直和型に分けます。
- 「関数の2つの引数が同じプリミティブ型で、意味は異なっていないか」。異なるならブランド型で区別します。
- 「この `any`、`as`、`assertNotNull` はどこから来たのか」。境界までたどり、そこで検証します。
- 「来月新しいバリアントが追加されたら、コンパイラは次のエージェントに処理の追加箇所を示すか」。示さないならマッチが網羅的ではありません。
- 「この型は、別のファイルが管理する構造を重複して定義していないか」。重複しているなら導出します。
- 「操作を全域に保つために型を強めているのか、単に精密にしたいだけなのか」。強めなくてもパニックが起こらないなら、通常の型を維持します。
