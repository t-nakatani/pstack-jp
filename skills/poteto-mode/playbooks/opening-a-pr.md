### PR を開く

他のすべての プレイブック の最後に呼び出されます。

**ワークツリー。** メインから離れた git ワークツリーから作業します。サブエージェントはそれを継承します。同じブランチ上の複数の `Task` 呼び出しは、それぞれ独自のワークツリーを取得するか、それらの間の `git fetch && git reset --hard origin/<branch>` を取得します。無関係な作業を伴うダーティなブランチ: パッチアウト、新しいワークツリー、適用。うねったワークツリー: メインからリセットし、最小限にやり直します。

**コミットします。** 積極的にコミットしてください。 PR を開く前に、小さく順序付けられたコミットにリベースします。それぞれのコミットは将来の PR です。つまり、着陸可能であり、ストーリーを伝えるように指示されています。修正が作成されたばかりのコミットに属する場合は修正します。分離可能な場合は新しいコミット。

**PRs.** コミット前に、差分に対して `cursor-team-kit` から `/deslop` を実行します。レビューする前に `/no-comments` を実行してください。すべての PR タイトル、PR 説明、およびコミット本文を `/technical-writing` で記述し、`/unslop` を適用します。 Diataxis を除くすべてのテクニカル ライティング レイヤーを適用します。各アクションに 1 つの単語を使用し、記事を保持し、単純な動詞が機能する場合は `-ing` を避けてください。

**タイトル。** `type(scope): subject` 形式の従来のコミットを使用します。タイプとして `feat`、`fix`、`docs`、`refactor`、`test`、`chore`、または `perf` を使用します。 `pstack` や `poteto-mode` などの変更された領域をスコープとして使用します。件名は短く、命令的なものにしてください。変化が起こるとき、実際のシンボルに名前を付けます。たとえば、`fix(pstack): retarget opening-a-pr babysit trigger`。末尾にピリオドを追加しないでください。

**説明。** PR 本文は説明書であり、ラボ ノートブックではありません。差分を持っているレビュー担当者は、変更が存在する理由、変更によって何が除外され、何が壊れる可能性があるか、そしてそれが機能することをどのように証明したかを 1 分以内に理解できるはずです。識別子をほとんど含まない短くて単純な文を書きます。壁に文字を書き込まないでください。スカッシュのコミット本文は PR 本文です。ボディがスカッシュコミットを約 40 行より長くする場合は、ボディをカットしてください。

各セクションを太字の導入部ではなく `##` という見出しの下に配置して、セクションが区別できるようにします。これらのセクションを順番に使用してください。何も言うことがない場合はセクションを削除します。

- `## Why` は、問題とアプローチを 1 ～ 3 つの短い文で示します。 SHA をリストしたり、系図をリベースしたりしないでください。 「メインに基づく」プリアンブルを追加しないでください。
- `## What changed` には 1 ～ 3 つの短い箇条書きがあります。変更が含まれる場合にのみ、実際のシンボルまたはパスに名前を付けます。名前変更または再ターゲットの両側に名前を付けます。
- `## Scope` は常に、PR がカバーするものと意図的に省略するもの (関連するフォローアップや既知のギャップなど) に名前を付けます。短いアイテムを 1 ～ 3 つ使用します。シンボルやパスをリストしたり、ファイルごとにエッセイを書いたりしないでください。
- `## Tradeoffs` は、査読者が質問するであろう拒否された代替案のみを指定します。実際に選択肢がない場合は、このセクションをスキップしてください。
- `## Blast Radius` は、変更が誰に、または何に影響するか、そしてそれが安全であるか危険であるかについて 1 つまたは 2 つの文を示します。メインが赤の場合、赤のままにするコストを示します。
- `## Verification` には 1 ～ 3 個の箇条書きがあります。各箇条書きには、実際の実行パスとその結果が示されています。パフォーマンスの変化については、1 つの主数値とその単位を `before → after` 形式で報告します。残りの証拠については、アリーナまたは swarm ディレクトリをリンクします。サンプルサイズの方法論、群衆の発表、または指標表は含めないでください。

これらのセクションの後に、主張を証明するビデオまたはスクリーンショットを添付してください。完全な SHA、スウォームまたはアリーナ レーンのリサイタル、レバー修正エッセイ、ファイルごとのチェックリスト、または「クリーン」判定を貼り付けないでください。これらの詳細をリンクされた成果物に含めます。コミット本体はその主題を再記述しません。

**フォージ。** 最初の PR 操作の前にフォージを解決し、その選択を作成、編集、表示、監視、およびマージに保持します。 GitHub CLI (`gh`) がデフォルトです。 `command -v origin` が成功し、Origin がリポジトリを解決できる場合は、`origin pr ...` を優先します。 Origin が存在しない場合、またはリポジトリを解決できない場合は、`gh` に留まり、フォールバックを記録します。グラファイトは必要ありません (`gt`)。

**組み込み PR ツール。** 実行で組み込み PR ツールが提供される場合、forge CLI を使用するのではなく、それを使用して作成、編集、リターゲット、準備完了のマークを付けます。独自の説明書にその方法が記載されています。 CLI を使用して作成された PR では、後で実行される説明など、ツールが追跡するものは編集できません。ツールでカバーされていないすべての場合、および実行にそのようなツールがない場合はすべての PR 操作に対して、解決された forge を使用します。

**サイズとスタック** 1 つの大きな PR よりも 5 つの狭い PR を優先します。スタックは基本分岐チェーンです。ルート PR はトランクをターゲットとします。各子ブランチはその親の正確なヒントにリベースされ、その PR は親ブランチをターゲットにします。組み込みの PR ツールを使用しない場合は、解決された forge に従って `origin pr create --status open --base <parent-branch>` または `gh pr create --base <parent-branch>` で子を作成し、`origin pr edit <pr> --base <parent-branch>` または `gh pr edit <pr> --base <parent-branch>` で既存の子を再ターゲットします。単独作業の場合のみトランクから分岐します。実質的なスタック作業の前にトランクでリベースします。

**準備完了** 準備ができたすべての PR を、決して下書きとしてではなく開きます。組み込みの PR ツールはデフォルトでドラフトに設定できるため、それを使用するすべての作成呼び出しで `draft: false` を設定します。 Origin では、`--status open` を渡します。 `gh` の場合は、`--draft` を省略します。 PR がまだドラフトとして開いている場合は、PR ツールを通じて PR を準備完了としてマークするか、解決された Forge に従って `origin pr ready <number>` または `gh pr ready <number>` を実行します。 PR ステータスを参照する前に、`origin pr view <number>` または `gh pr view <number>` を実行してください。

**ベビーシット。** PR を開いてもベビーシットは開始されません。 URL を投稿して構築を続けてください。最初にフェーズまたはスタックを終了します。スタック全体が存在した後でユーザーがベビーシット パスを要求した場合にのみ、個別のベビーシット パスを実行します。新しい PR ごとにベビーシットを行うと、ビルドが停止し、後の Wave が再開されるコミットにチェックが費やされます。フィードバックが意図から逸脱した場合は押し返します。

PR を開くサブエージェントは、`interrogate`、`/deslop`、および `/no-comments` を実行し、URL をポストします。その後、Autopilot-full または Autopilot-stack の所有者でない限り、子守りを行わずに親に戻ります。その所有者の概要はベビーシット ループを割り当て、`playbooks/babysit.md` が待機する要求です。オーナーはコード準備完了レポートの後にループを開始し、プレイブックに記載されているようにマージ準備完了または STACK-READY を報告します。ここと `playbooks/babysit.md` の、スタック全体が構築されるまでベビーシッターを保持するルールは、その所有者には適用されません。
