<a id="orchestrate"></a>

### オーケストレーション

**あなたはプログラムを所有するものであり、コードを所有するものではありません。ブリーフを作成し、キューを空にし、辺境を緑に保ち、決定します。** プロジェクト全体の場合、1 人の常任コーディネーター チャットに引き渡されます。数日にわたって、多数の PR が積み重なり、数十から数百のサブエージェントが存在し、人間は 5 分ごとではなく 1 日 2 回チェックインします。述語によって駆動されるタスクの 1 つは自律実行です。オーダーメイドのワークフローを必要とする野心的な実行の 1 つは、「把握」です。作業が単一のエージェントよりも長引く場合は、ここにルーティングします。 1 人のエージェントがセッションの予算内で完了できる作業はプログラムではありません。

式典はプログラムに合わせて規模を拡大する必要があります。安価なほぼ同一のユニットでは、各セクションの指示に従って折りたたんでください。

残りは 3 つのルールで決まります。

- 完了はキュー イベントであり、割り込みではありません。
- すべてのスポーンとすべての履歴書には、継続的な命令がそのまま記載されています。
- 概要は商品です。従業員は質問できないため、曖昧な概要は静かに失敗します。

<a id="roles-and-placement"></a>

#### 役割と配置

- **コーディネーター (このチャット)。** ローカル。フレームを作成し、ブリーフを作成し、受信箱を空にし、人間のレポートを所有し、判断を下します。コードを作成したり編集したりすることはありません。競合するマージ、再スタック、およびコードの変更は常にタスクです。検証済みのユニットを機械的にランディングする (ワーカーのコミットを早送りまたはクリーン チェリーピックしてからプッシュする) ことは、ローカル git が安価なリポジトリ上でコーディネーターが自動的に実行できる簿記です。完成した作品をアイドル状態のスタッカーの後ろに並べると、締め切りを過ぎても何も収穫されません。ループはエージェントのエンドツーエンドです。エージェントは、タスク ツールを介してのみ生成、再開、排出されます。状態の読み取りと書き込みは、ドレイン ポイントで `scripts/orch/orch.ts` を経由し、1 つのコマンドが入力され、1 つのラインが出力されます。 CLI は何も生成したり、待機したり、ウェイクアップしたりすることはありません。
- **サブコーディネーター** 常にローカル、耐久性があり、トラックごとに 1 つ、プログラムが 1 つのコーディネーターの排水量を超えた場合のみ。コーディネーター自体が排出できるトラックには中間層は必要ありません。ネストされた各レイヤーは完全なオリエンテーション プリアンブルを再支払いし、ブロッキング サブコーディネーターは親がアイドル状態である間、その子を非表示にします。トラックのユニットとボードを所有し、ワーカーの概要を作成し、独自のワーカーと検証者を生成します (ネストは深さ 3 まで機能し、ネストされた生成には `environment` を含む完全なタスク スキーマが含まれます)。波の境界で骨材をロールアップします。生の子レポートは決して転送しないでください。機内の子供たちには、1 つの排水管で処理できる量をローリング ウィンドウとしておよそ 10 個に制限します。すべてのバッチの中で最も遅い子にコストがかかるブロッキング バッチのようにはなりません。
- **ワーカー/検証者** タスクがこのマシンを必要としない限り、常に `environment: "cloud"` です: `control-ui` または `control-cli` ランタイム検証 (`cursor-team-kit` から)。 `agent-transcripts/` でローカルのトランスクリプトを読み取ります。シミュレーターとローカル IDE の状態。ここにしか存在しない本物。クラウド エージェントはローカル ストアを読み取ることができないため、概要には必要なものがインライン化されるか、リポジトリ パスが示されます。より少ない、より広範囲の労働者を好みます。ワークツリーまたはブランチごとに 1 つのライター (原則としてシリアル化前に分離、共有状態)。ユニットのベリファイアをそのワーカーとは異なるモデル ファミリで実行します。

深さはコーディネーター、トラック、ワーカーに留まります。プロジェクトごとにトラック分解を作成します (ビルド、ランディング、および検証は一般的な部分であり、必須の形状ではありません)。ハードコーディングされたスウォーム ツリーは試行されましたが、硬すぎるため保留されました。

<a id="store-layout"></a>

#### 店舗レイアウト

現在のエージェントのストア (システム プロンプト内のパス) に `orchestrate/<project-slug>/` を作成します。すべてのファイルには 1 つのライターが存在します。所有者は事実を公開し、読者は読み取り時に集計します。簿記には `bun scripts/orch/orch.ts` を使用します (以下では `orch` として記述します)。ただし、その正規のプレーン TSV と JSON は CLI なしでも読み取り可能なままです。

- `preferences.md` はスタンディング オーダー レジスタです: 番号付きの行、それぞれ 1 つの制約 (モデル ポリシー、スタックの形状と数、検証バー、禁止されたパス、エスカレーション ポリシー)。すべてのスポーンとすべての履歴書にそれをそのまま貼り付けます。指令は履歴書ごとに減衰し、ドロップされるたびに人間のターンがかかります。指示を言い換えていることに気づいた場合は、行動する前にその行を追加してください (principle-encode-lessons-in-struction)。
- `overview.md` は永続的な PR および問題 DB です。追加します。イベントごとに大規模に書き換えないでください。
- `units.tsv` には、ユニットごとに 1 行があります: ID、トラック、状態、ブランチ、PR、ヘッド SHA、簡単なパス。行をその場で更新します。
- `frontier.json` は、スタックの安全性に従って計算されたマージ フロンティアです。
- `ledger.tsv` は、検証ごとの検証元帳です。
- `inbox/` は完了ポインターを保持します。 `gates.md` は人間のゲートをパークします (質問、オプション、デフォルトは無回答)。
- `decisions.tsv` は、show-me-your-work スキルによるトレイルです。
- `status.md` は、各ドレインの `units.tsv` および `ledger.tsv` から導出され、手作業で維持されることはありません。イベントを説明するのではなく、テーブルからテーブルを再生成します。

<a id="the-brief"></a>

#### 概要

エージェントへのプロンプトが唯一の製品であり、ずさんな概要がツリー全体に悪影響を及ぼします。すべてのスポーンにはそれがすべて含まれています。入力できないフィールドは、まだスコープを設定していないユニットです。

```
GOAL         one sentence, the outcome, executable by a stranger with no chat access
SCOPE        paths this unit may write; paths it may not; its exclusive worktree or branch
CONTEXT      pointers to files and PRs; upstream reports pasted in full when this unit
             depends on them, because workers cannot see siblings
ACCEPTANCE   checkable criteria, one per line
VERIFY       exact commands or the control-skill path, plus known gotchas
TIMEBOX      rough cap on runtime; on expiry, return partial findings and stop rather than run on
FORBIDDEN    no gt, no rebase, no force-push, no fixes outside scope, plus unit-specific bans
REPORT       status, branch, head SHA, PRs, verdict, what you actually ran, deviations,
             suggested follow-ups
STANDING     <preferences.md pasted verbatim>
```

ブリーフをユニットに合わせてサイズ設定します。 1 つのコマンド単位では、目標、範囲、検証コマンド、およびレポートの形状を指定した段落に折りたたまれたテンプレートが取得されます。 2 行の編集を囲む 4KB のスキャフォールドは、編集よりも書き込みと従うのにコストがかかります。ローカルスポーンは、ストアパスによってスタンディングオーダーファイルを参照できます。逐語的なペーストは、クラウドのスポーンとすべての履歴書に使用されます。

サブコーディネーター ブリーフには、トラック境界とユニット リスト、クラウド デフォルトとローカル例外リストを含むスポーン バジェット、ドレイン プロトコル、ロールアップ形式 (子ごとに: 名前、ステータス、PR、ヘッド SHA、判定、1 行、トラック ステータスとフロンティア デルタ) が追加されます。

依存関係は、単なる順序付けではなく、コンテキストのリレーです。宣言されていないアップストリーム コンテキストにより、ワーカーは推測します。フィールドが欠落していると、スポーンが拒否される状態になります。ウェーブごとにサブコーディネーターごとに 1 つのサンプリングされたワーカー ブリーフィングを、サンプリングしたウェーブと同時に監査します。ウェーブの前のゲートとしては決して行いません。ブリーフに失敗すると、その追跡が停止され、作業者だけでなくサブコーディネーターの指示が修正されます。これは、ブリーフの品質が実行の後半で低下するためです。決してブリーフをレジュームチェーンしないでください。統合されたスコープで新鮮にリスポーンします。

<a id="steps"></a>

#### の手順

1. **Frame.** 完了述語を可算なものとして記述します (「126 個のユニットすべてがマージされ、各台帳で検証された `unit-test-verified` 以上」)。範囲を定量化します: ユニット、大まかな労力、予想されるスタック、および実際の予算。 1 人のエージェントがその予算内で終了できる場合は、ここで停止し、代わりに自律実行を実行します。折りたたみは、存在する別のドキュメントに依存してはなりません。これは、このセッションで作業を直接実行し、単純な作業者が手助けをし、インラインで検証し、移動中に着陸し、以下の店舗、レジスター、またはパイロット機械を使用しないことを意味します。予算に合わせて着陸のスケジュールを立てます。およそ 70% までにスポーンを停止し、確認されたものを着地させます。プロジェクトごとにトラックに名前を付けます。競合する分解または一方通行のドアは、パイロットよりも先にアリーナ スキルを通過します。一度フレームを提示してください。待ち時間なしで可逆的な準備が進みます。
2. **ランタイムをインストールします。** `orch init` を実行します。 show-me-your-work スキルを使用してトレイルを開き、スポーン前にスタンディング オーダーを書き込み、`orch frontier set --repo <repo-dir>` を使用して既存の PR から `frontier.json` をシードします。
3. **パイロット。** パス全体を通じて 1 つのユニットをプッシュします: ブリーフ、ワーカー、検証、スタック エントリ、レジャー行、マージ。パイロットは、簡単なテンプレート、検証レシピ、ユニット サイズを改ざんするために存在しますが、それには 50 人ではなく 1 人のエージェントが必要になります。ファンアウトの前に、パイロットの証拠からコントラクトを修正します。パイロットをユニットに合わせてスケールします。ほぼ同一の安価なユニットのプログラムでは、最初のユニットがパイロットで、検証コマンドがインラインで通常のユニットとして実行され、着地した瞬間にファンアウトが始まります。専用のパイロット パイプライン (個別の検証エージェント、監査ゲート) は、高価なユニットまたは新しいユニット形状用であり、シリアル化されたパイロットに改ざんするものが何もないクローン ユニット用ではありません。
4. **スケール。** ワーカーのローリング ウィンドウを飛行中のキャップまで生成し、子が完了するにつれて補充します。バッチをブロックすると、各バッチの中で最も遅い子に支払いが行われます。ロールの 1 ドレインしきい値を超えた場合にのみ、トラック サブコーディネーターをスポーンします。各ドレイン後に準備完了作業を再計算します。上流のレポートを下流のブリーフに中継します。兄弟間のコミュニケーションは上向きのみに留めてください。サンプリングされた簡単な監査は、サンプリングした波形と並行して実行され、失敗すると現在のリフィルではなく次のリフィルを停止します。
5. **ドレイン。** すべてのドレイン ポイントで以下のキュー規律を実行します。
6. **着陸。** 着陸は継続的に行われ、終末段階ではありません。統合は最初に検証されたユニットから開始され、残りのウェーブと並行して実行されます。重いリポジトリでは、スタッカーはウェーブ 1 から常設の役割を果たし、ユニットが検証するにつれて統合されます。ローカル git が安価なリポジトリでは、コーディネーターがロールごとに検証済みユニット自体を配置します。上部スタックの作業の前に、フロンティアを緑の状態に保ってください。スタックの安全性が管理します。マージまたは報告された新しいヘッド SHA でのみ `frontier.json` を進めます。
7. **閉じる。** 最後の受信箱を空にし、生成されたすべてのエージェントをターミナル行に調整し (完了、放棄、ゾンビ調整済み)、実際のアーティファクトの述語を確認し、着陸したすべての PR に現在のヘッド SHA に対する判定があることを確認し、クロスモデル レビューを含むショーミーユアワークごとの証跡を監査し、繰り返し発生する修正を `preferences.md` または概要にエンコードします。テンプレート。店をそのままにしておきます。それは死後です。

<a id="queue-and-drain"></a>

#### キューとドレイン

- 完了通知が表示されたら、`orch inbox push <agent> <unit> <status> [--report PATH]` を実行して、実行していた作業に戻ります。インラインでの詳細なレビューは決して行わないでください。レビューが必要な完了は検証ユニットになります。排水管内の差分を決してレビューしないでください。
- クリティカル セクションの終了、トラック ロールアップ、フロンティア ウォッチャー ウェイク (ループ スキルを介して、長いハートビート フォールバックで準備)、および人間によるレポートの前の 4 つの時点でバッチでドレインします。各バッチは `orch inbox drain` で始まります。排水中の到着は次の到着を待ちます。
- 最初に完了する重要なセクション: ブリーフの作成、スタック操作、競合決定、ゲートの作成、台帳またはフロンティアの更新。
- 各ドレインは、すべてのポインター (着陸、ニーズ検証、失敗、ゾンビ、ノイズ) を分類し、結果の行を `orch unit add`、`orch unit set`、および `orch ledger record` に書き込み、`orch status` を実行して、1 つのメッセージで次のウェーブを生成します。
- トラックのロールアップでスポーンされたすべての子のアカウント: 到着、再スポーン、またはスコープが明示的に吸収されました。行方不明の子供の仕事を黙ってやり直すことで、無駄な支出と、その結果として存在していたカバー範囲のギャップを埋めることができなくなります。
- ドレイン ターンは `orch status` からの 3 行で終了します。状態、変更内容、ゲートが開いていることをカウントします。詳細は `status.md` にあります。完全な返信コントラクトはチェックポイントとクローズ時に適用されます。

<a id="stack-safety"></a>

#### スタックの安全性

- フロンティアは計算されたオブジェクトであり、決して物語ではありません。マージとスタックの変更のたびに、`gt` から `frontier.json` を再計算します。これは、GitHub のベース参照が再スタックの途中でドリフトするためです。GitHub のベース参照は、GT トラッキングが権威である一方で、順序付けされた PR リスト、ブランチ名、ヘッド SHA、世代番号、マージされていない最低の PR です。 gt がスタック (通常はスタッカーのクローン) を認識している場所で解決します。 gt メタデータが送信を一度も見たことがないチェックアウトは、推測ではなく PR とコマンド エラーを報告しません。
- スタックごとに 1 つのスタッカーが、スタック内でシリアル化された `gt` を実行できます。保持者をスタンディングオーダーに記録します。再スタックはクラウドで実行されます。この規模でローカルに再スタックを行うとラップトップがダウンします。
- ワーカーは決してリベースせず、`gt` を実行しません。ベビーシッターは `playbooks/babysit.md` に従い、スタックごとに 1 つ、範囲は 1 つの不変フロンティア世代に限定されます。再スタッキングではなく、競合をスタッカーに報告します。
- PR が閉じられ、再ターゲットはスタッカーのみを通過します。ベース PR を閉じると、その上のすべてのチェーンが孤立します。マージとスタック手術は、他のユニットと同様にブリーフを備えたユニットです。
- あるレトロ ウォッチャーは、マージされた PR をフォローして、元に戻す、マージ後の CI ブレーク、孤立したフォローアップを行っています。

<a id="verification"></a>

#### 検証

ユニットに対するスケール検証。 VERIFY が単一の安価なコマンドである場合、ワーカーはそれを実行して出力を報告し、コーディネーターは受信内容をスポットチェックします。専用の検証エージェント (ワーカーとは異なるモデル ファミリ上) は、検証にコストがかかる、判断が必要な、または爆発範囲が広いユニット用です。製品全体が 1 つのコマンドを再実行する検証エージェントは、検証ではなく儀式です。

`orch ledger record` を使用して台帳行を書き込みます。現在の PR とヘッド SHA を `orch ledger check` で確認します。 `ledger.tsv`、判定ごとに 1 行、PR 番号とヘッド SHA をキーにします: `live-ui-verified | unit-test-verified | type-check-only | verifier-blocked | verifier-failed`。 CI グリーンは評決への入力であり、評決ではありません。行動に関する作業には `type-check-only` よりも優れたものが必要です。 `verifier-blocked` はパスではありません。環境が回復すると復活します。 `verifier-failed` は再検証ではなく修正ユニットを取得します。労働者は自己申告することができます。ベリファイアは同じキーでそれをオーバーライドします。新しいヘッド SHA は行を無効にするため、再スタック後に再検証してください。台帳は、記憶や記録ではなく、「これが検証されたかどうか」に答えます。

ユニットは、着地した瞬間に出力が外部化されるまで完了せず、実行の最後までバッチ処理されることはありません。従業員が支店をプッシュし、検証者が台帳の行を書き込み、レシートが店舗に到着します。 1 つの VM にのみ存在する作業は、その VM が停止したときに実行されることはありません。

<a id="liveness-and-failure"></a>

#### 活性と失敗

- エージェントを再開して確認しないでください。再開すると、アイドル状態のエージェントが再起動されます。読み取り専用のプローブ: 台帳、`units.tsv`、`gh`、プッシュされたブランチ、Cursor ダッシュボードのクラウド エージェントのステータス。トランスクリプトの mtime は liveness ではありません。
- 静かな死は、受信トレイに合成事後分析行 (ユニット、障害モード、最後の証拠、オプション) を取得します。証拠が到着次第、計画を立て直します。完全に静止するまで決して待たないでください。
- モードで再試行します: キャップヒットまたはウーム、より小さいスコープでリスポーンします。ネットワークをドロップし、そのまま再試行します。ツールエラー。別のモデルで再試行してください。不明です。一度再試行してください。 2 回再試行し、その後ユニットを放棄し、それを中心に計画を立て直します。
- 数時間遅れて戻ってきたゾンビは、何も受け入れられる前に現在のフロンティアと台帳と照合します。ブラインドマージではなく、新しいユニットを通じてユニークな発見を回収します。
- スポーンを続けるとツリー全体にガベージ (上流出力の不良、受け入れの中断、インフラの停止) が発生する場合は、スタンディング オーダーの先頭に停止ラインを書き込み、実行中の作業を終了させ、原因を修正してクリアします。
- 子のインフラストラクチャをバインドするのと同じ方法で、自分自身のインフラストラクチャの再試行をバインドします。数回連続してツールが異常終了した後、再試行を停止します。永続状態へのターミナルのハンドオフ (何が行われるか、どこに存在するか、再開する正確なコマンド) を記述し、実行を終了します。
- Cursorの再起動後: ローカル エージェントは停止していますが、クラウドの作業は停止していません。スタンディングオーダーと `units.tsv` を再読み取り、フロンティアを再計算し、エージェント ID ではなく PR とブランチによってクラウド作業を再アタッチし、保存されたブリーフと現在の状態からトラックごとに 1 つのサブコーディネーターを再生成し、ドレイン、再開します。デッドセッションのストアロックは、次回の書き込み時に自動的にクリアされます。 `orch` は、ホルダー PID が失われているロックを置き換えます。

<a id="escalation"></a>

#### エスカレーション

人間に到達し、アイテムごとではなくステータス ページにバッチ化されます: 不可逆的なアクション (共有ブランチへの強制プッシュ、デプロイ、削除、他人の PR のクローズ)、正規の製品または優先コールによる実験の解決なし、観察された現実と矛盾する常駐の命令、再計画を生き残ったプログラム レベルの行き詰まり。質問する前にそれぞれを `gates.md` エントリとして保存し、それを回避して作業をルーティングします。

人間には決して届きません: フロンティアナッジ、再スタックメカニズム、再試行、CI フレークトリアージ、レビュースレッドトリアージ、フォーマット修正、ブリーフですでに禁止されている範囲 (拒否して続行)、そして「続けるべきか」。疑問がある場合は、行動して記録してください。

途中の発見では、フロンティアをブロックしているもののみを修正します。他のすべてはフォローアップに保留されます。このファンアウトでは、小規模なスコープのリークが増殖して、誰も求めなかった PR になります。

**返信:** チェックポイントとクローズ: `units.tsv` および `ledger.tsv` からの述語とそれに対するカウント、トラックとそれぞれが着陸したもの、フロンティア (PR リストと SHA)、評決の概要、放棄されたものとその理由、人間を待つゲート (唯一の質問)、店舗のパス、トレイルのパス。物語ではなく、表からの数字。 PR リンクを含めます。
