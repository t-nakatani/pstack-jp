### バグ修正

**あなたはこのタスクの所有者です。計画、レビュー、検証。** 調査と修正をサブエージェントに委任し、常に主導権を握ります。

科学的になりましょう。すべてのリリースラインは実行時の証拠を追跡します。 「役立つかもしれない」ベルトとサスペンダーは仮説であり、解決策ではありません。リリースはしておりません。証拠が仮説を否定する場合は、その仮説を元に戻します。ほんのわずかな変化でも船が正当化される証拠はありますが、それ以上のものではありません。

1. デバッグまたは計測プロトコルがユーザーに再現を要求する場合でも、コントロール スキル (交渉不可) を介してマッチング サーフェス上で自分で再現します。操舵面が目標に到達できない具体的な理由をユーザーに尋ねるのは、操縦翼面を限界まで運転した後でのみにしてください。直接再現しない場合は、トリガーを合成し、条件を厳しくするか、起動するまで機器を調整します。
2. 原因を二分探索します。候補となる仮説を立て、仮説が残るまで除外します。影響を受けるサブシステム上で `how` をシードし、回帰履歴の **why** スキルをシードします。各パスでは、最も残っている問題スペースをカットする分割を取得し、実行時の証拠を取得して除去します。プログラムの状態が不明瞭な場合は、インストルメンテーションまたはログを追加し、コードの実行時に読み取ります。推測しないでください。 Cursor の `/loop` コマンドを使用して、長時間または頑固な狩りを実行します。ステップ 3 のアーキテクト/質問ファンアウトの前に、実行時の証拠で生き残っている *メカニズム* を確認します。
3. 修正を計画します。関数境界を越える場合は、`architect` が最初です。特定のスコープで構成されたバグ修正モデル (デフォルト `grok-4.7-xhigh-fast`) を使用して、実装をサブエージェントに委任します。
4. 同一面上で検証します。オリジナルのリプロは現在では合格です。 「決定的でない」または間違った表面はパスではありません。フラグを立ててください。単体テストでは、バグの有無ではなく、分岐の動作が示されます。
5. コミットをステージングして、失敗した再現が git 履歴の修正の前に表示されるようにします。バグに安価なローカル テスト パスがある場合の、failed-test-first のケイデンスについては、**tdd** スキルを参照してください。テストに費用がかかる、統合が多い、または不明確な場合はスキップしてください。
   これは標準的な **sequence-verifiable-units** の原則スキルであり、失敗したテストが最初に行われ、その上に修正が加えられます。
6. **PR を開く** を実行します。

**返信:** 何が壊れたのか、根本原因、修正、どのように検証したか。失敗してから合格した再現出力をそのまま貼り付けます。
