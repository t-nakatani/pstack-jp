### 

**土地の所有者はあなたです。各 PR を個別に検証し、検証された実行のみをルートから実行して、キューから手を離します。**

これは `playbooks/babysit.md` の後の半分です。

1. **フォージを解決し、すべての PR を個別に検証します。** GitHub CLI (`gh`) がデフォルトです。 `command -v origin` が成功し、Origin がリポジトリを解決できる場合は、PR 表示、監視、編集、マージ操作に `origin pr ...` を使用します。それ以外の場合は、`gh` に留まり、フォールバックを記録します。決してグラファイトを必要としないでください (`gt`)。 PR ごとに 1 つのサブエージェント (バッチ化されていない)、それぞれが Cursor クラウド エージェントであり、親とヘッドに対して一致する制御スキル (`control-ui` または `cursor-team-kit` からの `control-cli` など) を使用して実際のサーフェスを実行します。それぞれが `PASS`、`PASS+NOTES`、または `FAIL` を返し、その判定を独自の PR に投稿します。安全とは、コードを作成していないエージェントによる判定を意味します。 CI グリーンは評決ではなく、ボットのレビューの承認も評決ではありません。
2. **最下位をルートとする連続した検証済み実行のみをランディングします。** マージされていない最下位の PR から上に進み、合格判定なしで最初の PR で停止します (`PASS` と `PASS+NOTES` の両方が合格)。未検証の PR の上にある検証済みの PR は、着陸できません。上限を PR 番号として報告し、何が連鎖を断ち切るのかを述べます。
3. **各判定がまだパッチを記述していることを再確認します。** 判定のヘッド SHA、ベース SHA、および PR のベースツーヘッドの差分の安定した `git patch-id` を記録します。リベースまたはベース リターゲットは SHA を書き換え、チェックを行わずにサイレントに判定を無効にすることができます。 PR をランディングする前に、記録されたパッチ ID と現在のベースツーヘッドのパッチ ID を比較します。 2 つのパッチがテスト、ドキュメント、または lint 構成のみで異なる場合は、各レーンで実行されたものをビルドします。評決 SHA で 2 回、現在のヘッドで 1 回ビルドします。判定 SHA での 2 つのビルドでもそれが示される場合、またはそれが埋め込みコミット SHA である場合、違いはノイズになります。ファイルごとではなく、差異ごとに判断し、さまざまな種類のノイズをそのファイルとともに報告します。ノイズのみが異なる場合、そのレーンの結果は有効のままであり、変更のチェックとレビューが新たに実行されます。開発サーバーからのレーン結果や、ビルド出力のない他のものからのレーン結果を再利用しないでください。そのレーンを再実行します。パッチが変更されたときに、その他のことを再確認します。そうでなかった場合は、コードの判定を保持しますが、現在の先頭でマージ可能性と CI を再実行します。一致するコミット メッセージや古い SHA のグリーン チェックを代替として使用しないでください。
4. **最下部の PR のみを準備します。** 現在のトランクを取得します。必要に応じて、検証された最下位のブランチを正確なトランク チップにリベースし、プッシュし、`origin pr edit <pr> --base <trunk>` または `gh pr edit <pr> --base <trunk>` を使用してその PR のみをトランクに再ターゲットします。プッシュ後にステップ 3 を再実行します。まだ子孫の再ターゲット、装備、またはマージを行わないでください。
5. **一度に 1 つの PR を配置します。** 一番下の PR がマージ可能になった場合は、`origin pr merge <pr> --squash` または `gh pr merge <pr> --squash` で潰します。要件がまだ実行中で、ユーザーが準備完了時のマージを要求した場合は、その PR のみを `origin pr merge <pr> --squash --auto` または `gh pr merge <pr> --squash --auto` で準備します。 Origin の `--auto` は、Origin merge-when-ready です。 GitHub の `--auto` は GitHub 自動マージです。次の PR を準備する前に、その PR がマージされるまで待ちます。
6. **GitHub `autoMergeRequest` をスタックの準備として読み取らないでください。** 最大でも 1 つの GitHub PR に対して GitHub 自動マージが要求されたと表示されます。これは、Origin merge-when-ready が準備されていること、子孫がキューに登録されていること、パッチの判定が最新であること、または連続したスタックが安全であることを証明するものではありません。現在のボトム PR のアクティブ フォージの状態を確認し、アクティブ フォージがそれを報告できない場合は状態が不明であることを示します。
7. **マージごとに再計算します。** トランクを取得し、マージされた SHA が存在することを確認し、マージされた PR を凍結された下から上のリストから削除し、新しい下位 PR のベース、ヘッド、チェック、およびパッチ ID を検査します。ホストは子を自動的に再ターゲットする可能性がありますが、実際に再ターゲットしたと想定しないでください。その 1 つの PR に対してステップ 3 ～ 6 を繰り返します。独立した作品はこのチェーンの外側に留まり、単独でリリースされます。
8. **現在のフロンティアがマージまたは失敗するまで監視してください。その周囲のキューを変更しないでください。** Origin では、`origin pr view <pr> --checks --comments` と `origin pr checks <pr> --watch` を使用し、マージまたはブロックされたことが報告されるまで PR を再読み込みします。 GitHub では、`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom>` をイベント ウェイクとしてのみ使用し、各ウェイク後に `gh pr view <pr> --json state,mergedAt,mergeStateStatus,statusCheckRollup,autoMergeRequest` をポーリングし、`mergedAt` が null 以外になるか、`state` が `MERGED` になるまで、`READY` を無視します。その後、ステップ 7 を実行します。 `state` が `CLOSED` で `mergedAt` がない場合、必要なチェックで `FAILURE` または `CANCELLED` と結論づけられ、自動マージが保留されなくなった後にブロックがマージされる場合、または `mergeStateStatus` が `UNSTABLE` である場合にのみハード失敗します。 `DIRTY` 保留中の自動マージはありません。チェックが保留中または自動マージが有効になっている間の `BLOCKED` は失敗ではありません。ここでは、Babysit のキューに登録された `WAITING`/`merge-queue` 停止条件を使用しないでください。動的モードで時計を `/loop` の下に置きます。各マージと新しい上限をレポートします。キューが停止した場合は、変更する前に診断してください。
9. **天井で停止します。** 検証済みの実行がマージされたら、何が着陸したか、次の未検証の PR が何であるか、およびその検証に何が必要かを報告します。ランの延長は、ステップ 1 を介した新たなパスです。

**返信:** 検証されたランとその天井、各 PR の評決と誰がそれを作成したか、何を武装しどのように確認したか、何が着地したか、次のギャップに何が必要か。
