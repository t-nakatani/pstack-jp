### オートパイロットフル

**評決を所有するのはあなたであり、PR を所有することはありません。 1 人の所有者がビルドからマージまで各 PR を実行し、クリーン swarm の判定がなければ何もマージされません。** 「このキューを自動操縦」、「完全自動操縦」、および PR ごとに 1 人の所有者プログラムの場合。 Orchestrate は、コーディネーターが検証済みの作業自体を実行し、ワーカーがマージすることのない常駐プログラムを実行します。ここでは、各 PR の所有者がマージを通じてライフサイクル全体を実行し、ルートは検証、副署名、監査のみを保持します。

1. **オペレーターのアイテムにマークを付け、state-then-wait を尊重します。** オペレーターの名前が付けられたアイテムはオペレーターに残ります。オペレーターがレビューしてクリックし、所有者がそれをマージすることはありません。オペレーターがプロトコルや計画の説明を求めたら、それを伝えて終了します。実行は、オペレーターが明示的に実行した場合にのみ開始されます。
2. **完全なライフサイクルと初期の証跡を備えた PR ごとに 1 人の所有者を生成します。** プログラムのフォージを 1 回解決します。 GitHub CLI (`gh`) がデフォルトです。 `command -v origin` が成功し、Origin がリポジトリを解決できる場合は、PR の作成、編集、表示、監視、マージ操作に `origin pr ...` を使用します。それ以外の場合は、`gh` に留まり、フォールバックを記録します。決してグラファイトを必要としないでください (`gt`)。 PR ごとに 1 つの Cursor クラウド エージェントがビルド、最初のプッシュ、準備ができた PR、実際のアーティファクトの自己証明 (**prove-it-works** 原則スキル)、`../references/bugbot-triage.md` による懐疑的なバグボットの選別、スロップストリップ (`cursor-team-kit` プラグイン (`/deslop`) の `deslop` スキル)、 `/no-comments` (**no-comments** スキル)、現在のトランクへのリベース、緑色へのベビーシット ループ (`playbooks/babysit.md`)、およびマージ自体。約 15 分以内に、すべての所有者が **show-me-your-work** スキルに従って `decisions.tsv` トレイルを開始し、最初のブランチ スナップショットをプッシュし、準備完了の PR を開きます (ドラフトは行われません)。その後、所有者は検証可能なユニットごとにブランチを再度プッシュします (フックオン、WIP コミットは問題ありません)。自己証明する前に PR を開いて、URL、決定、チェックが永続的な証跡を形成するようにします。 `decisions.tsv` をコミットしないままにし、レポートとともに返します。サブエージェントが開始するとすぐに、所有者はその ID、予想される実行時間 (少なくともその種類の過去の最長の実行時間)、および状態を同じ方法で `children.tsv` に追加します。所有者は、トランクがドリフトしたかどうかに関係なく、コード準備完了レポートとベビーシッターの前に最初のリベースを実行します。修正ラウンドでは、所有者はそのマージベースを保持します。所有者は、マージ準備 (ステップ 5)、トランクとの `git merge-tree` 競合、またはトランクの変更による CI 障害の場合にのみ、再度リベースを実行します。リリースされたコードが最終的な場合、スロップ ストリップと `/no-comments` の後、コードレディ ヘッド SHA が報告されます。また、パッチを変更するその後の各プッシュの SHA も報告します。その後、Self-proof、CI、および babysit が swarm と並行して実行されます。所有者は、自己証明、CI、およびベビーシットが終了すると、ヘッド SHA にマージ準備ができたことを報告します。ラウンドを開始するプッシュの前に、リポジトリの AGENTS.md ファイルとタッチされたパスのルール名を確認する事前レビュー チェックを実行します。コミットされたヘッド上でそれらを実行します。フックパスは証拠ではありません。各リベースを公開するには、`ls-remote` チェックの後に、所有者自身のブランチを `git push --force-with-lease` でプッシュします。共有ブランチを強制的にプッシュしないでください。合併は、所有者が単独で実行できない一歩です。ステップ 4 でゲートします。
3. **オーナーを真の並列で実行し、スタックすることはありません。** PR が自己完結型である場合、一度に多数のオーナーが実行されます。ブランチごとに 1 つのライター、結合されていないファイル、リベースによって吸収される PR 間のドリフト。本当に重複した作品のみ連載します。自己完結型 PR はメインから直接分岐し、順序付けられた作業はマージしてから分岐します。 1 つの例外: 純粋に依存する変更を分割する必要がある所有者は、短いプライベートのベース ブランチ スタックを保持する場合があります。
4. **マージ前にすべてのラウンドをスウォーム検証します。** ラウンドは、所有者のコード準備完了ヘッド SHA から始まり、PR のパッチを変更するその後の各プッシュから始まります。その SHA では、**swarm** スキルごとに並列の独立した検証者をファンアウトし、1 つの判定に集約します。マージには、パッチがマージ準備完了のヘッドと一致するラウンドからのクリーンな判定が必要です。判定の前に、マージ準備完了レポート内のレシートを監査します。レーン: その SHA でゲートを再実行します。 (`cursor-team-kit` からの `control-cli` や `control-ui` などの一致する制御スキル、または存在しない名前付きドライバーを使用して) 変更が触れる実際の表面上で耐荷重動作が生きていることを証明します。 PR 団体を信頼せずに diff を監査します。完全な概要を使用して、2 つ以上のレビュー レーンとして監査を実行します。トランクとの消費者同等性、ライフタイムとレース、データと構成の安全性など、各レーンに 1 つの主な焦点を与えます。 **トランクに対する回帰レーン。** 現在のトランクで同じ耐荷重シナリオを実行します。トランクにその機能がない場合は、トランクがそれを生成できるかのように振る舞うのではなく、その事実を記録し、diff が追加する動作とユーザーが待機する終了状態をゲートします。ライブレーンはフロアであり、それのない評決はクリーンとは言えません。ルートのクリーンな判定がなければマージはできません。レーンが戻ったら、PR に対して証明されたすべての結果を 1 回の修正で所有者に送信します。レーンがメモとして提出した欠陥は所見です。動作の発見ごとに、同じ欠陥のあるすべてのサイトを対象とするレッド テストを依頼します。テストで欠陥が示されない場合は、代わりに再現レシートを要求してください。その欠陥を次のラウンドのレビュー概要に追加します。新しいヘッドは、`playbooks/shipping.md` のパッチ ID ルールに基づいて有効なレーン結果を除き、新しいスウォームと新しい判定を取得します。
5. **クリーンな判定に基づいて、所有者がマージされ、新しい所有者が次のアイテムを取得します。** 所有者は、トランクに新しくリベースされたヘッドからのみマージされます。マージの準備はラウンドのレーンの開始前に行われることはなく、マージの直前に現在のトランクへのリベースで終了します。マージ準備リベースの後、所有者は新しいヘッド SHA を報告します。 CI はマージ前にそのヘッドを渡す必要があり、パッチ ID ルールによってラウンドの判定がまだ有効であるかどうかが決定されます。ヘッドが緑色になり、そのパッチ ID が `playbooks/shipping.md` のパッチ ID ルールに基づく判定と一致すると、その後のトランクの移動によって別のリベースが強制されることはありません。マージの直前に、トランクを取得し、現在のトランクに対するヘッドの `git merge-tree` がクリーンであることを確認します。また、`git diff --name-only $(git merge-base HEAD origin/main) origin/main` 内のパスが、PR が変更するパス、またはリポジトリの CI 構成パスなど、PR に対して実行される CI を決定するパスではないことも確認してください。いずれかのチェックが失敗した場合は、再度リベースし、新しいヘッド SHA を報告し、CI がそれを渡すのを待ち、これらのチェックを繰り返します。新しいヘッドは、パッチ ID が変更されない限り、判定を無効にします。所有者は、解決されたフォージを通じて自身の PR をスカッシュマージし、戻ります。新しい所有者は、poteto-mode のサブエージェント セクションに従って、キューから次の自己完結型アイテムを取得します。オペレーターの完全な自律性の許可とルートのクリーンな判定は、ベビーシッターだけでは決して得られないマージ許可です。オペレータ名付きアイテムはマージ準備完了で停止し、オペレータのクリックを待ちます。
6. **ルート層を実行します。** ピン留めされたゲートまたはバジェット値 (制限 CI のみが厳しくする) を真に新しく引き上げるには、検証者の証明後にのみ付与される、新しい副署名が必要です。オペレーターの許可または継続命令が承認をカバーする場合、その副署名が承認となります。所有者は、ルートの副署名へのポインタを使用して、ツールの承認契約で許可されている形式でそれを記録します。レーンはその副署と照合して記録をチェックします。ルートは、フォージが強制する承認を与えたり回避したりすることはありません。すでにメインに到達した値を吸収することはドリフトであり、レイズではありません。すべての所有者に対して監査ティックを 1 時間ごとに実行します。オペレーターが外出中に、このティックを実行するプロンプトを `/loop 1h` に設定します。 `/loop` はローカル ルートとクラウド ルートで動作します。リズムを記憶や損失のある完了通知に任せないでください。各ティックで、`git show origin/main:pstack/skills/poteto-mode/playbooks/autopilot-full.md` を使用してこのプレイブックをトランクから再読み込みし、それに対する操作を監査します。そのティック中のドリフトを修正します。一般的な生存確認またはステータス チェックで各所有者を調査し、決定証跡を収集します。副作用のみを進行状況としてカウントします: コミット、プッシュ、PR またはチェック デルタ、および保存レポート。エラーが発生したレーン、または副作用なしに予想される実行時間を経過したレーンをスタックとして扱います。そのままにして、すぐに交換品を送ります。丁寧な返答を待たないでください。ティックは、プッシュされたブランチとステップ 2 で必要な決定軌跡に基づいて所有者を判断し、エージェントがターンを開始できない所有者を置き換えます。各ティックは、プログラムのエージェント リスト (プラットフォームに 1 つある場合) およびすべての所有者の `children.tsv` に対してレーン スタック テストも実行します。停止が機能するかどうかに関係なく、ルートは所有者に、スタックした各サブエージェントをスタックとして記録させ、その作業がまだ必要な場合は置き換えます。停止した各置換には同じ手順が適用されます。所有者が両方のステップを実行できない場合、ルートは両方のステップを実行します。失速しても作業が証明されたり、作業が中断されたりすることはありません。バッチをマージするときは、レトロ パスとマージ後のボット コメント スイープを実行します。最後のマージの後であっても、委任された作業が残っていない場合にのみティックを終了します。
7. **オペレーターの停止で即座にスタンドダウンします。** オペレーターの保留またはスタンドダウンは、ゼロ書き込み命令としてすべての所有者に即座に届きます。所有者はオペレーターがブリーフを解放するまでブリーフを保持します。

**返信:** 各 PR の所有者、状態、およびヘッド SHA を含むキュー。それぞれの判決とそれを生み出した群れ。何が合併したのか、そして新しいオーナーが次に何をとったのか。認められた副署とその理由。オペレーターゲートを開けてください。収集された意思決定の証跡が存在する場所。
