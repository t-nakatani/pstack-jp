### リファクタリング

**契約の所有者はあなたです。構造が変わります。 ** 動作を追加する機能と、動作を修正するバグ修正とは異なります。

クリーンアップによって欠落している機能や実際のバグが明らかになった場合は、それを分割し、固定されたコントラクトに対して最初に構造変更をリリースします。再設計は許可されていますが、名前を付けて機能にルーティングします。大規模または横断的な構造作業は、**figure-it-out** スキルに属します。このプレイブックは、焦点を絞ったものから中程度のものへの変更です。

1. 最初に動作コントラクトを固定します。影響を受けるサブシステム上で **how** スキルを実行してコントラクトを学習し、構造が移動する前に現在の動作をキャプチャする特性評価テスト、スナップショット、または等価ハーネスを作成します。エリアにカバレッジがない場合は、構造に触れる前にピンを書き込みます。型チェックと lint はピンと来ません。
2. **principle-model-the-domain** ごとに、コードが欠落している構造に名前を付けます。形がすでに明確で局所的である場合、退屈なコードは残ります。再形成では、間接性を追加するのではなく、分岐または無効な状態を削除する必要があります。
3. ターゲット シェイプに名前を付けます。今日構築する場合のモジュールのレイアウト、型、およびコール グラフがどうあるべきかを述べます (**principle-foundational-thinking**、**principle-redesign-from-first-principles**)。ターゲットが関数の境界を越える場合は、**architect** スキルを実行して、移動前に形状の並行設計調査を行います。
4. 加算する前に減算してください。新しい形状 (**principle-subtract-before-you-add**) を導入する前に、無効なコードを削除し、単一呼び出しラッパーを折りたたんで、冗長なバリデーターを削除し、孤立した参照を削除します。目標の形状に達する最小の変更がリリースされます (**principle-laziness-protocol**)。 「役立つかもしれない」という投機的なクリーンアップが元に戻される。
5. 動作を維持する小さなステップで移動し、各ステップでピンを緑色に保ちます。 API を再構成する場合は、すべての呼び出し元を移行し、同じウェーブで古い API を削除します (**principle-migrate-callers-then-delete-legacy-apis**)。互換性シムや、新旧の並列パスはありません。実際のファイルに対してすべての名前変更をスポットチェックします。文字列、文章、後方参照での使用を無視して名前を変更します。特定のスコープ (ファイル パス、移動される名前、保持する動作) を持つ構成済みのリファクタリング モデル (デフォルト `grok-4.7-xhigh-fast`) を使用して、機械的な編集をサブエージェントに委任します。
6. 証明の動作は実際のアーティファクトでは変更されませんが、「コンパイルされる」(**principle-prove-it-works**) わけではありません。より大きな再形成の場合は、等価性チェックを実行します。つまり、古い出力と新しい出力を比較するスクリプト、新しいコードに対して再生される記録されたベースライン、または関連するコントロール スキルを介して一致するサーフェス上でスモークを実行します。
7. 変更を保持する価値があることを確認します。成功の基準は、リーダーの負荷を軽減することです (**principle-minimize-reader-load**)。 diff によってリーダーの負荷が低下しない場合は、差分を元に戻してください。
8. 小さな順序付けされたコミットにリベースします。減算コミット、次に再形成、そして後続のクリーンアップ。 **sequence-verifiable-units** 原則スキルを使用してそれらを整形し、動作を保持する各スライスが次のスライスの前に緑色のままになるようにします。 **PR を開く** を実行します。

**返信:** 変更された構造、それを押し当てたピン、等価性証明、リーダー負荷デルタ、リリースされたものと戻されたもの。新しい動作はありません。
