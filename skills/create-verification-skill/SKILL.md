<a id="create-a-verification-skill"></a>

# 検証スキルの作成

すべての本格的なプロジェクトには、実際のアプリを実行して動作を証明するためのスクリプト化された方法が必要です。アプリを起動し、ユーザーが行うように機能を実行し、証拠をキャプチャします。このスキルは、リポジトリに合わせたプロジェクト ローカル スキル (`.cursor/skills/verify-<app>/`) としてそれを生成します。ジェネレーターの出力は、人間ではなく、次のエージェントのために書きます。その出力は、アプリを一度も見たことのないエージェントによって、タスク中にコールドで読み取られます。

<a id="1-interview-the-repo-not-the-user"></a>

## 1. ユーザーではなくリポジトリにインタビューします

コードベースからこれらに答えて、観察できないことのみをユーザーに尋ねます。

- **Surface:** ユーザーが実際に触れるものは何ですか? Web UI、CLI/TUI、デスクトップ アプリ、API、モバイル アプリ、ライブラリ?リポジトリには複数のリポジトリを含めることができます。主要なものを選択し、残りを書き留めます。
- **実行:** アプリはローカルでどのように起動しますか?リポジトリ独自の文書化された開発コマンド (パッケージ スクリプト、Makefile、README クイックスタート) を優先します。ポート、環境変数、シード データ、認証に注意してください。
- **ドライブ:** エージェントはプログラムでどのように操作できますか?まずは既存のハーネス — Playwright/Cypress 仕様、期待スクリプト、PTY ヘルパー、curl 対応エンドポイント、デバッグ ポート。その場合のみ、Web および Electron 用のブラウザ/CDP、CLI/TUI 用の tmux/PTY ハーネス、サービス用のプレーン HTTP など、一般的なレシピを選択します。
- **観察してください:** どのような証拠が撮影できるでしょうか?スクリーンショット、端末トランスクリプト、応答本文、ログ、終了コード、DB 状態。
- **分離:** 2 つのインスタンス (ポート、データ ディレクトリ、プロファイル) を並行して実行できますか?そうでない場合は、生成されたスキルでその旨を伝えます。共有インスタンスの二重駆動を拒否することは、ユーザーのセッションを破壊することに勝ります。

チェックアウトがそのままではビルドまたは開始されない場合は、生成する前にまずそれを修正します (または正確に報告します)。壊れたベースに対して書かれたスキルは、間違った手順を教えてしまいます。無関係な欠落アセットによって起動がブロックされる場合 (API が決して提供しない静的ディレクトリ、サンプル構成)、生成されたスキルによってそれが作成され、検証スキャフォールディングとして明確にマークされ、クリーンアップで削除されることがあります。

<a id="2-generate-the-skill"></a>

## 2. スキルを生成する

YAML フロントマターを使用して `.cursor/skills/verify-<app>/SKILL.md` を記述します (`name: verify-<app>` と、アプリ、サーフェス、およびそれに到達するタイミングを指定する `description` を指定します。フロントマターがないとスキルは登録されません)。これらのセクションはそれぞれ、インタビューで実際に見つかった内容に基づいています (プレースホルダーは残されていません)。

- **起動:** 検証のためにアプリを起動する正確なコマンドと、準備ができたことを確認する方法 (ログ行、ポート応答、プロンプト)。分解も含めて。有効期間が短い CLI または TUI の場合、生き続けるサーバーはありません。起動とは、バイナリを一度ビルド (または deps をインストール) し、その後、独自の分離された PTY または tmux セッションで各ドライブを起動することを意味します。
- **博士:** 「このインスタンスは運転する価値がありますか?」に答える読み取り専用チェックが 1 つあります。 — プロセスアップ、正しいバージョン/ビルド、当社が所有するポート、有効な認証。何か問題があると思われる場合は、エージェントが最初にこれを実行します。
- **ドライブ:** サンプルではなく、このリポジトリの実際のセレクター/コマンドを使用したハーネス レシピ。座標やタブ オーダーよりも、安定したハンドル (ARIA ラベル、データ属性、プロンプト文字列、ルート パス) を優先します。
- **証拠:** 証拠として何をキャプチャし、どこに送信するか。証明基準を明示します。内部セッターやテスト専用のエンドポイントではなく、実際のユーザー パスを実行します。最終画面だけでなく、アクションとその結果の状態をキャプチャします。副作用 (書き込まれたファイル、挿入された行、送信されたメッセージ) を、表示されている内容とともに検証します。実稼働境界によって外部システムがすでに分離されている場合にのみモックを作成します。安全なパスがドライランまたはテスト モードの場合は、その名前を信頼するのではなく、(ファイル、ネットワーク、git refs) を観察して、実際に何がスキップされるかを確認してください。一部のドライランは依然としてネットワークに接続しているか、ブラウザを開いている場合があります。
- **クリーンアップ:** 実行によって作成されたインスタンスを破棄する方法。決してプロセス名で強制終了しないでください。あなたが始めたことを殺します。クリーンアップではインスタンスとスクラッチ状態は削除されますが、証拠は削除されません。証拠となるアーティファクトは、スキルが指定した場所にある分解後も生き残ります。
- **ヘルパー:** スキルに付属するスクリプトはすべて実行可能であり、その呼び出しはスキル本体に表示されます。読者がリバースエンジニアリングしなければならないヘルパーはヘルパーではありません。

<a id="3-seed-the-feature-map"></a>

## 3. 機能マップのシード

`.cursor/skills/verify-<app>/features/README.md` に加えて、特定できるユーザー向け機能ごとに 1 つのファイルを作成します (ルート、コマンド、メニュー、またはドキュメントから上位 3 ～ 5 を目指して開始します)。 [`references/feature-map-example/`](references/feature-map-example/) の形式に従い、README インデックスと機能ごとに 1 つのファイルを使用します。各ファイルは、機能が何であるか、その機能に到達する方法、ハーネスを使用してそれを駆動する方法、およびその機能が動作していることを証明する観察可能な最終状態など、ユーザーの視点からの答えを返します。 4 つの H2 は、`Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>`、および `Gotchas` です。マップはリポジトリで維持される検証ソースです。マップに他のエントリ ポイントがリストされている場合、1 つの便利なエントリ ポイントを駆動する証明は不完全になります。

<a id="4-prove-the-generated-skill-before-handing-it-over"></a>

## 4. 生成されたスキルを引き渡す前に証明する

独自の命令をエンドツーエンドで 1 回実行します: 起動、ドクター、マップされた機能を 1 つ駆動 (1 つで十分です。マップが存在するため、後の実行で残りをカバーできます)、証拠のキャプチャ、クリーンアップ。クリーンアップ後、指定された場所に証拠がまだ存在していることを確認します。証拠を消去するクリーンアップはこのステップに失敗します。失敗したものを修正し、反復が失敗するたびに生成されたクリーンアップを実行することで、失敗した試行によってプロセスやポートが取り残されることがなくなります。生成されて実行されなかったスキルは、成果物ではなくドラフトです。

<a id="5-offer-the-maintenance-loop"></a>

## 5. メンテナンス ループの提供

アプリの変更時に地図を正確に保つために、ユーザーに `/maintain-verification-skill` を指示します。彼らが尋ねた場合にのみ、リズムを提案してください。
