# ノート検証マップ

このディレクトリは、Notes のユーザー側の動作を検証するために維持されるソースです。アプリを実行する前にインデックスを読み取り、一致する機能ファイルをレシピとして使用します。

<a id="baseline-preconditions"></a>

## ベースラインの前提条件

- 使い捨てデータ ディレクトリを使用して、`http://127.0.0.1:4173` で Notes を起動します。
- `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID` を設定して、同時実行が状態を共有しないようにします。
- `Quarterly plan` および `Grocery list` というタイトルのシード ノート。
- `control-notes` と `notes` CLI を `PATH` に配置します。
- `control-notes doctor` を実行し、予想される URL、データ ディレクトリ、およびビルド リビジョンを必要とします。
- この検証実行によって開始されていないインスタンスは決して駆動しないでください。

<a id="driving-conventions"></a>

## 運転規則

- 前提条件に別の記載がない限り、すべてのレシピをベースライン状態から開始します。
- CSS セレクターや DOM 位置よりも ARIA ロールとアクセス可能な名前を優先します。
- すべてのコマンドをリテラルとして扱います。引用符で囲まれた名前とフラグは変更しないでください。
- `control-notes browser` を通じてブラウザー アクションを実行します。
- `control-notes cli -- <command>` を通じてターミナル アクションを実行します。
- ミューテーション後にシードされたデータを復元します。クリーンアップ中にプルーフ アーティファクトを削除しないでください。

<a id="proof-and-skip-reporting"></a>

## 校正およびレポートのスキップ

- 最終画面だけでなく、ユーザーのアクションとその結果の状態をキャプチャします。
- UI 証明には、ARIA スナップショットと、アプリ ID が表示されたスクリーンショットが含まれています。
- CLI 証明には、コマンド、stdout、stderr、および終了コードが含まれます。
- 変異証明には、格納された値の読み取り専用の 2 番目のビューが含まれます。
- すべてのアーティファクトで使用される機能 ID とエントリ ポイントを記録します。
- 試行されたコマンドと満たされていない前提条件を含む到達不能なパスを報告します。
- スキップされたエントリ ポイントを、別のパスを通じて検証されたものとして報告しないでください。

<a id="feature-entry-contract"></a>

## 機能エントリー契約

各機能ファイルは、H1 タイトルと、ユーザーに表示される動作を説明する 1 つの段落で始まります。次に、この順序でちょうど 4 つの H2 セクションを使用します。

1. `Sub-features` は、動作ごとに 1 行の短い ID をリストします。
2. `How to get to it (user POV)` には、すべてのユーザー エントリ ポイントがリストされます。
3. `Driving it with <harness>` は `Preconditions:` で始まり、各ユーザー アクションと正確なコマンドおよび観察可能な結果を組み合わせるラベル付きの箇条書きを使用します。
4. `Gotchas` は、検証の実行を無駄にしたり無効にしたりする可能性のあるトラップをリストします。

実装の詳細をマップに載せないでください。ユーザー パス、安定したハンドル、必要な状態、コマンド、および観察可能な証拠のみを指定します。

<a id="features"></a>

## の特徴

- [検索メモ](./search.md) は、ツールバー、キーボード、および一致、空、およびクリア状態の CLI 検索をカバーします。
