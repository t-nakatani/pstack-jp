# コード品質レビュー

各レビュー担当者は、ルーブリックに加えて、このコード品質のレンズを適用します。これは、実装の品質、保守性、抽象化の品質、コードベースの健全性に重点を置いた厳格な標準です。

何よりも、コード構造については意欲的に取り組んでください。単にローカルなクリーンアップを特定するだけではありません。 「コード柔道」の動き、つまり実装を劇的に単純化、小型化、直接的、洗練させながら動作を維持する再構築を積極的に検索します。

<a id="core-prompt"></a>

## コア プロンプト

このベースラインから開始します。

> 現在のブランチの変更について詳細なコード品質監査を実行します。
> 動作に影響を与えることなくコードの品質を有意義に向上させるために、変更を構造化/実装する方法を再考します。
> 抽象化、モジュール性の向上、スパゲッティ コードの削減、簡潔さと読みやすさの向上に努めます。
> 野心的になり、コードベースの一部の再構築を含む実装を改善するための明確な道筋がある場合は、それに取り組んでください。
> 非常に徹底して厳密に行ってください。 2回測って1回カット。

<a id="dimensions"></a>

## 寸法

各寸法は 1 回ずつ記述されます。関連するものを適用してください。

0. **構造の簡素化については意欲的に取り組んでください。** 「もう少しすっきりするかもしれない」で終わらせないでください。ブランチ、ヘルパー、モード、条件文、またはレイヤー全体を非表示にするリフレーミングを探してください。 「コード柔道」の動きが頻繁に利用可能であると仮定します。既存のアーキテクチャをより効果的に使用し、変更を劇的に簡素化します。複雑さを再配置するのではなく削除できる場合は、そのために全力を尽くしてください。

1. **よほどの理由がない限り、PR にファイルを 1,000 行未満から 1,000 行を超えるファイルにプッシュさせないでください。** これは強い臭いとして扱ってください。ヘルパー、サブコンポーネント、またはモジュールを抽出することを好みます。差分がそのしきい値を超えた場合は、最初にコードを分解する必要があるかどうかを尋ねます。結果として得られるファイルが明確に整理されたままであるという、やむを得ない構造上の理由がある場合にのみ放棄してください。

2. **既存のコードでスパゲッティの増大を許可しないでください。** 新しいアドホックな条件文、散在する特殊なケース、または無関係なフローに挿入された 1 回限りの分岐を疑ってください。 「ランダムな場所にある奇妙な if ステートメント」は、スタイルの問題ではなく、設計の問題として扱います。既存のパスを複雑にするのではなく、ロジックを専用のヘルパー、ステート マシン、またはモジュールにプッシュすることを好みます。

3. **動作するコードを受け入れるだけでなく、設計をクリーンにすることへのバイアス。** 構造が大幅にクリーンになる一方で動作が変わらない場合は、クリーンなバージョンを推し進めてください。同じ複雑さを分散させるリファクタリングよりも、移動部分を取り除く単純化を優先します。

4. **ハッキーなコードや魔法のようなコードよりも、直接的で退屈で保守可能なコードを優先します。** 脆弱な、その場限りの、または「魔法の」動作を問題として扱います。単純なデータ形状の仮定を隠す一般的なメカニズムには懐疑的になってください。明確さを損なわずに間接性を追加する薄い抽象化、ID ラッパー、またはパススルー ヘルパーにフラグを立てます。

5. **保守性に影響する場合は、型と境界のクリーンさを重視します。** より明確な型境界が存在する可能性がある場合は、不必要なオプション、`unknown`、`any`、またはキャスト負荷の高いコードを疑ってください。大まかな形状のアドホック オブジェクトよりも、明示的に型指定されたモデルを優先します。ブランチが不明確な不変条件よりも紙へのサイレントフォールバックに依存している場合は、境界を明示する必要があるかどうかを検討してください。

6. **正規レイヤーにロジックを保持し、既存のヘルパーを再利用します。** 共有パスに漏れる機能ロジックや、API を介して漏れる実装の詳細を呼び出します。特注の一回限りのユーティリティよりも、既存の正規ユーティリティを優先します。ドリフトを正規化するのではなく、コードを適切なパッケージ、サービス、またはモジュールにプッシュします。

7. **クリーンな構造が明らかな場合は、不必要なシーケンシャル オーケストレーションと非アトミックな更新をデザインの臭いとして扱います。** 独立した作業が理由もなくシリアル化される場合は、並列実行する必要があるかどうかを確認してください。関連する更新によって状態が半分適用されたままになる可能性がある場合は、よりアトミックな構造を推し進めてください。マイクロ最適化ではインデックスを過剰に設定しないでください。ただし、コードを脆弱にする回避可能なオーケストレーションの複雑さにはフラグを立ててください。

<a id="output-expectations"></a>

## 出力の期待値

最初に構造的なコード品質の回帰と単純化の欠落を優先し、次にスパゲッティと分岐の複雑さ、次に境界、タイプ、およびファイル サイズの問題、次に小さなモジュール性と読みやすさの問題を優先します。

<a id="approval-bar"></a>

## 承認バー

動作が正しいと思われるだけでは承認しないでください。作成者が正当化できない限り、これらを推定上のブロッカーとして扱ってください。コードと柔道の動きが削除される場合でも、PR は多くの付随的な複雑さを保持します。ファイルを 1000 行未満から 1000 行以上にプッシュします。既存のフローを複雑にするアドホック分岐を追加します。機能チェックを共有コード全体に分散します。明確な正規ホームがある場合に、不必要な抽象化、ラッパー、またはキャスト負荷の高いコントラクトを追加したり、既存のヘルパーを複製したり、間違ったレイヤーにロジックを配置したりします。これらの条件が満たされない場合は、明示的で実用的なフィードバックを残して、よりクリーンな分解を推進してください。

<a id="review-tone"></a>

## レビュートーン

品質に関しては率直かつ真剣で、厳しい要求を持ちます。失礼なことはしないでください。ただし、保守性に関する主要な問題を穏やかな提案に和らげないでください。コードのせいでコードベースが乱雑になっている場合は、その旨を伝えてください。実装に明らかな大幅な簡素化が欠けていた場合は、そのことも伝えてください。実際の問題が構造的な場合は、「名前を変更してもいいかもしれない」という考えで満足しないでください。
