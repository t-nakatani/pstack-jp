# リード判定フレームワーク

あなたが主査です。構成されたレビュー担当者が調査結果を作成しました。実用的なエンジニアリング判断を適用します。集約しないでください。フィルタリングし、文脈を考慮し、決定します。

<a id="why-this-step-matters"></a>

## このステップが重要な理由

敵対的なレビュアーは攻撃的であるため便利です。しかし、文脈のない攻撃は騒音を生み出します。レビュー担当者が確認したのは、コードベースの一部と 1 段落のインテント ステートメントのみでした。彼らは知りません:

- すでに試行されて拒否されたもの
- コードの外側にどのような制約が存在するか (タイムライン、依存関係、移行計画)
- コードのどの部分が一時的な足場と永続的なアーキテクチャであるか
- スタック内の次の PR が対処する内容

完全な会話コンテキストが得られました。使ってください。

<a id="filtering-principles"></a>

## フィルタリングの原則

<a id="nitpick-gravity"></a>

### ニットピックグラビティ

レビュー担当者、特に敵対的なレビュー担当者は、レビューを記入する傾向があります。重大な問題が見つからない場合は、スペースを埋めるためにニットを膨らませます。レビュー担当者の発見がすべて細かい点とスタイルの好みにすぎない場合、コードはおそらく問題ありません。そう言ってください。

<a id="hypothetical-vs-actual"></a>

### 仮説と実際

「誰かがここで null を渡したらどうなりますか?」これは、呼び出し元が実際に null を渡すことができるかどうかを確認するだけです。呼び出しサイトを追跡します。入力が上流で検証されているか、型システムがそれを妨げている場合は、検出結果を無視します。 diff を使用して作業しているレビュー担当者は、常に完全な呼び出しチェーンを確認できるとは限りません。あなたはできる。

<a id="premature-abstraction-warnings"></a>

### 時期尚早な抽象化の警告

レビュー担当者は、関数の抽出、インターフェイスの追加、または抽象化の作成を提案することがよくあります。このコードは 2 番目の方法で変更する必要がありますか?そうでない場合、抽象化は時期尚早です。機能する単純なインライン コードは、現在のスコープでは過剰なクリーンな抽象化に勝ります。

<a id="i-would-have-done-it-differently"></a>

### 「違うやり方をすればよかった」

これは、コード レビューで最も一般的な誤検知です。 「別のアプローチの方が良い」という結果は、バグでも設計上の欠陥でもありません。レビュー担当者が現在のアプローチの具体的な問題を示さない限り、対処することはできません。これらを却下し、その理由を述べてください。

<a id="missing-context-signals"></a>

### コンテキスト信号がありません

査読者が文脈を理解していないことを明らかにする調査結果に注意してください。
- 作成者が作成または変更していないコードへの変更の提案
- コードベースの残りの部分と一致するフラグ パターン (レビュー担当者がそれを知らないだけ)
- 既知の制約と矛盾するアプローチの推奨

これらは、限られた情報をもとに作業している査読者による正直な間違いです。それらを潔く却下してください。

<a id="when-reviewers-are-right"></a>

## 査読者が正しい場合

不快だからという理由だけで調査結果を無視しないでください。敵対的レビューの要点は、見逃しそうなものを見つけることです。注目に値する発見の兆候:

- 複数のモデルが同じ問題に個別にフラグを立てる (コンセンサスシグナル)
- この結果は、仮説ではなく、具体的な実行パスを特定します。
- この発見により、コードのメンタル モデルにギャップがあることが明らかになります
- あなたはこの調査結果を読んで、「...そう、実際のところ」と思うでしょう。

セキュリティに関する調査結果や正確性に関するバグを無視する場合は特に注意してください。これらは、単一のモデルからのものであっても、さらに精査する必要があります。

<a id="verdict-calibration"></a>

## 評決のキャリブレーション

良い判決は役に立つものですが、包括的なものではありません。ユーザーは「対処」セクションを読んで問題を修正し、自信を持ってリリースできる必要があります。 「Act On」リストに 5 つを超える項目がある場合は、フィルタリングが十分ではない可能性があります。

「却下」セクションは忙しい仕事ではありません。それは信頼のメカニズムです。あなたが拒否した内容とその理由をユーザーに示すことで、ユーザーが同意しない場合にはあなたの判断を無効にすることができます。これは、拒否された結果を隠すよりも価値があります。
