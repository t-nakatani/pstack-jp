<a id="review-rubric"></a>

# レビュールーブリック

関連するレンズを通して確認してください。すべてのレンズがすべての変更に当てはまるわけではありません。判断力を使いましょう。

<a id="correctness"></a>

## 正確さ

コードは、意図に示されたとおりのことを実際に実行していますか?

- エッジケース: 空の入力、nil/未定義、境界値、同時アクセス
- エラー処理: エラーは捕捉され、伝播され、あるいは黙って飲み込まれますか?
- Off-by-one、型強制、整数オーバーフロー、文字列エンコーディング
- 状態管理: 競合状態、古いクロージャ、ダングリング参照
- ハッピーパスはうまくいきますか?悲しい道はうまくいきますか？
- べき等性: この操作が 2 回実行された場合、または前の実行が途中でクラッシュした場合はどうなりますか?答えが「どのような状態が取り残されたかによる」である場合、調整のステップが欠けていることになります。
- 同時実行性: 複数のアクターが同じ変更可能な状態 (ファイル、ブランチ、共有データ) にアクセスできる場合、アクセスは構造的にシリアル化されますか (ロック、順次フェーズ、排他的所有権)、それとも保持されない規則によってシリアル化されますか?

潜在的なバグを見つけたら、実行パスをトレースします。 「これはゼロである可能性があります」というフラグを立てるだけではありません。それを nil にする呼び出しチェーンを表示します。

<a id="root-causes-vs-symptoms"></a>

## 根本原因と症状

コードは実際の問題を修正しているのでしょうか、それとも症状を覆い隠しているのでしょうか?

これに答えるには、多くの場合、変更されたファイルをさらに調べる必要があります。周囲のコード (呼び出し元、呼び出し先、型定義、兄弟モジュール) を読み、変更が存在するアーキテクチャを理解します。利用可能なツール (Read、Grep、Glob) を使用して探索します。呼び出しチェーンをたどります。種類を読んでください。変更が適切なレイヤーに対応しているかどうかを判断する前に、コードが存在する理由を理解してください。

- より深い不変条件違反をマスクするガード句
- 壊れたコントラクトを隠す再試行ロジック
- モデリング エラーを黙らせるタイプ キャスト
- 回避策が見つかった場合は、なぜその回避策が必要なのかを尋ねてください。適切な修正とはどのようなものでしょうか?
- モジュール A の修正ですが、実際にはモジュール B のコントラクトの修正である必要があります
- 構造がより良い場合の指示: 修正が「X を実行しないでください」というコメントや誰かが覚えておく必要がある規則である場合、代わりに型制約、lint ルール、または間違ったことを不可能にする実行時チェックを使用できるかどうかを尋ねます。

<a id="structural-integrity"></a>

## 構造的完全性

コードは、それが属するシステムにうまく適合していますか?

- 境界規律: 検証はシステム境界で行われますか? それともビジネス ロジック全体に分散されますか?データがシステムに入力される時点で一度検証し、その後内部で信頼します。
- 抽象化レベル: コードは高レベルのオーケストレーションと低レベルの詳細を混合していますか?
- カップリング: この変更により、将来の変更が困難になる依存関係が導入されますか?
- データ モデルの適合性: データ構造は実際のアクセス パターンと一致していますか?適切な構造により、下流のコードが明確になります。間違った者があらゆる場面であなたと戦います。
- ボルトオン vs 統合: 変更は既存の設計にパッチされたものですか、それとも設計が常に考慮しているかのように解釈されますか?新しい要件が最初からわかっていた場合、コードは次のようになりますか?
- レガシー デュアルパス: この変更により、古い API は維持されたまま新しい API が導入されますか?外部コンシューマが存在しない場合は、同じ Wave で呼び出し元を移行し、古いパスを削除します。永続的になる互換性レイヤーを残さないでください。

抽象化が欠如している単純なコードにペナルティを与えないでください。時期尚早な抽象化は重複よりも悪いです。

<a id="verification"></a>

## 検証

このコードを読んだだけで動作することがわかりますか?

- テストはありますか?動作や実装の詳細をテストしますか?
- 回帰を検出するアサーション/不変条件はありますか?
- これがバグ修正の場合: バグのテストはありますか?
- これが統合境界に触れている場合: フルパスはテストされていますか?
- 代理店ではなく実物をご確認ください。コードが実際の値を読み取るのではなく、ファイルの mtime またはキャッシュされた状態を介して生存性をチェックする場合、それは検証ギャップとなります。
- 委任された作業または非同期作業の場合: コードは実際の出力アーティファクトを検証しますか、それとも自己報告と概要を信頼しますか?

<a id="complexity-budget"></a>

## 複雑さの予算

その複雑さは、コードが実現する内容によって正当化されますか?

- 正確さや明瞭さを失わずに、より単純化できるコード
- 1 つの呼び出しサイトのみにサービスを提供する抽象化
- まだ存在しないケースの構成またはパラメータ化
- デッドコード、未使用のインポート、痕跡パラメータ
- オーバーエンジニアリング: 現在の呼び出し元が存在しない「念のため」のコード パス
- 廃止された互換性パスは、不要になった過渡的な安定性のために存続しています。移行が完了したら、スキャフォールディングを削除します
- ユーザー エクスペリエンスはその複雑さを正当化しますか?すべての機能、コントロール、オプションが適切な位置を占める必要があります。中途半端な機能は、欠けている機能よりも悪いです。

シンプルであることが間違っていない限り、シンプルであるほど良いです。 3 行の重複は、時期尚早な抽象化を打ち破ります。

<a id="security"></a>

## セキュリティ

セキュリティの検出結果ごとに、コード内の入力パスをトレースして表示します。

- サニタイズなしで危険なシンク (SQL、シェル、eval、innerHTML) に流れるユーザー入力
- 新しいエンドポイントの認証/認可のギャップ
- コード、ログ、またはエラー メッセージ内の秘密
- セキュリティ クリティカルなパスの TOCTOU (チェック時間-使用時間)
