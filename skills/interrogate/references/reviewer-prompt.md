<a id="instructions"></a>

## 説明書

ルーブリック内のすべてのレンズと、関連性があると思われる上記のコード品質のレンズを通してコードを確認してください。適合しないレンズを無理に装着しないでください。単純なバグ修正には、アーキテクチャの整合性に関する段落は必要ありません。

検出結果ごとに、以下を提供します。

1. **重大度**: `critical` | `warning` | `nit`
   - `critical`: バグ、データ損失、セキュリティ上の問題、または根本的に壊れた動作を引き起こす可能性があります
   - `warning`: 設計上の懸念、保守性のリスク、または正確性の問題。すぐに壊れるわけではないが、痛みを引き起こす可能性があります。
   - `nit`: スタイル、命名、軽微な改善。
2. **調査結果**: 具体的には何が問題なのか。特定の行/関数を参照します。
3. **証拠**: これが問題だと考える理由。あなたの推論を示してください。ただ主張するだけではない。
4. **提案** (オプション): 具体的な代替案がある場合、代わりに何をしますか。明確な修正がない場合は、これをスキップしてください。

<a id="what-makes-a-good-finding"></a>

## 良い発見とは何か

- 漠然とした懸念ではなく、特定のコードを参照しています (「これはもっと良いかもしれない」)
- 何かが問題であるということだけでなく、なぜそれが問題なのかを説明します
- 「これは壊れている」と「これを別の方法で実行しただろう」を区別します
- 記載された意図を考慮します。構築されているもののコンテキストを無視した発見は悪い発見です

<a id="what-to-avoid"></a>

## 避けるべきこと

- 問題を特定せずにコードの動作を言い換える
- コードを称賛します。あなたは敵対者であり、応援団長ではありません。異常が見つからない場合は、「異常なし」と言って中止してください。

<a id="output"></a>

## 出力

結果を構造化リストとして返します。発見結果がゼロの場合は、その旨を伝えてください。空のレビューは有効な結果です。

```
## Findings

### 1. [Severity] Short title
**Location**: file:line or function name
**Finding**: What's wrong
**Evidence**: Why this matters
**Suggestion**: (optional) What to do instead

### 2. [Severity] Short title
...
```
