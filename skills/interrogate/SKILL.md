<a id="interrogate"></a>

# 尋問

構成されたモデルごとに 1 人のレビューアーを生成し、コードの変更を敵対的にレビューします。各モデルには同じプロンプトとルーブリックが表示されます。敵対的シグナルは、割り当てられたペルソナではなく、モデルの多様性から生じます。

成果物は合成された評決です。変更を自動適用しないでください。

<a id="step-1-determine-scope"></a>

## ステップ 1、範囲の決定

コンテキストから何を確認するかを特定します。

- ユーザーが特定のファイルまたは差分を指定した場合は、それを使用します
- 機能ブランチの場合は、完全な変更セットに対して `git diff main...HEAD` (または適切なベース ブランチ) を実行します。
- ユーザーのメッセージが最近の作業に言及している場合は、関連ファイルを収集します

差分 (またはファイルの内容) と、レビュー担当者がコードを理解するために必要な周囲のコンテキスト ファイルをパッケージ化します。

<a id="step-2-state-the-intent"></a>

## ステップ 2、意図を述べる

レビュー担当者を作成する前に、その意図を明示的に述べてください。これを次から導き出します。

- ユーザーのメッセージ
- コミットメッセージ
- PR の説明 (存在する場合)
- コード自体

明確な段落を 1 つ書きます。意図がわからない場合は、続行する前にユーザーに尋ねてください。

<a id="step-3-spawn-reviewers"></a>

## ステップ 3、レビュアーの作成

タスク ツールを使用して、単一のメッセージですべてのレビュー担当者を起動します。 `~/.cursor/rules/pstack-models.mdc` の `interrogate reviewers` 行を使用し、エントリごとに 1 人のレビュー担当者を指定し、以下のレビュー担当者 A/B ラベルを設定されたエントリ数まで拡張または縮小します。ルールまたはその行が欠落している場合は、テーブルのデフォルトを使用します。

| サブエージェント | デフォルトモデル |
|----------|---------------|
| レビュアー A | `claude-opus-5-5-xhigh` |
| レビュアー B | `grok-4.7-xhigh-fast` |

各レビュー担当者:
- `subagent_type`: `generalPurpose`
- `model`: 構成された `interrogate reviewers` エントリ、または構成された行のないテーブルのデフォルト。 `auto` または `inherit-parent` エントリの場合は、レビューアが親モデルで実行されるように `model` を省略します。
- `readonly`: `true`

タスク ツールが構成されたエントリを拒否した場合は、そのファミリーのテーブル デフォルトに対してそのレビューアーを実行して、その旨を伝えます。ファミリはプレフィックス `claude-*` および `grok-*` で指定されます。一致するファミリーがない場合は、レビュー担当者 A のデフォルトを使用します。テーブルのデフォルトが拒否された場合は、タスク ツールのエラー メッセージで有効なスラッグを確認し、最も近い同等のもの (同じファミリーと推論層を優先) を選択し、それを使用して生成し、別の PR を開いてデフォルト テーブルを更新します。ナメクジの問題に関するレビューをブロックしないでください。エイリアス エントリを拒否されたスラッグとして扱ったり、フォールバックを適用したりしないでください。

`references/reviewer-prompt.md` を読み取り、テンプレートに次のように入力します。
1. 記載された意図
2. 差分またはファイルの内容
3. `references/rubric.md` のレビュー ルーブリック
4. `references/code-quality-review.md` のコード品質のレンズ

同じ入力済みのテンプレートがすべてのレビュー担当者に送信されるため、すべてのモデルにコード品質のレンズが適用されます。

<a id="step-4-synthesize"></a>

## ステップ 4、合成

結果が返されたら、統合された図を構築します。

1. **査読者からのすべての結果を解析**
2. **コンセンサスを特定する**。 2 つ以上のモデルによって個別に提示された結果が最も高いシグナルです。
3. **単独モデルの結果を特定します**。それでも読む価値はありますが、それに応じて重み付けしてください。
4. **重複排除**。モデルが異なると、同じ問題の説明が異なる場合があります。これらをマージし、どのモデルがそれを引き起こしたかに注目してください。
5. **意見の相違があることに注意してください**。あるモデルが何かにフラグを立て、別のモデルが明示的に反対のことを言っている場合、それは評決にとって有用なコンテキストです。

<a id="step-5-lead-judgment"></a>

## ステップ 5、リードの判断

あなたは主任レビューアーであり、中立的なアグリゲーターではなく、現実的な上級エンジニアです。

完全なフレームワークについては、`references/lead-judgment.md` をお読みください。

これらのバケットを使用して、すべての結果を分類します。

- **行動してください**。実際の目標を考慮すると、正確性、セキュリティ、または保守性に影響を与える実際の問題。これらは実際の PR を妨げることになります。
- **検討してください**。正当な指摘ですが、現時点で対処するコストを上回るかどうかはわかりません。ユーザーの注目に値します。
- **注**。技術的には有効ですが、実用的ではありません。コンテキスト依存、時期尚早な最適化、または現在の段階では影響が少ない。
- **却下**。間違っている、注意が必要な、またはコンテキストが欠落している。その理由を簡単に説明。

検出結果ごとに、以下を含めます。
- どのモデルがそれを上げましたか
- カテゴリ (対応/検討/注目/却下)
- 分類の 1 行の根拠
