<a id="unslop"></a>

# アンスロップ

テキストを編集して AI パターンを削除します。

<a id="process"></a>

## プロセス

1. 以下のパターンをスキャンしてください。
2. 書き換えます。意味を保ち、意図したトーンに一致させます。

<a id="patterns-to-detect-and-fix"></a>

## 検出および修正するパターン

ルール番号は、他のスキルが引用する安定した ID です。ルールを削除するとギャップが残ります。

<a id="content"></a>

### コンテンツ

3. **表面的なフレーズ。** 「...を強調する」、「保証する...」、「反映する...」、「紹介する...」、「育成する...」。実際のソースを削除または展開します。
5. **帰属が曖昧です。** 「専門家は信じている」、「業界の報告書は示唆している」、「一部の批評家は主張している」。ソースに名前を付けるか、削除します。

<a id="language"></a>

### 言語

7. **AI の語彙。** さらに、重要、掘り下げる、永続的、強化する、育成する、収集する、相互作用、複雑、風景 (抽象)、極めて重要、ショーケース、タペストリー (抽象)、遺言、アンダースコア、活気に満ちています。わかりやすい言葉に置き換えてください。
8. **「である」のおしゃれな言い方。** 「として機能する」、「として立つ」、「自慢する」、「特徴がある」。 「ある」または「ある」とだけ言ってください。
9. **「X だけではなく、Y。」** 代わりに要点を直接述べてください。
10. **3 人のルール。** アイデアを 3 人のグループに強制的に分けます。自然数を使います。
11. **同義語サイクリング。** 主人公、主人公、中心人物、ヒーローのすべてが 1 つの段落にまとめられています。一つ選んで、それを繰り返します。
12. **誤った範囲。** 「X から Y まで」。X と Y は意味のあるスケールではありません。トピックを直接リストします。

<a id="style"></a>

### スタイル

13. **全ダッシュの使いすぎ。** 全ダッシュは完全に避けてください。ピリオドまたはカンマのみを使用してください (括弧、小文字、ダッシュ、ハイフンとダッシュの代替は使用できません)。考えを区切る必要がある場合は、文を終了するか、コンマを使用します。
14. **コロンの多用** リストや例の前にコロンを使用しても問題ありません。文の途中で接続するものではありません。 「従来の自動化から来ている場合: イベント ハンドラーを登録する代わりに、条件を記述します。」ではコロンは何も追加されません。比較フレームなしでポイントを独立させるように書き直します。 「スケジューラをいつ起動するかを記述するのは、平易な英語として最も効果的です。」同じ意味ですが、句読点は必要ありません。
15. **太字の使いすぎ。** すべての固有名詞や頭字語を太字にしないでください。
16. **インラインヘッダー リスト。** テルは、「**パフォーマンス:** パフォーマンスが向上しました...」という行を再表現する太字のラベルとコロンです。それらを文章に変換します。ピリオドで終わり、項目に名前を付け、その後にまったく新しい詳細 (「**TypeScript のスキーマ。** テーブルは 1 つのファイルに存在します。」) が続く太字の導入は問題ありませんが、指示ではありません。
17. **タイトルの大文字と小文字の見出し。** 文の大文字と小文字を使用します。
18. **装飾絵文字。** 見出しと箇条書きから削除します。
19. **中引用符。** 直線引用符に置き換えます。

<a id="communication-artifacts"></a>

### 通信アーティファクト

20. **チャットボット フレーズ。** 「これがお役に立てば幸いです!」、「もしあればお知らせください...」、「もちろんです!」、「確かに!」、「決定的な証拠を見つけました!」取り除く。
22. **おべっかのような口調** 「素晴らしい質問ですね! まさにその通りです!」直接応答してください。

<a id="filler"></a>

### フィラー

23. **フィラーフレーズ。** 「In order to」は「To」になります。 「という事実により」が「なぜなら」になります。 「注意が必要です」は削除されます。
24. **過剰なヘッジ。** 「潜在的におそらくそれが可能であると議論される可能性がある」が「かもしれない」になります。
25. **一般的な結論** 「未来は明るいようです。」具体的な計画や事実を述べます。

<a id="jargon"></a>

### 専門用語

26. **抽象的なメタファー名詞。** 基板、ウェッジ、ベクトル、軌跡、ヴァンテージ、ネクサス、プリミティブ (名詞として)、ハーネス (メタファーとして)、表面 (「API サーフェス」など)、岩盤、足場 (メタファーとして)、モダリティ、パラダイム、金メッキ、ラチェット (メタファーとして)、退避 (コードを移動するため)、エンドゲーム、北極星、フライホイール。これらは技術的なもののように見えますが、通常はより単純な具体的な言葉が含まれています。 「基材」が「ベース」になります。 「ウェッジイン」が「追加」になります。 「ベクトル」は「方法」や「方法」になります。 「金メッキ」は「仕事のニーズ以上」になります。 「ラチェット」は機構の本名、つまり「締めるだけの限界」になります。 「避難」が「引っ越し」になります。 「エンドゲーム」は「最終段階」になります。具体的な言葉を選んでください。

<a id="plain-speech"></a>

### 平易なスピーチ

27. **それがどのように感じるかではなく、それが何をするかを語ってください。** 「データベースがすぐ近くにある」、「SQL が読める」、「スキーマに従う型」が感覚に名前を付けます。この修正では、メカニズムまたは数値に名前を付けます。「`.toSQL()` は、データベースに送信された正確な文字列を返します」、「列名の変更はビルドに失敗します」。その文が読者に何をするべきか、何を知るべきかを尋ねてから、それを書きます。具体的な指示、事実、数字として言い直すことができない場合は、カットしてください。もう 1 つ確認してください。別のプロジェクトのドキュメントでその文が変更されていない可能性がある場合、このドキュメントについては何も述べられていません。カットしてください。
28. **密集した文を短くするか分割します。** 読者が文を解析するために後戻りする必要がある場合は、文を 2 つに分割するか、文節を削除します。 1 文につき 1 つのアイデア。
29. **アクティブな音声。** 推奨します。 「is/are/was/were + 過去分詞」をキャッチし、アクターに名前を付けます。「クエリが検証される」は「コンパイラがクエリを検証する」になり、「ファイルはローダーによって解析される」は「ローダーがファイルを解析する」になります。パッシブは、俳優が未知の場合、または本当に重要でない場合にのみ問題ありません。
30. **副詞を削除するか、より強い動詞を使用してください。** 「すぐに走る」は「速い」または数字になります。 「大幅に改善」が測定されたデルタになります。副詞が弱い動詞を支えている場合は、その動詞が間違っていることを意味します。
31. **平易な言葉を好みます。** 「utilize」は「use」、「leverage」は「use」、「facilitate」は「help」、「numerous」は「many」、「in the events that」は「if」になります。派手な同義語がこれほど明確なものはめったにありません。
32. **礼儀正しい文章。** 文字通りのフレーズが存在する場所での比喩や繁栄: 格言 (「配線するか、削除するか」)、効果を高めるための修辞的断片、擬人化されたコード (「計画はそれを保持している」)、比喩動詞 (「一緒に乗る」、「立ち上がる」)、ストック フレーミング フレーズ。 「回す価値のあるダイヤル」は「変える価値のあるパラメーター」になります。言いたいことを言ってください。ルール 26 は比喩名詞を対象としています。
33. **過剰圧縮。** 読者に読ませる代わりに解読させる記事、言葉のない断片、記号の話、および略語が削除されました。 「パーサーは不正な日付を拒否 → 終了 2、書き込みなし」は、「パーサーは不正な日付を拒否し、コード 2 で終了し、何も書き込みません」になります。冠詞と動詞を含む文章全体を書き、矢印と略語を詳しく書きます。
