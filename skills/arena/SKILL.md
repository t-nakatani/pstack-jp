<a id="arena"></a>

# アリーナ

同じタスクに対する N 回の並列試行をファンアウトします。すべての候補を端から端まで読んでください。ベースとして最も強力なものを選択します。他の人からの最高のアイデアを移植します。合成結果を確認します。

<a id="start"></a>

## スタート

何かを起動する前に、フェーズごとに 1 つのエントリを含む todolist を開きます。

1. フレーム
2. ファンアウト
3. クロスジャッジ
4. ピック
5. グラフト
6. 確認する

<a id="phase-a-frame"></a>

## フェーズ A: フレーム

N 人の候補者が同じプロンプトを受信するため、プロンプトは契約になります。

1. 各候補者が作成している成果物を述べます。
2. ルーブリックを導出します。 *この*タスクの成功とはどのようなものか述べ、それを 3 ～ 6 個の具体的な採点可能な基準に変換します。ルーブリックはフェーズ D のピッカーのツールです。受験者にはタスクのみが表示されます。
3. ランナーを選択します。 `~/.cursor/rules/pstack-models.mdc` の `arena runners` 行を使用します。ルールまたはその行が欠落している場合は、デフォルトで `claude-opus-5-5-xhigh` と `grok-4.7-xhigh-fast` にそれぞれ 1 つが設定されます。この行またはクロスジャッジ行の `auto` または `inherit-parent` エントリは親モデルを意味するため、`model` を省略します。タスク ツールが設定されたエントリを拒否した場合は、そのシートをそのファミリーのデフォルトで実行して、その旨を伝えます。ファミリはプレフィックス `claude-*` および `grok-*` で表されます。ファミリー一致がない場合は、`claude-opus-5-5-xhigh` を使用します。デフォルトが拒否された場合は、エラー メッセージにある同じファミリーの最も近い有効なスラッグを使用します。アリーナが複数のデザイン方向をカバーしている場合、より多くのスポーンが行われます。作品が判断に依存するのではなく世代に依存する場合、同じモデルが N 回発生します。
4. 出力パスを割り当てます。各候補者は、**共有状態のシリアル化前に分離** 原則スキルに従って、独自の場所 (可能な場合は git ワークツリー、それ以外の場合は `/tmp/arena-<slug>/candidate-<n>/`) に書き込みます。

<a id="phase-b-fan-out"></a>

## フェーズ B: ファンアウト

`run_in_background: true` を含む 1 つのメッセージで N 個のサブエージェントすべてを生成します。各サブエージェントには、タスク、共有接地へのパス、独自の出力パス、およびアーティファクトと短い根拠の両方を生成する命令が含まれます。

それぞれの根拠には、候補者が検討した代替案と候補者が拒否した内容が記載されています。

候補が出力の生成に失敗した場合は、N-1 に進み、合成レコード内のドロップアウトに注目します。

<a id="phase-c-cross-judge"></a>

## フェーズ C: クロスジャッジ

フェーズ B の候補がすべて完了したら、`~/.cursor/rules/pstack-models.mdc` の `arena cross-judge pool` 行からモデルを 1 つ選択します。ルールまたはその行が欠落している場合は、`claude-opus-5-5-xhigh` および `grok-4.7-xhigh-fast` から選択します。親のモデル ファミリとは異なるモデル ファミリを選択します。そのモデル上に読み取り専用のジャッジ サブエージェントを 1 つ生成します。パスラベルごとにルーブリックと候補を確認し、各基準をスコアリングして、根拠のあるベースを推奨します。これは、候補者自身ではなく、フェーズ D の保護者の読書と並行して実行されます。候補者がまだ執筆している間は裁判官を生成しないでください。

<a id="phase-d-pick-a-base"></a>

## フェーズ D: ベースを選択する

選択する前に、すべての候補を端から端まで読んでください。

全体的な感覚ではなく、基準ごとにルーブリック基準に照らして各候補者を採点します。クロスジャッジと比較します。ベースに関する合意により指名が確定する。意見の相違は、どちらかが偏見を持っているか、ルーブリックがあいまいであることを意味します。決定する前に両方の根拠を読んでください。

将来のメンテナが不変条件を破ることなく最も簡単に拡張できる候補のベースを選択します。 Laziness Protocol に従って、2 つが結びついていると感じる場合は、より明確な境界またはより小さい API を優先します。

選択とその理由を、ベース アーティファクトと一緒に短い合成ノートに記録します (クロスジャッジの評決も含む)。

<a id="phase-e-graft"></a>

## フェーズ E: 移植

敗者候補をそれぞれもう一度歩き回り、何をベースに移植する価値があるかを特定します。シグナルは通常、候補者ごとに 1 つまたは 2 つのものであり、ほとんどではありません。

**第一原理からの再設計**の原則スキルに従って、各グラフトを手で折り込みます。機械的に貼り付けないでください。結果は 1 つのメンタル モデルの下で一貫性を保たなければなりません。

どの候補から何が接ぎ木されたか、何が拒否されたか、そしてその理由を記録します。

N 個の候補が同じ形状に収束する場合、それは強い一致信号です。レコード内の収束に注意し、コンセンサス形状を送信します。移植片は必要ありません。 N 個の候補が大きく異なる場合、フェーズ A は仕様が不十分でした。発散を平均するのではなく、再フレームして再実行します。

<a id="phase-f-verify"></a>

## フェーズ F: 検証

合成されたアーティファクトは、**prove-it-works** 原則スキルに従って、他の出力と同じ精査の下で耐える必要があります。

検証の結果、アリーナが捉えられなかった問題が明らかになった場合は、フェーズ A が間違っていた (再フレームして再実行) か、1 人の候補者が問題を捉えてグラフトを逃した (フェーズ E に戻る) かのいずれかです。紙を重ねないでください。

<a id="outputs"></a>

## 出力

合成アーティファクト 1 つ。塩基、移植片 (ソース候補を含む)、拒絶反応、ドロップアウト (存在する場合)、および検証結果の名前を示す 1 つの短い合成メモ。
