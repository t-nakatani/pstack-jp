<a id="maintain-a-verification-skill"></a>

# 検証スキルを維持する

機能マップは、アプリが変更された瞬間に腐ってしまいます。このスキルは、`/create-verification-skill` によって生成されたスキル (または機能マップを持つプロジェクト ローカル検証スキル) の維持ループです。厳密さの単位は、すべての文ではなく機能です。ソースからすべての機能ファイルをカバーし、すべての箇条書きを終了することなく、すべての機能をライブで実行します。

<a id="outcomes"></a>

## 結果

1 つ選んで、どれかを言ってください:

- **クリーン** — すべての機能がソースとライブ カバレッジを取得しました。リリースする価値のあるものは何もありません。支店も広報もありません。
- **変更** — 1 つの PR には、実績のあるドキュメント、ハーネス、またはマップの修正が同梱されています。
- **ブロックされました** — カバレッジを終了できなかったか、証明された修正を安全にリリースできませんでした。何がブロックしたのか正確に言ってください。

<a id="edit-scope"></a>

## スコープの編集

検証スキル自体のディレクトリ (SKILL.md、features/、および所有するハーネス スクリプト) のみを編集します。実行中にプロダクト コードを編集しないでください。マップで説明されている、アプリが実行しなくなった動作は、ドキュメント ドリフト (マップを修正) または製品の回帰 (報告してください。ドキュメントに記載しないでください) のいずれかです。

<a id="pass"></a>

## パス

0. **ターゲットを見つけます。** 維持する検証スキルを見つけます。本体に起動/駆動セクションと機能マップ (通常は `.cursor/skills/verify-*/`) があるプロジェクト ローカル スキルです。複数の候補者→どれを選ぶか尋ねます。なし → ターゲットを作成する代わりに、停止して `/create-verification-skill` を指します。

1. **インデックスの衛生管理。** 機能マップの README を読み、その兄弟ファイルをグロブします。不足しているエントリ、余分なエントリ、重複したエントリ、または無効なエントリを修正します。軽量;生成された在庫はありません。

2. **ソース ウェーブ。** 機能ファイルごとに 1 つの読み取り専用サブエージェントが同時に起動されます。それぞれが「このユーザー向け機能はどのように機能するのか?」について説明しています。ソースから、フラグは引用とともにドリフトする可能性が高く、1 つの簡潔なライブ検証レシピを返します。子どもたちはアプリを操作したり、ファイルを編集したりすることはありません。戻り値: 機能の概要 / ソース エントリ ポイント / ドリフトまたはなし / 1 つのレシピ。

3. **調整します。** すべての機能ファイルには要約が返されます。重複するレシピを可能な限り少数のアプリ状態にマージします。引用されたドリフトをスポットチェックします。きれいな主張を再証明しないでください。最近のチャーンをスイープして、マップから欠落しているユーザーに面したサーフェスを探します。欠落しているサーフェスを呼び出す前に、具体的なソース パスが必要です。

4. **ライブ パス。** ソースがきれいに見える場合でも必要です。コーディネーターがすべての運転を所有します。検証スキル独自の起動モデルに従います。つまり、サーバーと UI に対して連続的に駆動される 1 つの長期インスタンス、または短期間の CLI に対してドライブごとに新たに分離されたセッションです (このモデルではなく、スキルの起動セクションが決定します)。すべての機能を少なくとも 1 回実行し、障害が何であれ、パス全体で 3 つの不変条件を保持します。(1) 最後に何か驚くべきことを実行して以来、ヘルスチェックを行っていないインスタンスを決して駆動しないでください。最初の駆動の前にドクター、セッションが単位である新しいセッションごとにドクター、失敗したドライブの後に再度ドクター、ドクターが障害を確認できない場合 (正常なプロセス上のウェッジされた UI 状態)、既知の状態にリセットするか、期待するのではなく再起動します。 (2) これまでに捕獲された証拠は、指定された場所で確認され、想定されていないすべての清掃で生き残っています。 (3) 開始されたドライブがそのドライブの有用性を超えて存続するものはありません。セッションがスタックしているか、終了しているか、共有されているかに関係なく、失敗した反復の残留物はクリーンアップされます (共有インスタンスの場合は、インスタンスではなく残留物をクリーンアップします)。スキル ドリフトによって引き起こされるドクターの失敗はドリフトです。編集スコープで修正し、パス `blocked` を呼び出す前に、無効になった修正をすべて再開し、それ以上は何もせずに 1 回再試行します。到達できない機能は、具体的な前提条件 (認証、資格、OS、外部状態) と試行されたルートがある場合のみ `verified-unreachable` です。マップがその前提条件を省略している場合、それはドリフトです。トリアージによるハーネス修正は、リリース前にライブで再駆動されます。最終的な分解は、再校正も含め、ランの最後のドライブ後に行われるため、ランが終わるまで生き残るものは何もありません（スキルごとに証拠は残ります）。

5. **トリアージ。** ユーザー POV の説明が間違っているか欠落している → ドキュメントのずれ、修正してください。ハーネスが駆動できない動作動作 → ハーネスのギャップ、修正します。ハーネスの修正は、生成と同じヘルパー ルールに従います (実行可能なスクリプト、スキル本体に記述された呼び出し)。実際に壊れているアプリの動作 → 製品のギャップ。ユーザーのために記録し、この PR には含めないでください。

6. **リリースまたは停止。** 変更の場合: 証明された修正の 1 つの PR、最初に変更されたすべてのファイルを再読み込みします。クリーンまたはブロックの場合: PR は行わず、結果と報道内容を正直に報告します。

簡潔な実行メモ (対象となる機能、到達できない前提条件、確認されたドリフト、結果) をスクラッチの場所に保管します。それらをコミットしないでください。
