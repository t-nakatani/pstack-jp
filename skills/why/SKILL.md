<a id="why"></a>

# 設計の理由を調べる（why）

コードの背後にある動機と意図を調査します。

`how` スキルのコンパニオン。 `how` は、コードが何を行うのか、どのように機能するのかを答えます。 `why` は、どのような力によってその形状が形成されたのかを答えます。

以下の各スポーンは、`pstack-models.mdc` ルールのロール行とデフォルトに名前を付けます。 `model` をその行の値に設定するか、ルールまたは行が欠落している場合はデフォルトに設定します。値が `auto` または `inherit-parent` の場合は、`model` を未設定のままにしておきます。タスク ツールがスラッグを拒否した場合は、デフォルトを使用してその旨を伝えます。デフォルトが拒否される場合は、エラー メッセージにある同じファミリーの最も近い有効なスラッグを使用します。

<a id="operating-posture"></a>

## 動作姿勢

**注意深く、用心深く、正確な捜査官**として行動してください。自分が知っていることと推測していることについて正直になってください。完全な信頼フレームワークと表現ガイドについては、`references/epistemics.md` をお読みください。シンセサイザーはそれに従う必要があります。

<a id="step-1-understand-the-target-and-the-question"></a>

## ステップ 1. ターゲットと質問を理解する

ユーザーの質問を解析します。 **ターゲット**は通常、コードの塊、パターン、機能、または名前付きの設計上の決定です。 **質問**は通常、設計の理論的根拠、トレードオフ、動機となるエッジケース、外部制約、デッドコード、または広範な歴史の概要です。

ターゲットがあいまいな場合 (明確な指示対象がない「なぜこのようにするのか?」)、会話のコンテキスト (開いているファイル、最近の編集、Cursorの位置、今議論された内容) から最善の推測を立てます。解釈を簡潔に述べて、ユーザーがオフの場合にリダイレクトしてから続行できるようにします。

<a id="step-2-establish-the-code-anchor"></a>

## ステップ 2. コード アンカーを確立する

調査員を生成する前に、調査を具体的なコードで固定します。必要なものは次のとおりです。

- 関連するファイル パスと行範囲
- キー記号（関数名、クラス名、定数）
- 初期コミットリスト。ターゲットに触れている最後のいくつかのコミット。
- マージ コミットからの PR 番号 (件名のパターン `(#1234)`)

これをインラインでビルドします。

```bash
# Blame target lines for last-touch commits
git blame -L <start>,<end> <file>

# Full file history, with patches, through renames
git log --follow -p -- <file>

# Last N commits touching the file, PR numbers visible
git log --oneline -20 -- <file>

# Extract PR numbers from a commit message
git log -1 --format=%B <commit>
```

実質的なコミットについては、`gh` 経由で PR 本文とディスカッションをプルします。

```bash
gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews
```

これをシード コンテキスト (ファイル パス、シンボル、コミット、PR 番号、リンクされたチケット ID) としてキャプチャします。それを捜査官に渡します。

<a id="step-3-spawn-parallel-investigators-default-posture"></a>

## ステップ 3. 並行調査者を生成する (デフォルトの状態)

**デフォルトは完全な並行調査です。**

<a id="discovery"></a>

### ディスカバリー

探索者を生成する前に、Cursor環境から利用可能な MCP をリストします。利用可能なツール マップが存在する場合は、それを使用します。それ以外の場合は、Cursorが公開する有効な MCP サーバーの `mcps/` ディレクトリを検査します。

利用可能な各 MCP を 1 つの証拠カテゴリにマップします。

1. ソース管理履歴
2. 問題 / チケット トラッカー
3. 長い形式の文書
4. リアルタイムのチームチャット
5. インフラストラクチャの可観測性
6. エラー/例外の追跡
7. 製品分析ウェアハウス

ソース管理は、git および `gh` を通じて常に利用できます。他の 6 つについては、MCP 名、サーバー命令、ツール名、リソース記述子を使用して分類します。 MCP が複数のカテゴリに適合する可能性がある場合は、その主要な証拠に一致するカテゴリを選択します。あいまいなケースをカバレッジ マップに記録します。

最小限のマップではなく、完全な **カバレッジ マップ**を目指します。 null を文書化します。検索をスキップしないでください。

一致するすべての調査員を 1 つのメッセージで起動し、同時に実行できるようにします。 1 人のエージェントに複数の MCP をカバーするよう依頼しないでください。

サブエージェント構成 (それぞれ):
- `subagent_type`: `generalPurpose`
- `model`: `why investigators` 行、デフォルト `grok-4.7-xhigh-fast`
- `readonly`: `false` (エージェント モード)。 **読み取り専用/質問モードは使用しないでください。** これにより MCP アクセスが剥奪され、MCP が支援する調査員が完全に無効になります。捜査官はやはり何も書くべきではない。

各探索者は以下を取得します:
1. `references/investigator-prompt.md` からの基本プロンプト
2. `references/source-playbook.md` の例を基にした、選択した MCP のカテゴリ プレイブック `references/sources/<source>.md`
3. 横断的な `references/sources/incident-postmortem.md` **ターゲット コードが防御的である場合** (null チェック、再試行ロジック、タイムアウト処理、レート制限、機能フラグ、出力ガード、OOM ハンドラー)
4. ステップ 2 のコード アンカー (ファイル パス、シンボル、コミット ハッシュ、PR 番号、チケット ID)
5. ユーザーの元の質問

<a id="investigator-roster-one-per-available-evidence-category"></a>

### 捜査員名簿。利用可能な証拠カテゴリごとに 1 つ

一致する MCP を持つカテゴリごとに 1 人の探索者を生成します。それぞれが 1 つのツールまたは MCP を所有します。

各エントリは、カテゴリと、それが独自に表面化する「理由」の種類に名前を付けます。これを使用して、何が返されることを期待するか、カテゴリが空になったときにギャップに名前を付ける方法を知り、(まれに無関係であると証明される場合にのみ) スキップを正当化するために使用します。

1. **ソース管理調査者**。 Git 履歴、PR の `gh`、コード コメント、テスト。常にスポーンします。唯一の保証されたソース。 *レビュー中に取得された実装時の理論的根拠*を表面化するのが得意です。

2. **問題/チケット トラッカー調査者** (例: Linear、Jira、GitHub Issues、Plane、Shortcut MCP)。 *製品やビジネスの強制機能*を表面化するのが得意です。なぜ最も強いのは、理由がエンジニアリングの外部にある場合です。

3. **長文ドキュメント調査者** (例: Notion、Confluence、Google Docs、Coda MCP)。 *長い形式の設計理論*を表面化するのが得意です。コードになる前に理由が書き出される場所。

4. **リアルタイム チーム チャット調査員** (例: Slack、Discord、Microsoft Teams、Mattermost MCP)。文書に到達することのなかった*リアルタイムの審議*を表面化するのが最も得意です。ソース管理、チケット、ドキュメント用紙の痕跡が薄い場合は特に重要です。

5. **インフラストラクチャ可観測性調査者** (例: Datadog、New Relic、Honeycomb、Grafana、Splunk MCP)。インフラ/ランタイムビュー。コードの動機となった*インフラストラクチャと実行時の現実*を明らかにするのが得意です。ターゲットがインフラ信号 (タイムアウト、再試行、レート制限、サーキット ブレーカー) に反応する場合に最も強くなります。

6. **エラー/例外追跡調査者** (例: Sentry、Rollbar、Bugsnag、Airbrake MCP)。 *防御コードや修正コードの動機となった特定の例外とエラーの軌跡*を明らかにするのが得意です。キャッチブロック、ヌルガード、タイプチェック、リトライなどの防御に最強。

7. **製品分析ウェアハウス調査員** (例: Databricks、Snowflake、BigQuery、ClickHouse、dbt、Redshift MCP)。製品/データビュー。コードを形成した *製品とデータの現実 * を明らかにするのが得意です。フラグゲートされたコード、実験主導の船、データ移行、および「この数字はどこから来たのか」という質問に最も強力です。

<a id="when-to-skip-an-investigator"></a>

### 調査員をスキップする場合

最後の「参考にした情報源」セクションにある **明示的な書面による根拠**がある場合のみスキップしてください。 2 つの正当な理由:

- **この環境では、そのカテゴリで使用できる MCP はありません**。これは選択肢ではなく、ギャップとしてフラグを立ててください。例: 「リアルタイム チーム チャットはスキップされました。利用可能な一致する MCP がないため、会話レコードは検索できませんでした。」
- **出典は「おそらく無関係」であるだけではなく、無関係であることが証明されています**。高いハードルです。例: 「エラー/例外の追跡はスキップされました。ターゲットはランタイム コード パスのないビルドタイム スクリプトです。」

スコープ評価で、PR の説明にすでに完全な回答が含まれているシングルコミットの簡単なターゲットが提案されている場合は、利用可能な 7 つのカテゴリ検索がすべて冗長であることを確認した**場合にのみ**、インラインで回答できます。はっきりそう言ってください。これは珍しいはずです。

<a id="step-4-synthesize"></a>

## ステップ 4. 合成する

1 つのシンセサイザー サブエージェントを生成します。

- `subagent_type`: `generalPurpose`
- `model`: `why synthesizer` 行、デフォルト `claude-opus-5-5-xhigh`
- `readonly`: `false` (エージェント モード)。シンセサイザーの品質チェックでは引用をスポット検証しますが、これには MCP アクセスが必要になる場合があります。 Readonly/Ask モードは MCP を取り除き、それを無効にします。

シンセサイザーは次を取得します。
1. 調査結果 (ヌル結果および正当な理由によりスキップされたカテゴリを含む)
2. ステップ 2 のコード アンカー (ファイル パス、シンボル、コミット ハッシュ、PR 番号、チケット ID)
3. ユーザーの元の質問
4. `references/epistemics.md` の認識論フレームワーク
5. `references/synthesizer-prompt.md` のシンセサイザー プロンプト テンプレート

<a id="step-5-present"></a>

## ステップ 5. プレゼント

シンセサイザーの出力を取得し、ユーザーに提示します。わかりやすくするために軽く編集したり、会話のコンテキストを追加したりすることはできますが、**自信に満ちた言葉を書き直さないでください**。

<a id="output-format"></a>

## 出力形式

出力構造は `references/synthesizer-prompt.md` にあるものです: 質問、問題のコード、見つかったこと、合理的に推論できること、競合する仮説、不明なこと、参照した情報源、信頼性の概要。必要に応じて調整しますが、信頼度の分離はそのままにして、調査対象の情報源を調査者ごとに 1 行として、何も返されなかった情報やスキップされた情報も含め、その理由を付けます。

Sources Consulted ブロックの後、ユーザーの `why` の質問がこのコードを実際に変更する前兆である場合、リネージの結果を、変更の計画に適した保持 / 変更 / 回避 / リスク制約セットに変換します。

<a id="common-failure-modes-to-avoid"></a>

## 回避すべき一般的な障害モード

- **最新性バイアス**。最新のコミットが権限のあるものであると仮定します。現在の形は、多くの場合、以前の決定が積み重なったものです。遡ってみましょう。

<a id="reference-files"></a>

## 参照ファイル

- `references/epistemics.md`。信頼度の段階と表現ガイド。シンセサイザーはそれに従う必要があります。
- `references/investigator-prompt.md`。調査員サブエージェントの基本プロンプト テンプレート。
- `references/source-playbook.md`。以下のカテゴリのプレイブックを指すインデックス。
- `references/sources/*.md`。カテゴリごとに 1 つの自己完結型サンプル プレイブックと、横断的な `incident-postmortem.md` が含まれています。調査員にそのカテゴリに一致する 1 つのファイルを提供し、それを利用可能な MCP に適合させます。
- `references/synthesizer-prompt.md`。出力形式を含む、シンセサイザー サブエージェントのプロンプト テンプレート。
