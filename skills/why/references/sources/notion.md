# Notion ドキュメント

<a id="what-this-source-contains"></a>

## このソースの内容

- PRD (製品要件文書)
- 技術仕様と RFC
- アーキテクチャ決定記録 (ADR)
- 設計レビューの会議メモ
- ドメイン コンテキストを含むチーム ページ
- インシデントの事後分析
- 防御コードを説明する可能性のある Runbook
- 優先順位を設定する戦略文書

Notion では、「なぜ」がコードになる前に長い形式で存在することがよくあります。通常、重要な機能にはドキュメントが含まれます。

<a id="how-to-search-it"></a>

## 検索方法

Notion MCP を使用します。

1. **`notion-search` を使用したキーワード検索。** 試してください:
   - 機能名
   - ターゲットコードのキーシンボル/クラス名
   - オーサー ハンドル (設計ドキュメントは多くの場合、コードが到着する前にオーサリングされます)
   - エラー文字列またはユーザーに表示される用語
   - コードのリリース時期がわかっている場合は、時間制限のあるクエリを実行
2. **`notion-fetch` を使用して候補ページを取得します。** プレビューではなく、完全なコンテンツを読み取ります。根拠は文書の途中に埋もれてしまうことがよくあります。
3. **バックリンクと子ページをたどります。** 設計ドキュメントには、検討された代替案、付録、または実装ノートのサブページが含まれることがよくあります。
4. **関連データベースを確認してください。** `notion-query-data-sources` および `notion-query-meeting-notes` により、決定について話し合った会議のメモが明らかになる可能性があります。
5. **作成者固有のスペースを検索します。** PR 作成者が個人用のノートブック (一部の企業で一般的) を持っている場合、コードに先行する探索的な思考が含まれている可能性があります。

<a id="what-good-evidence-looks-like-here"></a>

## 良い証拠は次のとおりです

- ターゲット コードの目的に一致する「問題ステートメント」または「動機」セクションを含む PRD
- 「検討された代替案」または「拒否されたアプローチ」セクション
- 特定のインシデントの修正としてターゲット コードを指定する事後分析
- 「Y のため X を決定しました」と記録され、PR と同じ作成者/日付範囲に関連付けられた会議メモ
- 重要な内容が記入された ADR テンプレート (ステータス、コンテキスト、決定、結果)

<a id="common-pitfalls"></a>

## よくある落とし穴

- **古いドキュメント。** 仕様は実装前に書かれ、更新されないことがよくあります。ドキュメントには、変更された計画が記載されている場合があります。実際の PR と照合してください。
- **ドキュメントと現実のドリフト。** 仕様では「X を実行します」と書かれているかもしれませんが、コードは実際には Y を実行します。発散にフラグを立てます。シンセサイザーは矛盾を表面化させます。
- **定型テンプレート。** 一部の組織では、綿毛で埋め尽くされた「理由」セクションが必要です。特異性を探してください。
- **リンクされていないドキュメント。** 最も関連性の高いドキュメントがどこからもリンクされていない可能性があります。広範なキーワード検索が役に立ちます。
- **複数のドラフト。** トピックに複数のドキュメントがある場合は、最終化されたドキュメントまたは最後に更新されたドキュメントを見つけます。日付を確認してください。
- **アクセス制限されたページ** ページにアクセスできない場合は、そのページにギャップがあることをメモしてください。

<a id="what-to-return"></a>

## 返すもの

関連する各ドキュメントについて:
- タイトルと URL
- 作成者と最終更新日
- 動機のテキスト (逐語的な引用)、ページ/セクションの場所を含む
- 関連するリンクされたページ (合成者がそれらを引用できるようにするため)
- ドキュメントが完成したか草案か
