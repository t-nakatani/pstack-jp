# Slack での会話

<a id="what-this-source-contains"></a>

## このソースの内容

- 問題と意思決定についてのリアルタイムのディスカッション
- 消防訓練の決定が行われたインシデント チャネル
- トレードオフが議論されたデザイン ディスカッション スレッド
- ドキュメントに記載されなかった上級エンジニアによる質問の回答
- 何かが再考された理由を説明するマージ後のディスカッション
- DM (通常は検索不可、範囲は適宜)

Slack は、特にドキュメントを必要としない小さな変更の場合、「実際の」 意思決定が行われる場所であることがよくあります。それは最も一時的な情報源でもあります。スレッドは削除され、チャンネルはアーカイブされ、検索の品質は時間の経過とともに低下します。

<a id="how-to-search-it"></a>

## 検索方法

Slack MCP ツールはさまざまです。どの Slack MCP が利用可能であるかを確認し、最初にそのツール スキーマを調べます。 `mcp_auth` が必要になる場合があります。認証が失敗した場合は、停止してギャップを報告します。

1. **作成者限定検索。** PR 統合日前後の PR 作成者からのメッセージ。範囲が大幅に制限され、多くの場合はゴールドに到達します。
2. **機能名とキー記号のキーワード検索。** スペルミスやカジュアルな表現も含めます。
3. **PR URL 検索。** Slack は、レビューや議論の際に PR をリンクすることがよくあります。 PR URL (または単に `/pull/<number>`) を検索します。
4. **エラー文字列の検索。** コードが特定のエラーを処理する場合は、エラー文字列を検索します。事件のスレッドが表面化することがよくあります。
5. **チャネル スコープの検索。** 可能性の高いチャネルに絞り込みます:
   - `#eng-*`。エンジニアリングに関するディスカッション
   - `#proj-*`。プロジェクトチャンネル
   - `#incident-*` / `#sev-*`。インシデントチャネル
   - 所有チームのチーム固有のチャネル
   - デザイン レビュー チャネル
6. **スレッド トラバーサル。** 関連するメッセージが見つかったら、スレッド全体をフェッチします。多くの場合、決定は返信に反映されます。

<a id="what-good-evidence-looks-like-here"></a>

## 良い証拠は次のとおりです

- トレードオフが明示的に議論されたスレッド (「A を使用するつもりだったが、B の方が優れているため...」)
- コードが防止するバグを説明するインシデント チャネル メッセージ
- 査読者からの質問と著者またはリードからの信頼できる回答
- 決定が行われた会議への参照
- 顧客からの質問を説明するプロダクト マネージャーまたは顧客対応エンジニアからのメッセージ

<a id="common-pitfalls"></a>

## よくある落とし穴

- **チャネル考古学上の制限。** 非常に古いメッセージは、保持ポリシーにより失われる可能性があります。特定の日付より前に何も見つからない場合は、保持の崖に注意してください。
- **検索されない DM。** 検索できない DM では多くの決定が行われます。寂しくなるでしょう。これは既知の制限です。
- **「決定」としての推測的なジョーク** Slack はカジュアルです。たとえそれがコミット前であっても、「とにかくやるだけ」は決断ではありません。熟慮された議論を探してください。
- **単一メッセージでのコンテキストの崩壊。** スレッドがないと、単一メッセージがコンテキスト内とは異なって解釈されることがよくあります。常にスレッドをフェッチします。
- **認証失敗** MCP が認証されない場合は、停止します。調査結果をでっち上げないでください。 Slack が検索できなかったことを報告します。

<a id="what-to-return"></a>

## 返すもの

関連する各スレッドについて:
- チャンネル名
- パーマリンクまたはスレッド ID
- 参加者
- ディスカッションの日付範囲
- 出典付きの主要な引用符 (逐語的)
- コンテキスト: これがどのスレッド/事件/ディスカッションの一部であったか
