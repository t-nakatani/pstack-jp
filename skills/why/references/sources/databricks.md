# Databricks 分析とシステム テーブル

<a id="what-this-source-contains"></a>

## このソースの内容

Databricks は、製品分析、データ パイプライン、ウェアハウス テレメトリ レイヤーです。 Datadog を補完します。 Datadog は *インフラ/ランタイム* ビュー、Databricks は *製品/データ* ビュー (ユーザーが何をしたか、どの実験を実行したか、機能の使用状況がどのように進化したか、しきい値定数はどこから来たのか) です。

- **製品分析イベント。** `your_warehouse.events.analytics_track_event` (生) および `<your_analytics_db>.<schema>.<table>` の型付けされ重複排除されたイベントごとの dbt モデル。ユーザーの動作: 機能の呼び出し、クリック、承認/拒否、送信、クライアントから報告されたエラー。
- **使用状況と請求イベント。** `your_warehouse.events.usage_event` / `<your_analytics_db>.<schema>.stg_usage_events`、`your_warehouse.events.raw_model_event` / `<your_analytics_db>.<schema>.stg_raw_model_events`。コストまたは量を重視した意思決定の場合。
- **実験 / 特徴フラグ データ。** 暴露表と結果表。 **スキーマは会社固有です。** 名前を仮定する前に `SHOW TABLES` を使用して調べてください。
- **システム テーブル。** `system.query.history`、`system.compute.warehouses`、`system.billing.*`、`system.access.audit`。 「このクエリは高価でしたか?」、「誰かがこれをどれくらいの頻度で実行しましたか?」、「ウェアハウスの負荷が急増したのはいつですか?」などの質問に答えます。
- **dbt lineage.** `<your_analytics_db>.<schema>` のモデルは、どのパイプラインがテーブル/フィールドに依存しているかを明らかにします。アップストリームの変更は、コンシューマ コードの変更を促すことがよくあります。
- **Databricks ノートブック。** エンジニアがコード変更前に作成した探索的分析。 **SQL MCP を介してクエリすることはできません。** 理論的根拠がノートブックにあると思われる場合は、それをギャップと名付けてください。

<a id="how-to-search-it"></a>

## 検索方法

Databricks SQL MCP を使用します。プライマリツール: `execute_sql_read_only`。 `statement_id` が返された場合は、再実行せずに `poll_sql_result` でポーリングします。

**クエリの前に方向を指定してください。** スキーマは会社固有です。テーブル名を信頼する前にプローブします。

```sql
SHOW TABLES IN <your_analytics_db>.<schema> LIKE '*<keyword>*';
DESCRIBE TABLE <your_analytics_db>.<schema>.stg_<event>;
```

**すべてのクエリには時間制限があります。** これらのテーブルは巨大であり、制約のないスキャンはタイムアウトになります。 `_timestamp` (イベント) または `start_time` (`system.query.history`) でフィルターします。リリース日 (通常は前後約 30 日) を囲むウィンドウを使用します。これより広いのは、強い理由がある場合のみです。

**生のテーブルよりも型付き dbt モデルを優先します。** `<your_analytics_db>.<schema>.<table>` は重複排除され、型付きで、液体クラスター化されています。 `your_warehouse.events.analytics_track_event` には重複と型指定されていない `properties_json` があります。モデル名パターン: `stg_<source>_<event_name_with_underscores>`、`<source>` は `app`、`backend`、`website`、または `cli` です。パターンだけでは解決できない場合は、`SHOW TABLES` で正確なモデル名を確認してください。 dbt モデルがまだ存在しない場合、または dbt 更新ラグ内からのイベントが必要な場合にのみ、生のテーブルにドロップします。

**型付き dbt モデルの列規則** (これらを知っておくと、`DESCRIBE` ラウンドトリップが回避されます):

- `_timestamp`、`_id`、`_auth_id`、`_request_id`、`event_name`。全モデルに標準装備
- `properties_<name>`。入力されたアンダースコアで囲まれたイベント プロパティ (`properties_entrypoint`、`properties_size_bytes`、…)
- `context_team_id`、`context_client_version`、`context_country`、`context_client_os`。事前に抽出されたクライアントコンテキスト

<a id="investigation-patterns-that-tend-to-pay-off"></a>

### 成果を上げる傾向にある調査パターン

ターゲットに一致するテーブルと列の組み合わせを選択します。

1. **イベント使用量の軌跡。** PR マージを中心とした ±30 日のウィンドウにわたる、関連する `stg_*` モデルの日次カウント。統合後 1 ～ 2 日以内にゼロから定常ボリュームまでのステップ関数があることは、PR がこの機能を開始したことを示す強力な状況証拠です。ゼロへの減衰は、非推奨または削除を示唆します。
2. **ガードレール / 防御チェックの起点。** PR の *前* 14 日間の関連する `properties_<name>` 列の分布 (中央値 / p99 / 最大)。ターゲットの閾値定数と一致する p99 は、その数値がデータから選択されたことを示唆しています。
3. **実験/機能フラグ検索** `SHOW TABLES ... LIKE '*experiment*'` を使用して露出テーブルを見つけ、PR 日付近の関連フラグ キーのバリアントごとに露出カウントを取得します。
4. **移行、バックフィル、またはパフォーマンス リライトのクエリ履歴の証拠。** 狭い `start_time` ウィンドウを使用して `statement_text ILIKE '%<table_or_symbol>%'` でフィルタリングされた `system.query.history` により、変更の動機となった可能性が高い高価なクエリが明らかになります (`total_duration_ms` で並べ替えるか、`SUM(read_bytes)` を集計して、 `COUNT(*)`)。
5. **dbt lineage.** ターゲットが `<your_analytics_db>.<schema>` モデルに対して読み取りまたは書き込みを行う場合、多くの場合、モデル自体の git 履歴 (このリポジトリ内) にその根拠が含まれます。自分で追いかけるのではなく、git 調査員に戻る手。

<a id="what-good-evidence-looks-like-here"></a>

## 良い証拠は次のとおりです

上記のパターン形状以外にも:

- 防御コード PR の数日後には、エラー分類イベントの数がゼロ近くに減少します。 PR がそのエラー クラスを解決したことを示唆します
- 暴露表の行は、PR リリース日前後に「リリース済み」/「完了」の決定を含むターゲットの機能フラグ キーに名前を付けます。

<a id="common-pitfalls"></a>

## よくある落とし穴

- **計測された≠原因** イベントの存在は、誰かがそれを記録するのに十分な注意を払ったことを意味し、それが原因でターゲット コードが存在するということではありません。因果関係を主張する前に、Git 研究者からの PR/コミット引用と組み合わせてください。
- **サイレント インストルメンテーションの変更。** イベント ボリュームのステップ関数は、ユーザーの動作が変化したことを意味するのではなく、新しいイベントのログが記録され始めたことを意味する可能性があります。ランプを機能起動信号として読み取る前に、同じウィンドウでインストルメンテーション PR を確認してください。
- **スキーマ ドリフト。** イベント プロパティは進化します。現在の型付き dbt モデルの列は、ターゲットが作成された時点では存在しなかった可能性があります。古いデータでは、生の `properties_json` 内にのみプロパティが含まれる場合があります。
- **dbt リフレッシュ ラグ。** `<your_analytics_db>.<schema>.*` はスケジュールに従って再構築されます (多くの場合、毎時/毎日)。過去数時間のイベントの場合は、`your_warehouse.events.*` にフォールバックし、`_id` までに重複を排除します。
- **会社固有のテーブル** 実験、機能フラグ、請求、および使用状況のテーブルはさまざまです。存在を一度も確認していないテーブルから結果を報告することは、典型的な失敗モードです。最初に `SHOW TABLES` / `DESCRIBE TABLE` を使用してプローブします。
- **保持クリフ。** 関連するウィンドウがテーブルの保持日または dbt モデルの作成日よりも古い場合、それは null 結果ではなく *ギャップ* です。シンセサイザーが「結果なし」を「アクティビティなし」と読み取らないように、明示的に名前を付けます。
- **ノートブックはクエリ可能ではありません。** SQL MCP は Databricks ノートブックを認識できません。論理的根拠が 1 つに存在すると思われる場合は、ギャップを返します。

<a id="what-to-return"></a>

## 返すもの

関連する各所見について:
- タイプ (製品イベント / 実験公開 / 使用または請求イベント / システム テーブル行 / dbt モデル)
- 完全修飾テーブル名と実行した正確なクエリ
- クエリされた時間ウィンドウ
- コンパクトな数値概要 (カウント、パーセンタイル、最初/最後に表示されたタイムスタンプ)。 **生の行をダンプしないでください。**
- ターゲットのリリース日との時間的相関 (例: 「最初の行 2024-08-15、PR #49074 マージ 2024-08-14」)
- 関連性 + 強さ: 直接的 / 状況的 / 弱い
