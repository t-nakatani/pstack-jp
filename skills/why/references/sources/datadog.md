# Datadog テレメトリ

<a id="what-this-source-contains"></a>

## このソースの内容

Datadog は、計画または議論されたこととは対照的に、運用環境で実際に何が起こったのか、実行時記録を保持します。

- **メトリクス** チームによって計測されたカウンター、ゲージ、ヒストグラム。メトリクスの「存在」自体が証拠です。この数字は注目に値すると考えた人がいます。
- **監視と警告** チームが誰かを起こすのが正当であると判断した条件。 `rate_limit_hit > 10/min` でモニターが起動していることは、チームがそのしきい値を懸念している直接の証拠です。
- **ダッシュボード** 厳選されたビュー。グラフは、チームがサブシステムにとって何が重要であると考えているかを示します。
- **APM トレースとスパン。** リクエスト レベルのランタイム データ。 「なぜ遅いのか」「なぜここでタイムアウトが発生するのか」という質問に役立ちます。
- **ログ。** 大量のイベント レコード。多くの場合、防御コードを動機付けるエラー条件が含まれています。
- **インシデント** タイムラインとリンクされた事後分析を含む正式なインシデント記録。
- **ノート。** 探索的調査。多くの場合、仮説や分析が含まれます。

Datadog は、「このコードが書かれた頃の運用の現実は何でしたか?」という質問に答え、多くの場合、コードの形状を説明します。

<a id="how-to-search-it"></a>

## 検索方法

Datadog MCP を使用します。最初は広く、次に狭くしてください。

1. **所有しているサービスを特定します。**

   ```
   search_datadog_services (filter by name or team)
   search_datadog_service_dependencies (see upstream/downstream)
   ```

2. **最初にダッシュボードとモニター。彼らはチームが何を重視しているかを教えてくれます。**

   ```
   search_datadog_dashboards (query: feature name, service name, symbol)
   search_datadog_monitors   (same queries)
   ```

   ダッシュボードまたはモニターがターゲットをカバーしている場合は、そのクエリと監視されたしきい値に注目します。多くの場合、しきい値は「なぜこれが N に固定されているのか?」に対する答えになります。

3. **ターゲットに関する指標。**

   ```
   search_datadog_metrics (by name pattern, e.g., the feature or symbol)
   get_datadog_metric_context (metadata: description, units, tags)
   get_datadog_metric (timeseries; "was there a spike around the PR date?")
   ```

   メトリクスの軌跡とターゲットの追加/変更日を関連付けることは、強力な裏付けとなる証拠です。「`payment_timeout` メトリクスは 2023 年 11 月 3 日に急増し、再試行ロジックは 2023 年 11 月 6 日にマージされました。」

4. **ログ。狭いので捨てないでください。**

   ```
   search_datadog_logs (raw log patterns near the target, set use_log_patterns=true)
   analyze_datadog_logs (SQL-style aggregations, only when you need counts)
   ```

   シンボル、エラー文字列、または機能名で検索します。 **時間制限のあるクエリを強く推奨します** (例: 変更の前後 30 日間)。ログの量が膨大です。制約のない検索は時間を無駄にし、タイムアウトになる可能性があります。

5. **APM スパンとトレース。**

   ```
   aggregate_spans    (stats: "how often does this endpoint fail?")
   search_datadog_spans (inspect individual spans)
   get_datadog_trace  (a specific trace ID)
   ```

   タイムアウト、再試行、低速パス、およびサービス間の動作に役立ちます。

6. **インシデント**

   ```
   search_datadog_incidents (by title, team, date range)
   get_datadog_incident     (full detail for a specific incident)
   ```

   ターゲットが防御的であるように見える場合は、ターゲットが追加された頃のインシデントを検索します。タイムラインに「X に対する防御チェックの追加」が含まれるインシデントは、ほぼ直接的な証拠です。

<a id="what-good-evidence-looks-like-here"></a>

## 良い証拠は次のとおりです

- クエリとしきい値がコードで強制される制約と一致するモニター (コードは 100 にクランプされ、リクエストが 100/分を超えるとモニターにアラートが表示されます)
- ターゲットの作成者によって作成されたダッシュボード。コードが測定または防御する対象に対応するウィジェットが含まれます。
- コードがマージされる直前の本番環境のスパイクとマージ後の安定した値を示すメトリクス
- ターゲット コード、同じシンボル、または同じエラー文字列を参照するインシデント レコード
- 防御コードによって防止される特定のエラー パターンを示すログ (変更前のウィンドウにタイムスタンプが付けられている)

<a id="common-pitfalls"></a>

## よくある落とし穴

- **相関関係は因果関係ではありません。** PR 前のスパイクとその後の安定化は示唆的なものであり、決定的なものではありません。他の変更も同じウィンドウに反映される可能性があります。隣接する PR を確認します。
- **見つけたチャートにオーバーフィットしています。** Datadog のビジュアライゼーションは人間によって *作成*され、人間のフレーミングを反映しています。 「再試行成功率」という名前のグラフは、チームが再試行の成功を重視している証拠であり、特定のコード行が存在する理由ではありません。
- **テレメトリが消えました。** メトリックは名前変更、削除、または短期間の保持が可能です。関連するウィンドウからデータが見つからない場合、それは結果が null ではなくギャップです。
- **大規模なノイズ。** 共通の文字列をログで検索すると、数千件の一致が返されます。サービス、タグ、時間で積極的に絞り込みます。生のログをダンプするのではなく、`analyze_datadog_logs` を使用して集約します。
- **計測された != 原因** メトリクスの存在は、誰かが何かを測定するのに十分な関心を持っていたことを示しますが、それが原因でコードが追加されたということではありません。コミット/PR 日付との相互参照。

<a id="what-to-return"></a>

## 返すもの

関連する各項目について:
- タイプ (ダッシュボード/モニター/メトリック/ログパターン/トレース/インシデント/ノートブック)
- タイトルまたは名前
- リンクまたは識別子 (ダッシュボード ID、モニター ID、メトリック名、インシデント ID)
- 所有者/作成者および作成/変更日
- 質問に関連する特定の条件、クエリ、または引用 (可能な場合はそのまま)
- 関連性: ターゲット コードに関してこれが示唆すること、および接続の強さ
