# リニアチケット

<a id="what-this-source-contains"></a>

## このソースの内容

- 機能、バグ、およびその動機を説明する問題
- 問題に添付されたプロジェクト ドキュメント (多くの場合、PRD または仕様)
- 親/サブ問題の関係 (より広範なイニシアチブ → 特定のチケット)
- 問題に関するコメント (説明、範囲の変更、「なぜこれを行うのか」の根拠)
- モチベーションの種類を示すラベル (例: `compliance`、`customer-request`、`perf`)
- スコープの変更を説明するステータス更新
- 添付ファイルとリンクされた GitHub PR

リニアは、多くの場合、製品/ビジネス コンテキストが存在する場所です。つまり、「顧客 X が要求したため、これを実行しています」または「これは第 3 四半期のコンプライアンス イニシアチブのためです」レイヤーです。

<a id="how-to-search-it"></a>

## 検索方法

リニア MCP を使用します。

1. **リンクされたチケットから開始します。** シード コミットまたは PR がチケット ID (例: `ENG-1234`、`[BUG-567]`) を参照する場合、最初に `get_issue` を使用してそれらをフェッチします。コメントを含む問題全文をお読みください。
2. **関連する問題をキーワードでリストします。** 機能名、キー記号、またはビジネス用語のテキスト検索で `list_issues` を使用します。複数のフレーズを試してみましょう。
3. **課題ツリーをたどります。** サブ課題に到達した場合は、その親をフェッチします。サブ問題は戦術的なものです。親は「なぜ」を抱えていることがよくあります。
4. **プロジェクトのドキュメントを読んでください。** 問題がプロジェクトに属している場合は、`get_project` を使用して、添付のドキュメントを確認してください。プロジェクト レベルのドキュメントには、仕様と理論的根拠が最も多く記録されます。
5. **ラベルとマイルストーンを確認してください。** ラベルは動機のカテゴリ (顧客の要求、インシデントのフォローアップ、コンプライアンス) を示唆します。マイルストーンは仕事を締め切りに結びつけ、多くの場合、モチベーションを明らかにします。

<a id="what-good-evidence-looks-like-here"></a>

## 良い証拠は次のとおりです

- ビジネス上の問題を示す問題の説明: 「SOC2 監査のため、顧客 Acme は X を必要としています」
- 決定を記録するコメント: 「アプローチ A では課金サービスに触れる必要があるため、アプローチ B を採用することにしました。」
- イニシアチブのようなタイトルの親問題: 「第 3 四半期のエンタープライズへの対応」または「支払い失敗の削減」
- 添付された PRD または仕様
- `customer:acme`、`incident-followup`、`compliance`、`perf-regression` のようなラベル

<a id="common-pitfalls"></a>

## よくある落とし穴

- **スコープ ドリフト。** PR が参照するチケットが閉じられ、別のスコープで再度開かれた可能性があります。歴史全体を読んでください。
- **機械的なテンプレート。** 一部のチームは「理由」セクションを必要としますが、定型文で埋めています。一般的なテキスト (「ユーザー エクスペリエンスの向上」) はおそらく本当の答えではありません。
- **古いチケット。** 古いチケットには、変更されたバージョンのプランが反映されていることがよくあります。日付を確認し、コードのリリース日と相互参照します。
- **重複として閉じられたチェーン** 重複関係をたどって正規チケットに戻ります。
- **プライベート ワークスペース コンテンツ。** 問題にアクセスできない場合は、推測ではなくギャップとしてメモしてください。

<a id="what-to-return"></a>

## 返すもの

関連する各チケットについて:
- チケットIDとタイトル
- 説明またはコメントから引用した問題/動機 (言い換えではありません。シンセサイザーには引用する正確なテキストが必要です)
- ラベル、親問題、プロジェクト
- 作成者、作成日、終了日
- チケットへのリンク (利用可能な場合)
