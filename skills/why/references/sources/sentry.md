# セントリー エラー履歴

<a id="what-this-source-contains"></a>

## このソースの内容

Sentry は、うまくいかなかったことのアーカイブです。防御コード、修正コード、またはエラー処理コードの場合、直接的な動機、つまりチェック、キャッチ、再試行、またはフォールバックの追加を強制した特定の例外、スタック トレース、および頻度が含まれることがよくあります。

- **問題。** エラー数、最初/最後に発生したタイムスタンプ、影響を受けるリリース、およびコメントを含むグループ化されたエラー
- **イベント。** 問題内の個々のエラー インスタンス (スタック トレース、タグ、ユーザー コンテキスト)
- **リリース。** 関連する問題を含むデプロイメント レコード (「どのバージョンがこれを修正したか?」に役立ちます)
- **リプレイ。** ユーザー側のエラーのセッション記録 (有効な場合)
- **プロファイル。** パフォーマンス プロファイリング データ (「理由」についてはあまり役に立ちませんが、「どの程度遅いか」については役に立ちます)
- **問題のコメントと割り当て。** 根本原因に関するエンジニアのメモが含まれる場合があります。

Sentry が提供する最も価値のあるものは **時間的相関** です。「問題 X は 2024 年 1 月 2 日に作成され、1 日あたり 500 イベントでピークに達しましたが、防御チェックをリリースしたリリースである 2024 年 1 月 15 日のリリース v2.14.0 後に表示されなくなりました。」

<a id="how-to-search-it"></a>

## 検索方法

セントリー MCP を使用します。

1. **方向。** プロジェクトのスラッグと組織がわからない場合:

   ```
   find_organizations
   find_projects
   ```

2. **ターゲットに関連する問題を検索します。**

   ```
   search_issues (natural language, e.g., "errors in PaymentService timeout", "unhandled exceptions in uploadFile")
   ```

   適切なクエリ コンポーネント: ターゲットが処理する例外クラス名、ターゲットの関数またはクラス名、ターゲットがチェックするエラー メッセージ文字列、ターゲットのファイル パス。

3. **リリースと時間枠で絞り込みます。**

   ```
   search_issue_events (filter by release, time, environment, trace ID, tags)
   get_issue_tag_values (for an issue, see distribution across versions, users, environments)
   ```

   疑わしい問題については、以下を確認してください。
   - **初めて発生しました。** エラーはいつから表示され始めましたか?
   - **最後に確認されました。** いつ停止しましたか?ターゲットのリリース日と一致していますか?
   - **影響を受けるリリース。** どのバージョンで発生しましたか?どれが修正でしたか？
   - **周波数の軌跡** 急上昇し、その後解消されましたか?

4. **コンテキストのために完全なイベントを取得します。**

   ```
   get_sentry_resource (pass a Sentry URL or type+ID)
   ```

   スタック トレースはターゲット コードを通過しますか?タグとパンくずリストは、ターゲットが防御する条件と一致していますか?

5. **ターゲットの近くに着弾したリリースを確認してください。**

   ```
   find_releases (around the commit date of the target)
   ```

   PR のマージ日との相互参照リリース バージョン。

6. **Seer は慎重に使用してください。**

   ```
   analyze_issue_with_seer
   ```

   Seer は AI の根本原因分析を生成します。仮説生成として役立ちますが、権威あるものではなく推論として扱います。実際のイベントとスタック トレースが主な証拠です。予見者の物語は二の次です。

<a id="what-good-evidence-looks-like-here"></a>

## 良い証拠は次のとおりです

- **最初に発生した**がターゲットの PR の直前であり、**最後に発生した**がその直後であり、ターゲットがこのエラーに対処したことを示唆する問題
- ターゲット関数を通過または到達するスタック トレース。防御されている正確な障害モードを示します。
- 修正を説明する PR 作成者からの問題に関するコメント
- Sentry 発行 URL または ID を参照するターゲットの PR 説明またはコミット メッセージ
- ターゲットを含むリリース後に停止する、イベント数が多い問題

<a id="common-pitfalls"></a>

## よくある落とし穴

- **グループ化のドリフト。** Sentry は指紋によってエラーをグループ化します。リファクタリングまたは名前変更により、新しい問題 ID で「同じ」エラーを追跡できます。問題が突然終了した場合は、エラーが再グループ化されたばかりである可能性があります。直後に新しい問題がないか確認してください。
- **リリースの相関関係にノイズが含まれています。** リリースには多くのコミットが含まれています。 v2.14.0 で停止する問題は、ターゲットがそれを修正したことを証明するものではありません。同じリリースでの別の変更により変更が加えられる可能性があります。ターゲットの正確なコミットとの相互参照。
- **サイレント修正。** 防御コードのせいではなく、アップストリームが変更されたためにエラーが停止する場合があります。相関関係は修正を示唆しています。著者性を証明するものではありません。
- **解決済み != 修正済み。** コードを変更しなくても、問題は手動で「解決済み」とマークできます。 `resolved` は、コードが修正したという証拠ではなく、人間のマーカーとして扱います。
- **予見者の幻覚。** 予見者は、正しくない自信に満ちた説明を生成することがあります。クレームを行うときは、実際のイベント、スタック トレース、およびタイムスタンプにフォールバックします。
- **サンプリング** 一部のプロジェクトでは、イベントを積極的にサンプリングします。イベント数が少ないということは、まれなエラーではなく、サンプリングが多いことを意味しているだけである可能性があります。疑わしい場合は、ギャップに注意してください。

<a id="what-to-return"></a>

## 返すもの

関連する各問題について:
- 問題 ID とタイトル
- プロジェクトと組織
- 最初に確認された/最後に確認されたタイムスタンプ
- イベント数 (および既知の場合はサンプリング レート)
- 影響を受けるリリース
- ターゲットとの関連性を示す代表的なスタック トレース スニペット (概要ではなく逐語的な抜粋)
- 最初/最後に確認されたターゲットのリリース日との相関関係
- 問題へのリンク
- 作成者のコメントまたは解決メモ
