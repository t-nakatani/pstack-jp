# インシデントと事後分析のコンテキスト

別個のソースではなく、**横断的な角度**です。インシデントは防御的なコード (「X の停止後にこのチェックを追加しました」) を動機付けることが多いため、ターゲットが防御的なもの (null チェック、再試行ロジック、タイムアウト処理、レート制限、機能フラグ) に見える場合は、利用可能なすべてのソースにわたってインシデント履歴を特に探します。

- **概念**: ターゲット ファイル、機能、またはエラー文字列に言及している事後分析を検索します
- **線形**: `incident`、`sev-*`、`postmortem-action-item`、`reliability` というラベルの付いたチケットを探します
- **Slack**: ターゲット コードが追加された日付付近で `#sev-*` チャネルと `#incident-*` チャネルを検索します
- **Git**: 「インシデントの修正」、「防御チェックの追加」、「元に戻す」、その後に「... で再適用」などのメッセージを含むコミットは強力なシグナルです。
- **Datadog**: 事後アクション アイテムとして作成されたタイムライン、ダッシュボード、モニターを含む正式なインシデント レコードの `search_datadog_incidents`
- **Sentry**: 最初に確認された/最後に確認されたウィンドウがターゲットの PR リリース日と一致する銘柄、スタックはターゲットを追跡します
- **Databricks**: エラー状態を分類する製品分析イベント (クライアントから報告された障害、ユーザーに表示される再試行イベントなど) は、インシデント ウィンドウ中に急増することがよくあります。ターゲット PR のリリース後のイベント数の減少は、Datadog/Sentry 信号にノイズが多い場合でも、ターゲット コードがユーザーに見える症状を解決したことを状況的に裏付けています。

インシデントのリンクを見つけた場合は、完全な事後分析を取得します。通常、事後分析には、コードの変更に直接関係する「アクション アイテム」セクションがあります。複数のソースが裏付ける場合 (Datadog インシデント ID が Linear チケットに表示され、Notion 事後分析に表示され、ターゲット PR にリンクする Slack スレッドに表示され、修正後に Databricks のエラー イベント数が減少します)、証拠は特に強力です。

コードの防御的な性質により、インシデント主導型の起源がもっともらしい場合に時間を費やす価値があります。防御的に見えないコードの場合はスキップしてください。
