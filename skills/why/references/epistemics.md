# 認識論

証拠が歴史的で、断片的で、場合によっては矛盾している場合に、自信について推論する方法と、それを誤った確信に平坦化せずに伝える方法。

コードにはそれ自体の動機がありません。コードが何をするのかを読むことができます。 *なぜそれが存在するのか*を読むことはできません。それはコミット、PR、チケット、ドキュメント、会話の中に存在しますが、すべて不完全で偏っていて、場合によっては完全に欠落しています。そうでないふりをすると、ユーザーを誤解させる自信に満ちた推測が生成されます。

<a id="confidence-tiers"></a>

## 信頼度階層

最終出力のすべてのクレームは、これらの層のいずれかに存在する必要があります。層によって、クレームがどの出力セクションに入るのか、またそのクレームがどのように表現されるのかが決まります。

<a id="1-direct"></a>

### 1. 直接

質問に答える明示的なテキスト引用。 「コードは X を実行するので、作成者は X を望んだに違いない」ではありません。著者が実際にその理由を *書いた* もの。

例:
- 「アイテムが 1000 を超えるユーザーがページ分割できないバグが修正されました」という PR の説明
- 「顧客 Acme がセキュリティ レビューでリクエストしたため、これを追加します」というチケット
- 「// アップストリーム API がそれより大きな値を拒否するため、100 に固定します」というコード コメント
- 「再起動後の永続性が必要なため、オプション B ではなくオプション A を選択しました」という設計ドキュメント
- 作成者からのチャット メッセージ「古いアプローチはテストで不安定だったので、このアプローチに切り替えました」

表現: 自信を持って、現在形。 「Xがあるからこれが存在する。」出典を引用します。

<a id="2-supported"></a>

### 2. サポートされています

複数の間接証拠が集まります。単一の情報源がそれを明示的に述べているわけではありませんが、情報源全体のパターンからその可能性は高いと考えられます。

例:
- PR タイトルには「パフォーマンスの向上」と表示され、チケットには「perf」というラベルが付けられ、周囲のコミットはすべて同じホット パスに触れます
- 変更に伴い複数のテストが追加され、すべて非常に大きな入力を使用してエッジ ケースを実行しました。
- 同じ週の著者の他の PR はすべて、説明の中で同じ出来事について言及しています

フレーズ: 自信に満ちていますが、明確に派生しています。 「証拠は X: [特定の部分] を強く示しています。」複数の情報源を引用します。

<a id="3-inferred"></a>

### 3. 推測

コンテキストの妥当な解釈ですが、それを明示的にサポートするものはありません。読者は、これが *あなたの解釈* であり、記録からの事実ではないことを理解する必要があります。

例:
- PR は理由を述べていませんが、本番環境でエラーが発生し (インシデント チャネルのタイミングに従って)、修正が急いで行われた (同日にマージされた) ことを考えると、おそらくホットフィックスだったでしょう。
- 関数名は再試行ロジックを示唆しています。再試行回数は 3 です。これは、コードベースの他の場所で見られる「3 回の再試行」というチームの一般的な規則と一致します。

表現: ヘッジ。 「そう見える」、「可能性が高い」、「示唆する」、「と一致する」、「ある読み方がある」。推論チェーンを明示的にします。「A と B を考えると、D であるため、C である可能性が高くなります。」

<a id="4-speculative"></a>

### 4. 投機的

もっともらしい仮説ですが、証拠は薄く、他の説明も同様によく当てはまります。これらを提示することは価値がありますが、推測として明確にマークしてください。

例:
- 「これはブラウザのバグの回避策である可能性があり、現在は修正されていますが、その最新の証拠は見つかりませんでした。」
- 「このしきい値は SLA コミットメントに一致するように選択された可能性がありますが、SLA ドキュメントでは参照されていません。」

表現: 明らかに推測的です。 「可能性の一つはXですが、直接的な証拠はありません。」通常は、他の可能性とともに「競合する仮説」セクションに存在します。

<a id="5-unknown"></a>

### 5. 不明

調べてもわかりませんでした。妥当かつ重要な結果です。それを文書化します。

フレーズ: 「X、Y、Z を検索しましたが、理由の証拠は見つかりませんでした。」 *何を*検索したかを具体的に記入してください。 「見つけることができませんでした」は、「キーワード A と B でチケット トラッカーを検索し、2023 年以降にこのファイルにアクセスした 6 つの PR をスキャンし、しきい値に一致する文字列リテラルのリポジトリを grep しました。根拠となるものは何もありませんでした。」よりも役に立ちません。

<a id="phrasing-guide"></a>

## フレージング ガイド

<a id="words-that-carry-confidence-use-carefully"></a>

### 自信をもたらす言葉。慎重に使用してください

これらは、**直接** または **サポート** の信頼性を意味します。推論には使用しないでください。

- 「だから」。証拠を伴う因果関係の主張を暗示する
- 「理由は」。同じ
- は「するように設計されました」。著者の意図を主張する
- 「修正」、「アドレス」、「解決」。変更により目標が達成されたと主張する
- 「チームが決めた」。グループの決定があったと主張する

これらを使用している場合は、引用をすぐ隣に置く必要があります。

<a id="words-that-hedge-use-for-inferences"></a>

### ヘッジする言葉。推論に使用する

- "のように見える"
- 「らしい」
- "おそらく"
- 「提案します」
- 「と一致します」
- 「読み取り値は 1 つです」
- "おそらく"
- 「そうだったかもしれない」
- 「証拠は次のことを示しています」

これらは、報告するのではなく、解釈していることを示します。 「合理的に推論できること」セクションでは、それらを積極的に使用してください。

<a id="words-to-avoid"></a>

### 避けるべき言葉

- 「当然です」。それが明らかであれば、ユーザーは尋ねないでしょう
- 「明らかに」。ほとんどの場合、明確ではない主張が先行します
- 「もちろんです」。同じ
- 「ただ」 (「パフォーマンスのための単なる X です」のように)。否定的で、通常は不確実性を隠す
- 「私は思う」/「私は信じます」。あなたは個人的な意見を述べているのではなく、証拠を総合しているのです。代わりに「証拠が示唆している」を使用してください。

<a id="avoid-rationalization"></a>

### 合理化を避ける

現在「意味をなす」コードは、現在は当てはまらない理由で書かれたものであるか、書かれた時点では間違っていた可能性があります。汚い歴史にきれいな根拠を後付けしないでください。

次のような衝動を抑えてください。
- 著者が「正しい」ことをしたと仮定し、それを正当化するために逆算する
- コピーアンドペーストの可能性がある場合、コードベース全体で一貫したパターンが意図的であると仮定します。
- 証拠の不在を不在の証拠に変える (「誰もセキュリティ上の懸念について言及していなかったので、懸念はなかったに違いない」)

<a id="the-sycophancy-trap"></a>

## おべっかの罠

ユーザーは、仮説を埋め込んだ `why` の質問をよくします。「パフォーマンスのためだと思いますが、なぜこのようにするのですか?」単純に確認しないでください。複数の候補の中の 1 つとして扱い、独立して証拠を確認してください。証拠がそれを裏付ける場合は、引用とともにそう述べてください。そうでない場合は、そう言い、証拠が「実際」に裏付けていることを提示してください。

ユーザーの推測は調査を促すものであり、検証すべき結論ではありません。

<a id="when-evidence-contradicts"></a>

## 証拠が矛盾する場合

2 つの情報源が一致しない場合 (PR の説明では 1 つのことが述べられ、チケットでは別のことが述べられている)、両方を明らかにします。より整然とした物語に適合するものを選択しないでください。典型的なパターン:

- **チケットには**「顧客 X のコンプライアンス要件のためにこれが必要です」と記載されています
- **広報担当者は**「この分野の技術負債を一掃している」と述べています

どちらも正しいかもしれません (チケットが作品の動機となり、PR は作者が作品を組み立てたものです)、あるいは一方が間違っている可能性があります。両方を引用とともに提示し、ユーザーに電話をかけさせます。

<a id="when-evidence-is-missing"></a>

## 証拠が不足している場合

正直な「わかりません」は、このスキルが生み出す最も価値のある成果の 1 つです。ユーザーは次のことを知ることができます。

- 答えは明らかな場所にはない
- それを知るには人間 (オリジナルの作成者、製品所有者、チーム リーダー) に尋ねる必要があります。
- あるいは、その質問はこれ以上追求する価値がないと判断することもできます

ギャップをマークせず、自信に満ちた推測で埋めると、ユーザーに悪影響を及ぼします。彼らは推測に基づいて行動するでしょう。

ギャップに遭遇した場合は、具体的に名前を付けます。
- 答えようとしていた質問は何ですか
- 検索したソース
- それぞれで検索したもの
- 見つけたもの (何もないか、または関係のある内容のみ)

<a id="calibration-check-before-finalizing"></a>

## 仕上げ前のキャリブレーションチェック

出力を配信する前に、シンセサイザーは「見つかったこと」と「合理的に推測できること」のすべての主張を確認し、次のことを尋ねる必要があります。

1. この主張には出典がありますか?そうでない場合は、追加するか、「推測」/「仮説」に移動します。
2. フレージングは階層に合わせて調整されていますか? (直接クレームでは「 because 」を使用できますが、推論クレームでは使用できません。)
3. コード自体をそれ自体の意図の証拠として扱っているのでしょうか?もしそうなら、それは証拠ではありません。削除または再分類します。
4. 出力には「わからないこと」セクションが含まれていますか?ギャップが言及されていない場合、それは疑わしいです。証拠が異常に完璧だったか、何かが隠蔽されているかのどちらかです。
