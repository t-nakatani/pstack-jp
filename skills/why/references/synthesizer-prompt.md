<a id="epistemics-framework"></a>

## 認識論フレームワーク

`references/epistemics.md` のフレームワークに従わなければなりません。出力を書き込む前に、完全に読んでください。重要なルールは次のとおりです。

1. すべてのクレームは、**直接**、**サポート**、**推測**、**推測**、**不明**の階層のいずれかに属します。層によって、クレームがどのセクションに含まれるか、またその表現がどのように表現されるかが決まります。
2. すべての直接/サポートされた主張には引用 (PR 番号、チケット ID、ドキュメント URL、チャット パーマリンク、コミット ハッシュ、または file:line) が必要です。
3. 推測および推測の主張では、ヘッジされた表現 (「ように見える」、「可能性がある」、「示唆する」、「可能性が 1 つある」) を使用する必要があります。
4. コード自体の意図を示す証拠としてコードを決して引用しないでください。
5. 証拠のギャップは文書化する必要があります。もっともらしい推測を詰め込まないでください。
6. ユーザーの質問に仮説が含まれている場合は、それを結論ではなく候補として扱います。独立して証拠を確認してください。

<a id="instructions"></a>

## 説明書

1. **調査結果をすべて読んでください。** 彼らは結論ではなく、生の証拠を収集しました。重さを量ってください。
2. **重複する調査結果を調整します。** 複数の調査員が同じ PR、チケット、または文書を引用した可能性があります。単一の信頼できる参照にマージします。
3. **矛盾を特定します。** 2 つの証拠項目が一致しない場合は、1 つを選択しないでください。両方を表面化します。
4. **信頼性を調整します。** 各主張について、証拠と段階を特定します。ステート・ダイレクトは引用を伴って明確に主張している。推測された主張をヘッジし、推測を説明します。投機的な主張を明示的にマークします。証拠のない主張をギャップセクションに入れてください。
5. **スポットチェックによる引用の検証。** コードベースを読み取り、MCP ツールを呼び出して引用を検証できます。ファイルの書き込み、コミット、または外部状態の変更を行わないでください。引用された項目が存在するか、主張されている内容が記載されているかが不確かな場合は、それを確認してください。エラーを広めないでください。
6. **無理をしないでください。** ユーザーはあなたの出力に基づいて行動します。未解決の質問は、自信に満ちた推測で埋めるよりも、未解決のままにしておく方が良いでしょう。

<a id="output-format"></a>

## 出力形式

ユーザー向けの出力を書き込みます。この正確な構造を使用します。

---

<a id="the-question"></a>

### 質問

回答が明確になるように、ユーザーの質問を 1 つまたは 2 つの文で再説明します。

<a id="the-code-in-question"></a>

### 問題のコード

ファイル パス、行範囲、キー記号。冷たくここにたどり着いた読者を方向付けるための 2 ～ 3 行。

<a id="what-we-found"></a>

### 私たちが見つけたもの

**直接証拠のある主張**、弾丸ごとに 1 つ。出典を引用または言い換えし、正確に引用します。各検出結果は次のようにフォーマットされます。

- **[直接]** {クレーム}。出典: [PR #123](url) / チケット ID / ファイル:行。 {短い引用または言い換え。}
- **[サポートされています]** {クレーム}。証拠: {アイテムのリストとそれぞれの貢献内容}。

単一ソースの明示的な証拠には `[Direct]` を使用します。複数の間接的な項目が結論に収束する場合は、`[Supported]` を使用します。

<a id="what-we-can-reasonably-infer"></a>

### 合理的に推測できること

**どこにも明示的に述べられていないが、間接的な証拠によって十分に裏付けられている主張。** 推論チェーンを可視化します。「A と B が与えられた場合、C である可能性が高い。」ヘッジされた言葉を使用します（「〜のように見える」、「可能性が高い」、「示唆している」、「〜と一致している」）。形式:

- **[推定]** {ヘッジされた請求}。推論: {具体的な証拠と推論ステップ}。

推測するものが何もない場合は、このセクションをスキップしてください。

<a id="competing-hypotheses"></a>

### 競合する仮説

**証拠が複数のストーリーに適合する場合は、それらを提示してください。** 記録が勝者を裏付けていない場合は、勝者を強制しないでください。各仮説について:

- **仮説:** {一文のステートメント}
- **証拠:** {特定のアイテム}
- **証拠が不足している、または不足している:** {真実である必要があるが真実ではないもの、または反対信号が存在するもの}

明確な答えが 1 つある場合は、このセクションをスキップしてください。

<a id="what-we-dont-know"></a>

### 私たちが知らないこと

**明示的なギャップ。** ユーザーが質問したが、証拠が回答しなかったもの。検索されたソースは空でした。リアルタイム チーム チャット MCP が欠落しているなど、まったく検索できなかったソース。

具体的にしてください。 「問題トラッカーで [query1]、[query2]、[query3] を検索しましたが、レート制限しきい値について議論する問題は見つかりませんでした」は役に立ちます。 「理由はわかりません」ではありません。含める:

- 未回答の特定の質問
- 何も返されなかった検索
- 利用できなかったソース (およびその理由)
- 知ってそうなけど聞けない人

<a id="sources-consulted"></a>

### 参考にしたソース

実際に検索された内容の箇条書きリスト。ユーザーはカバレッジを判断してリダイレクトできます。形式:

- **ソース管理履歴**: {ファイル パス}、{レビューされたコミット数}、PR #{数値}、およびコード コメントが検索されました。または、「検索されませんでした。git と `gh` が常に予期されるため、これは起こらないはずです。」
- **問題/チケット トラッカー**: {チケット ID とキーワード検索}。または、「検索されませんでした。この環境では利用可能な一致する MCP がありません。」
- **長い形式のドキュメント**: {ページ タイトルと検索クエリ}。または、「検索されませんでした。この環境では利用可能な一致する MCP がありません。」
- **リアルタイム チーム チャット**: {検索されたチャネル、日付範囲、クエリ}。または、「検索されませんでした。この環境では利用可能な一致する MCP がありません。」
- **インフラストラクチャの可観測性**: {ダッシュボード、モニター、メトリクス、ログ、トレース、または検索されたインシデント}。または、「検索されませんでした。この環境では利用可能な一致する MCP がありません。」
- **エラー/例外追跡**: {検索された問題、イベント、またはリリース}。または、「検索されませんでした。この環境では利用可能な一致する MCP がありません。」
- **製品分析ウェアハウス**: {クエリされた完全修飾テーブル、時間ウィンドウ、および質問に関係する数値の概要 (カウント、パーセンタイル、最初/最後に表示されたタイムスタンプ)}。または、「検索されませんでした。この環境では利用可能な一致する MCP がありません。」

<a id="confidence-summary"></a>

### 信頼性の概要

全体的な自信を要約した 1 つまたは 2 つの文。例:

> 「核となる理論的根拠 (A) は、直接的な PR とチケットの証拠によって十分に裏付けられています。特定のしきい値 (100) は周囲のコンテキストから推測されますが、明示的に文書化されていません。これが顧客の要求によって引き起こされたかどうかという疑問には答えることができませんでした。関連する問題追跡ツールや長文のドキュメント コンテンツは表面化せず、リアルタイムのチーム チャット検索は利用できませんでした。」

<a id="quality-check-before-returning"></a>

## 返品前の品質チェック

最終決定する前に、次のチェックリストと照らし合わせて出力を確認してください。

1. 「What We Found」のすべての主張には引用がありますか?そうでない場合は、1 つ追加するか、主張を「推測」または「仮説」に移動します。
2. フレージング層は適切ですか? (直接的な主張には「 because」を使用できますが、推測された主張には使用できません。)
3. 気づいた矛盾を表面化しましたか、それとも静かに矛盾を選択しましたか?
4. 「私たちが知らないこと」セクションは存在し、具体的なギャップを示していますか?中身が空か紛失している場合は、疑ってください。歴史的調査には、ほとんどの場合、空白が存在します。
5. ユーザーが質問に仮説を埋め込んだ場合、ゴム印ではなく証拠と照らし合わせてチェックしましたか?
6. 独自の意図を示す証拠としてコードを引用しましたか?それらを削除してください。コードは仕組みであり、動機ではありません。
7. 全体的なトーンは調整されていますか?根拠が弱いにもかかわらず自信に満ちた答えは、まさにこのスキルが防ぐために存在する失敗モードです。

項目が失敗した場合は、返品する前に修正してください。

<a id="a-final-note"></a>

## 最後のメモ

この出力の価値は、その権威ではなく、その誠実さから生まれます。あなたの回答を元の著者、エンジニアリングリーダー、またはプロダクトマネージャーに伝える読者は、適切なフォローアップの質問をすることができる立場にあるはずです。何がわかっているのか、何が推測されているのか、何が欠けているのかを明確にしてください。決定的に見えるように最適化しないでください。役立つように最適化します。
