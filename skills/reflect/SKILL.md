<a id="reflect"></a>

# リフレクト

永続的な学習のために現在の会話をマイニングし、スキル編集にルーティングします。

<a id="when-to-invoke"></a>

## いつ呼び出すか

ユーザーが「reflect」または「/reflect」と言ったときに呼び出します。会話が些細な場合、主題から外れている場合、または親が正しく従った既存のスキルですでにカバーされている場合はスキップします。一回限りのものは学習ではありません。

<a id="process"></a>

## プロセス

<a id="1-locate-the-active-transcript"></a>

### 1. アクティブなトランスクリプトを見つけます。

親はファンアウトする前に独自のトランスクリプト ファイルを見つけます。システム プロンプトは、アクティブなワークスペースの `agent-transcripts/` ディレクトリに名前を付けます。そのパスを使用してください。 `~/.cursor/projects/*/` をまたいでグロブしないでください。これにより、ワークスペースの境界を越えて、無関係なプロジェクトからプライベート チャットが読み取られます。

```bash
ls -t <agent-transcripts>/*.jsonl <agent-transcripts>/*/*.jsonl <agent-transcripts>/*/subagents/*.jsonl 2>/dev/null | head -10
```

3 つのトランスクリプト レイアウト: 従来のフラット (`<id>.jsonl`)、現在のネスト (`<id>/<id>.jsonl`)、およびサブエージェント (`<parent>/subagents/<child>.jsonl`)。

各候補について、最初の JSONL 行を読み、`message.content[0].text` に会話の開始ユーザー プロンプトが含まれていることを確認します。一致するパスを選択します。パスが解決されない場合は、セッションの厳密なダイジェストを書き込み、代わりにそれを渡します。

<a id="2-spawn-three-reviewers-in-parallel"></a>

### 2. 3 人のレビュー担当者を並行して生成します

1 つのメッセージ、3 つの `Task` 呼び出し、`subagent_type: generalPurpose`、`model` が以下のように設定されている、エージェント モード (`readonly: false`)。レビュー担当者は、コンテキスト検索 (チケット、チャット スレッド、トランスクリプトで参照される可観測性トレース) のために MCP アクセスを必要とします。読み取り専用で MCP を削除します。

各レビュー担当者と合成者は、`pstack-models.mdc` ルールのロール行とデフォルトに名前を付けます。 `model` をその行の値に設定するか、ルールまたは行が欠落している場合はデフォルトに設定します。値が `auto` または `inherit-parent` の場合は、`model` を未設定のままにしておきます。タスク ツールがスラッグを拒否した場合は、デフォルトを使用してその旨を伝えます。デフォルトが拒否される場合は、エラー メッセージにある同じファミリーの最も近い有効なスラッグを使用します。

| レンズ | ロールライン | デフォルト `model` | プロンプト テンプレート |
|---|---|---|---|
|判決 | `reflect judgment, divergent, synthesizer` | `claude-opus-5-5-xhigh` | `references/judgment-reviewer.md` |
|ツーリング | `reflect tooling` | `grok-4.7-xhigh-fast` | `references/tooling-reviewer.md` |
|ダイバージェント | `reflect judgment, divergent, synthesizer` | `claude-opus-5-5-xhigh` | `references/divergent-reviewer.md` |

各テンプレートをそのまま渡し、マークされた箇所のトランスクリプト パスまたはダイジェストを置き換えます。レビュー担当者は、`Task` 応答本文で結果を返します。

<a id="3-synthesize"></a>

### 3. 合成する

1 つの `Task` 呼び出し、`subagent_type: generalPurpose`、`reflect judgment, divergent, synthesizer` 行からの `model` (デフォルトは `claude-opus-5-5-xhigh`)、エージェント モード (`readonly: false`)。シンセサイザーの品質チェックにはスポット検証引用が含まれており、これには MCP アクセスが必要になる場合があります。読み取り専用で MCP を削除します。 `references/synthesizer.md` をそのまま使用し、各レビュー担当者の完全な出力をマークのある場所にインライン化します。シンセサイザーは、構造化された承認/拒否/バックログのリストを返します。

<a id="4-structural-enforcement-check"></a>

### 4. 構造施行チェック

シンセサイザーの承認済みリストの健全性を確認します。 lint ルール、スクリプト、メタデータ フラグ、またはランタイム チェックによってより確実に適用される項目については、「承認済み」から「バックログ」に移動します。 **encode-lessons-in-structure** の原則スキルを参照してください。

<a id="5-apply"></a>

### 5. 適用する

承認された編集を適用する前に、シンセサイザーの完全な承認/拒否/バックログ出力をユーザーに提示し、明示的な承認を待ちます。ユーザーは適用するサブセットを選択し、ルーティングをリダイレクトできます。スキルの変更は、組織内の将来のすべてのエージェントに影響します。自動適用しないでください。

バックログ アイテム ファイルは、チームが使用する devex/バックログ トラッカーに自動的に保存されます。承認済みリストのみが承認を待ちます。

承認済みの承認済みアイテムごとに、[ルーティング] フィールドに正確に従います。

- 些細な既存スキルの編集 (一行箇条書き、文章の引き締め、古い事実の修正): 親が直接行います。
- 実質的な既存スキル編集 (新しいセクション、新しいパターン テーブル、約 10 行以上): Cursor の組み込み `create-skill` スキルに手を渡し、そのドラフト/テスト/反復ループを実行します。
- `tune description: <skill path>` (スキルは存在しますが、トリガーされるべきときにトリガーされませんでした): `create-skill` に渡し、その説明最適化ループを実行します。
- `new skill via create-skill: <kebab-name>`: `create-skill` に手動で作成します。場当たり的に形状を考え出さないでください。

環境に SKILL.md バリデーターが同梱されている場合は、完了を宣言する前に、タッチされたすべてのスキルでバリデーターを実行します。そうでない場合は、この手順をスキップしてください。

<a id="6-summarize-for-the-user"></a>

### 6. ユーザー向けの要約

短いリスト、前文なし:

- 適用された編集: `<skill path>`。何が変わったのか、それぞれ 1 行ずつ。
- 新しいスキルが作成されました: `<skill path>`。それぞれ 1 行 (まれ)。
- devex トラッカーにファイルされたバックログ: `<issue title>` (`<tags>`)。それぞれ1行ずつ。
- 削除: 拒否された結果ごとに 1 行 + シンセサイザーからの理由。
