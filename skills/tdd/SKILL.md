<a id="tdd-bug-fix"></a>

# TDD バグ修正

明確で安価なテスト パスを使用してバグを修正する場合は、製品コードを変更する前に、壊れた動作を実行可能にしてください。目標は、修正前に失敗し、修正後に合格する、集中的な回帰テストです。

現実的でない場合はテストを強制しないでください。利用可能なテストで、広範なハーネス設定、脆弱なモック、遅いエンドツーエンドのインフラストラクチャ、運用のみの状態、曖昧な再現手順、または大規模な無関係なフィクスチャのチャーンが必要な場合は、新しいテストの追加をスキップし、代わりに最も近い有用な検証を使用してください。

<a id="workflow"></a>

## ワークフロー

1. **バグを理解してください。** 意図した動作、現在の動作、影響を受けるパス、および観察可能な最小の再現を特定します。
2. **最も範囲の狭い実行可能チェックを選択してください。** そのコードパスに既に使用されている最も近いユニット、コンポーネント、統合、または回帰テストを優先します。実際のテスト パスが明らかでない場合は、ワークフローを満たすためだけに最初からテスト パスを作成しないでください。
3. **最初に失敗したテストを作成します。** バグを捕捉する可能性のある最小の焦点を絞ったテストを追加します。テストでは、現在の実装を反映するのではなく、意図した動作をエンコードする必要があります。
4. **修正する前に新しいテストを実行してください。** 意図した理由でテストが失敗することを確認してください。無関係な理由で合格または不合格となった場合は、実装を編集する前にテストまたは再現を修正してください。
5. **バグを修正します。** 近くのコントラクトを維持しながら、意図した動作を満たす最小限の運用変更を加えます。
6. **回帰テストを再実行します。** テストが成功したことを確認します。

<a id="if-a-failing-test-is-impractical"></a>

## 失敗したテストが現実的でない場合

代わりに、最も近い実行可能回帰チェック (ターゲット スクリプト、手動再現コマンド、ブラウザ自動化、スナップショット比較、ログ アサーション、または集中的な統合チェック) を使用してください。

悪いテストよりも新しいテストがないことを優先します。悪いテストとは、主にモックをテストし、現在の実装の詳細をエンコードし、タイミングや無関係なグローバル状態に依存し、小さな修正に高価なインフラストラクチャを必要とするか、修正を証明した後すぐに削除されるようなテストです。

<a id="guardrails"></a>

## ガードレール

- 間違った実装に一致させるためだけにテストを変更しないでください。
- 予想される動作が本当に変化し、その理由が明らかでない限り、既存のアサーションを弱めないでください。
- 回帰テストはバグに重点を置いてください。大規模なフィクスチャのチャーンや無関係なカバレッジの拡大を避けてください。
- バグが不安定な場合は、可能な限りテストを決定論的に行い、ロックダウンされている信号を文書化します。
- バグによってより広範な種類の障害が明らかになった場合は、まず焦点を絞った回帰パスを見つけてから、追加の兄弟カバレッジを検討します。

<a id="final-response"></a>

## 最終応答

結果だけでなく証拠も報告してください。

- 失敗する前のテストまたは実行可能チェックと、それによって生じた失敗に名前を付けます。
- 通過後のテスト実行と、近くで実行された検証に名前を付けます。
- 失敗前の証拠が証明できない場合は、その理由を述べ、代わりに使用された最も近い回帰チェックについて説明します。
