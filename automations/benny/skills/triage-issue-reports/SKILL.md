<a id="triage-issue-reports"></a>

# トリアージ問題レポート

1 つの Slack レポートを分類し、そのソース スレッドに 1 つの有用な判定を投稿します。明確な新しいバグに対してのみトラッカーの問題を作成してください。ここで再現したり修正したりしないでください。

オートメーションによって提供される外部 Benny 構成をロードします。構成が見つからない、形式が間違っている、または不完全な場合は、トラッカーへの投稿や書き込みを行わずに停止してください。

<a id="hard-safety-rules"></a>

## 厳格な安全規則

- ソース チャネルとルート スレッドの座標は不変です。
- ソース チャネルにルート メッセージを投稿しないでください。
- 別のチャンネルに投稿したり、返信をブロードキャストしたり、DM を送信したり、代替スレッドを開始したりしないでください。
- トラッカーの書き込み前、および判定ポストの直前にソースの親をプリフライトします。
- 親が見つからない、削除されている、アクセスできない、または不明な場合は、書き込みなしで停止します。
- 実質的な判決を 1 件投稿します。進捗状況を語らないでください。
- コーディネーターは唯一の Slack 投稿者です。
- 委任されたワーカーは結果のみを返します。これらは読み取り専用である必要があり、Slack 認証情報や書き込みアクションを受け取ってはなりません。
- すべての子プロンプトは、`SendSlackMessage`、`PostToSlack`、`chat.postMessage`、およびその他すべての Slack 書き込みを禁止する必要があります。
- ワーカーの分離でこれらの制限を強制できない場合は、コーディネーターで作業を行ってください。
- ソース スレッドにリンクできない問題は決して作成しないでください。
- 推測されたチケットや重複したチケットよりもチケットがないことを優先します。
- pstack の `principle-separate-before-serializing-shared-state` をソース座標に適用します。
- pstack の `principle-minimize-reader-load` スキルと `unslop` スキルを最終判定に適用します。

<a id="1-freeze-source-coordinates"></a>

## 1. ソース座標をフリーズする

作業リストを作成する前、または委任する前に、次のことを行ってください。

1. トリガーから `source_channel_id` を読み取ります。
2. 設定されたソース チャネルと等しいことが必要です。
3. `SOURCE_THREAD_TS` が存在する場合は、`trigger.thread_ts` に設定します。それ以外の場合は、`trigger.ts` を使用してください。
4. 空ではない `SOURCE_THREAD_TS` が必要です。
5. `SOURCE_CHANNEL_ID` および `SOURCE_THREAD_TS` を不変の値として保存します。
6. スレッドを読み取り、そのルートに正確にその座標があることを確認します。
7. 安定したソースのパーマリンクを取得します。

その後のすべてのソースの読み取りと送信では、これらの保存された値を使用する必要があります。これらを応答タイムスタンプや操作スレッドのタイムスタンプに置き換えないでください。

<a id="2-read-the-whole-report"></a>

## 2. レポート全体を読む

決定する前にルートと現在の返信を読んでください。

キャプチャ:

- レポーターの文言
- 製品バージョン、アプリのビルド、環境、プラットフォーム (存在する場合)
- 予期される動作
- 観察された動作
- 周波数とトリガー
- エラー テキストまたはスタック署名
- 既存の問題、コミット、またはプル リクエストのリンク
- 誰かがすでに修正しているという明示的な記述

関連するすべての添付ファイルを検査します。

- 実用的な最大解像度でスクリーンショットを読み取ります。
- 正しい動作と間違った動作を区別する状態遷移については、ビデオを確認してください。
- ログ、トレース、クラッシュ テキストを読み取り、具体的な署名を確認します。
- メディアに専門家のレビューが必要な場合は、読み取り専用のメディア ワーカーを使用して、限定的な質問をしてください。作業者は所見のみを返します。
- 添付ファイルを読み取れない場合は、評決でその旨を伝えてください。それが示すものをでっち上げないでください。

レポーターにさらに質問する前に、スレッドにすでに存在する証拠を使用してください。

<a id="3-trace-cause-before-routing"></a>

## 3. 配線前の原因の追跡

所有者または宛先を選択する前に、制限付きソースおよび履歴パスを実行します。 pstack の `how` スキルを使用して、報告されたアクションから観察された結果までのパスをトレースします。レポートが回帰のように見える場合、または防御コードに触れている場合は、`why` を使用します。

1. 報告されたアクションから観察された結果までの可能性のあるコード パスを特定します。
2. 表示されている症状がそのコード パスまたはその下の依存関係に属しているかどうかを確認します。
3. レポートが回帰のように見える場合は、最近の変更を確認してください。
4. マージされたコミットまたはオープン プル リクエストがすでに同じ症状に対処しているかどうかを確認します。
5. 確認された事実を仮説から分離します。

このパスには完全な根本原因は必要ありません。目に見える症状が間違った所有者に転送されるのを避けるのに十分な強度が必要です。

リポジトリを読み取れない場合は、コードの所有者を推測しないでください。保守的な分類を続けて、原因の追跡は利用できなかったと述べます。

<a id="4-classify"></a>

## 4. 分類する

カテゴリを 1 つ選択してください。

<a id="bug"></a>

### バグ

何かが意図された動作に違反しています。例としては、間違った出力、壊れた状態、エラー、クラッシュ、ハング、サイレント no-op、またはリグレッションなどがあります。

<a id="performance"></a>

### パフォーマンス

レポートには、測定可能な遅さ、過剰なメモリ、バッテリーの消耗、ジャンク、またはその他のリソースの問題が記載されています。これをバグとして扱いますが、測定値とプロファイルは保存してください。

<a id="feature-request"></a>

### 機能リクエスト

現在の動作は意図的に行われているように見えますが、報告者は別の動作またはアフォーダンスを望んでいます。

<a id="question-or-feedback"></a>

### 質問またはフィードバック

レポートでは、何かがどのように機能するかを尋ねたり、具体的な欠陥なしで好みを表現したり、一般的なフィードバックを与えたりします。

<a id="reroute"></a>

### ルート変更

原因のトレースにより、別の構成された宛先が問題を所有していることがわかります。

バグと機能ラインが明確でない場合は、ファイルしないでください。 1 つの評決では 1 つの焦点を絞った質問をし、`other` マーカーを使用する場合があります。

<a id="5-apply-configured-routing"></a>

## 5. 設定されたルーティングを適用する

`routing.map_path` からオプションのルーティング マップを読み取ります。

- 確認された製品領域、コード パス、またはエラー署名と一致します。
- 他の場所にトレースポイントを引き起こす場合、目に見える症状だけでは十分ではありません。
- 一致するルートがない場合は、所有者が不明であるとします。推測しないでください。
- クロス投稿しないでください。ソーススレッドのどこで問題を取り上げるべきかを記者に伝えてください。

所有者の ping はデフォルトではオフになっています。 ping は、次のすべてが満たされる場合にのみ許可されます。

1. ルーティング マップは所有者を明示的に指定します。
2. 設定では、その ping タイプが許可されています。
3. この項目は、所有者の入力が必要な機能リクエストであるか、最近の履歴により強力な証拠を持って回帰の作成者である可能性が高いことが特定されています。
4. 所有者は広範なオンコール グループではありません。

他のケースでは ping が受信されません。

<a id="6-use-the-issue-tracker-adapter"></a>

## 6. 問題追跡アダプターを使用する

トラッカーはアダプターであり、必須ベンダーではありません。リニア アダプタは有効な例の 1 つです。 GitHub Issues アダプターまたは別のトラッカーが同じコントラクトを実装する場合があります。

構成されたアダプターは以下を提供する必要があります。

- テキスト、状態、ラベル、ソース URL、および日付範囲で問題を検索します
- 1 つの問題とそのリンクを読む
- タイトル、本文、ステータス、ラベル、ソース URL を使用して問題を作成します
- 無関係なフィールドを置換せずに既存の問題を更新します
- ソースリンクと繰り返しメモを追加します
- Slack ハンドオフが失敗した場合、この実行によって作成された問題をキャンセル、クローズ、または削除します。

必要な操作が利用できない場合は、その書き込みに対してフェールクローズされます。

構成されたチーム、プロジェクト、ステータス、ラベルを実行時に解決します。構成で明示的に要求されていない限り、ID の作成、ラベルの作成、所有者の割り当て、または優先順位の設定を行わないでください。

<a id="7-dedupe"></a>

## 7.重複排除

このソース パーマリンクが既にトラッカーの問題または以前のトリアージ応答にリンクされているかどうかを常に確認してください。その場合は、投稿したり、複製を作成したりしないでください。

バグやパフォーマンス レポートについては、以下を使用してトラッカーを検索してください。

- 正確なエラーまたはクラッシュの署名
- 製品エリア
- トリガー
- 症状
- バージョンまたは日付ウィンドウ
- 回帰コミットの疑い
- ソース固定リンク

結果を 1 つ選択してください:

- 確信のある重複: 同じ署名、同じ領域、トリガー、症状、または確認された共有原因。
- 関連する可能性: 共通の原因が考えられますが、証明されていません。
- 弱い類似性: 類似性は表面的なものです。
- 一致しません。

確実な複製の場合は、ソースのパーマリンクと 1 つの短い再発メモを使用して既存の問題を更新します。構成で指示されていない限り、再度開いたり、ラベルを変更したり、再割り当てしたりしないでください。

一致する可能性がある場合は、不確実として判定にリンクし、何も作成しません。

長い間クローズされていた問題は回帰の原因であり、自動的にライブ重複になるわけではありません。

<a id="8-decide-whether-to-create"></a>

## 8. 作成するかどうかを決定する

これらがすべて当てはまる場合にのみ作成します。

1. 分類はバグまたはパフォーマンスです。
2. 動作は明らかに壊れています。
3. この問題はまだ存在しているか、修正されるか不明です。
4. 重複排除では、確実または妥当なライブ一致が見つかりませんでした。
5. ソースの親とパーマリンクはプリフライトを通過しました。
6. トラッカーのターゲット フィールドが解決されました。
7. アダプターは、判定ポストが失敗した場合に補償できます。

機能リクエスト、質問、フィードバック項目、ルート変更、重複の可能性、確実な重複、または既に修正された問題については、決して作成しないでください。

新しい問題は自己完結型である必要があります。

- 部位と症状を示すわかりやすいタイトル
- レポーターの引用
- 予想される動作と観察される動作
- バージョンと環境、または `unknown`
- トリガーと周波数
- ソース スレッドのパーマリンク
- 仮説としてラベル付けされた仮説を含む短い原因追跡結果
- インライン スクリーンショットまたは代表的なビデオ フレーム (サポートされている場合)
- 残りのアーティファクトへのリンク
- 設定された吸気ステータスとラベル

タイトルに推測される根本原因を入れないでください。

<a id="9-post-one-verdict"></a>

## 9. 1 つの評決を投稿する

新しいソース親プリフライトを実行します。次に、`channel=SOURCE_CHANNEL_ID` と `thread_ts=SOURCE_THREAD_TS` を含む返信を 1 つだけ投稿します。

空ではない `thread_ts` を指定せずに、ソースチャネル投稿アクションを決して呼び出さないでください。

返信は短くしてください:

- 結果を導き出す。
- 既存または新しいトラッカーの問題がある場合は、それをリンクします。
- 必要に応じて、ルート変更や不足している事実について言及します。
- 許可された所有者 ping を最大 1 つ含めます。
- ちょうど 1 つのマーカー線で終了します。

マーカーコントラクト:

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

構成されたマーカー文字列のみを使用します。再現自動化は、このソース スレッドで設定された優先順位付け ID からのマーカーのみを信頼します。

投稿後、同じソース スレッドを読み、`SOURCE_THREAD_TS` の下に判定が表示されることを確認します。そうでない場合は、ルートで再試行しないでください。

この実行によりトラッカーの問題が発生し、判定が下されなかった場合は、アダプターの補償アクションを使用してください。問題がキャンセル、クローズ、または削除されていることを確認します。補正を検証できない場合は、オートメーション実行の出力でのみ障害を報告してください。

<a id="10-watch-one-follow-up-window"></a>

## 10. フォローアップ ウィンドウを 1 つ視聴する

構成されたフォローアップ ウィンドウのソース スレッドを監視し、停止します。

- トリアージ ID に対する直接的な質問のみに答えてください。
- 安全なときにトラッカーの問題に具体的な修正を適用します。
- 同じ実行内で 2 番目のマーカーを発行しないでください。
- 人間の協調性や雑談を避けてください。
- 誰かが自動化の停止を要求した場合は、早めに停止します。

ウィンドウを複数回拡張しないでください。新しいレポートでは、新しい実行を開始する必要があります。
