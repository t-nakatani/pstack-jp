<a id="reproduce-and-fix-issues"></a>

# 問題を再現して修正する

ソース スレッドで信頼できるトリアージ マーカーを待ちます。ターゲット アプリの実際の UI を通じて正確な症状を再現します。既存の修正が存在する場合は、それを確認します。再現が確認された後にのみ、制限付きの修正を試みてください。

オートメーションによって提供される外部 Benny 構成をロードします。構成、必要なアクション、制御アダプター、または完成した機能マップが欠落している場合は、フェールクローズされます。

<a id="hard-safety-rules"></a>

## 厳格な安全規則

- 作業を行う前に、ソース チャネルとルート スレッドの座標をフリーズします。
- ソース チャネルにルート メッセージを投稿しないでください。
- すべてのソース スレッドのポストの前に、ソースの親をプリフライトします。
- コーディネーターは唯一の Slack ポスターです。
- 委任された分析ワーカーは読み取り専用で、結果またはメディア メモを返します。
- 修正フェーズのコード ワーカーは、その環境が Slack 認証情報とすべての Slack 書き込みアクションを明らかに除外している場合にのみ編集できます。それ以外の場合は、コーディネーターが編集します。
- すべての子プロンプトは、`SendSlackMessage`、`PostToSlack`、`chat.postMessage`、およびその他すべての Slack 書き込みを明示的に禁止する必要があります。
- お子様には、Slack トークン、投稿手順、投稿用のソース座標、または外部報告の許可を決して与えないでください。
- お子様が実行するために Slack 書き込みアクセスが必要な場合は、Slack を起動しないでください。
- ユーティリティ ボットは証拠ソースです。誰かが修正を明示的に委任しない限り、彼らは修正を所有しません。
- 正確な識別症状は、実際の UI インタラクションを通じて 2 回現れる必要があります。
- 州検査により所見が確認される場合があります。注射したり、症状を強制したりしてはなりません。
- 再現が確認されていないということは、修正が作成されていないことを意味します。
- 既存のプル リクエストまたはコミットは、実行モードを検証モードに切り替えます。これらをオーサリングしないでください。
- `github.com` プル リクエスト リンクを使用します。
- キャプチャ、録音、ログ、トークンをソース管理の対象外にします。
- 委任分析には pstack の `principle-guard-the-context-window` を使用します。
- pstack の `principle-sequence-verifiable-units`、`principle-fix-root-causes`、および `principle-prove-it-works` を再現、修正、検証を通じて適用します。

<a id="1-freeze-source-coordinates"></a>

## 1. ソース座標をフリーズする

作業リストを作成する前、または委任する前に:

1. トリガー チャネルが設定されたソース チャネルと等しい必要があります。
2. `SOURCE_THREAD_TS` が存在する場合は、`trigger.thread_ts` に設定します。それ以外の場合は、`trigger.ts` を使用してください。
3. 空ではない `SOURCE_THREAD_TS` が必要です。
4. `SOURCE_CHANNEL_ID` および `SOURCE_THREAD_TS` を不変の値として保存します。
5. ソース スレッドを読み取り、そのルートにその正確な座標があることを確認します。
6. ソースのパーマリンクを取得します。

これらの値を応答タイムスタンプ、操作タイムスタンプ、またはステータス メッセージ タイムスタンプに置き換えないでください。

すべてのソースチャネル投稿の前:

1. 不変の座標でスレッドを読み取ります。
2. 親が存在し、削除されておらず、まだソース チャネルに属していることを確認します。
3. `channel=SOURCE_CHANNEL_ID` および `thread_ts=SOURCE_THREAD_TS` でのみ送信します。
4. スレッドをもう一度読み、新しいメッセージが返信であることを確認します。

チェックに失敗した場合は、何も投稿しません。ルートまたはフォールバック チャネルでは決して再試行しないでください。

<a id="2-wait-for-the-triage-contract"></a>

## 2. トリアージ契約を待つ

構成された判定予算については、ソース スレッドを監視してください。待っている間は黙っていてください。

次の場合にのみ評決を受け入れます。

- その作成者は `slack.triage_identity_user_id` と一致します。
- `SOURCE_THREAD_TS` での返信です。
- 構成されたマーカーが 1 つだけ含まれています。

パブリック マーカー フォーム:

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

`bug` または `performance` の場合のみ続行します。オプションのトラッカー URL をキャプチャします。 `other`、判定の欠落、信頼できない作成者、マーカーの競合、またはタイムアウトの場合は、サイレント停止します。

このマーカーは、プライベート ボット ID と自由形式の判定一致を置き換えます。

<a id="3-apply-ownership-and-fix-artifact-gates"></a>

## 3. 所有権を適用し、アーティファクト ゲートを修正する

作業を始める直前にスレッドを読み直してください。

<a id="someone-is-explicitly-fixing-it"></a>

### 誰かが明示的に修正しています

ユーザーが修正を明確に主張したり、具体的な実装計画を提示したり、別のエージェントに実装、パッチ、修正、プル リクエストのオープンを依頼したりした場合は停止します。

これらを修正の所有権として扱わないでください。

- ボットが証拠を要約します。
- ツールはログまたはチケットを検索します。
- 誰かがボットに診断、説明、検査、または再現を依頼します。
- ボットが、実装に同意せずに原因仮説を投稿します。

ボットの存在ではなく、要求されたアクションを判断します。

<a id="a-fix-artifact-already-exists"></a>

### 修正アーティファクトはすでに存在します

オープンなプル リクエストまたはマージされたコミットによってこのレポートが修正される可能性がある場合は、`references/verify-existing-fix.md` に切り替えてください。

アーティファクトは、スレッド、トラッカーの問題、リポジトリ履歴、またはプル リクエストの検索から発生する可能性があります。コミットまたはプル リクエストのないクレームは修正アーティファクトではありません。

ある人が作品を所有しているが、成果物を作成していない場合は、停止してください。彼らと競争しないでください。

<a id="4-open-an-optional-operations-thread"></a>

## 4. オプションの操作スレッドを開きます

`slack.operations_channel_id` が構成されている場合、コーディネーターはそこに 1 つのルート ステータス メッセージを作成できます。これは、再現ワークフローで許可される唯一のルート投稿です。

その座標を `OPERATIONS_CHANNEL_ID` および `OPERATIONS_THREAD_TS` として保存します。これらをソース座標と混同しないでください。

構成されたプレーン Unicode ステータス文字列を使用します。ステータステキストは短くしてください:

- 再生中
- 再現できませんでした
- ブロックされました
- 再生産されました
- 既存の修正を確認しています
- 制限付き修正を試みています
- ドラフト プル リクエストがオープンされました
- 修正は適用されませんでした

設定されたCursorスラックアクションを優先します。 `BENNY_SLACK_BOT_TOKEN` は、この 1 つのステータス メッセージの編集など、ユーザーが欠落している狭い機能に対して設定した場合にのみ使用します。トークンをワーカーに公開しないでください。

操作チャネルが構成されていない場合は、オートメーション実行出力に詳細なステータスを保持します。ソースチャネルのルートメッセージを置き換えないでください。

<a id="5-load-and-check-the-control-adapter"></a>

## 5. コントロールアダプターをロードして確認します

`references/control-adapter.md` と `control.feature_map_path` にある完成したマップを読み取り、`control.skill_name` という名前のスキルを呼び出します。

報告されたユーザー パスに一致する機能マップ セクションを見つけます。アプリを使用する前にお読みください。この機能をカバーするセクションがない場合は、パスやセレクターを作成する代わりに、実行をブロック済みとしてマークします。

7 つの機能すべてが必要です。

1. 構成されたターゲット アプリとテスト環境を起動します。
2. マップされた機能をナビゲートし、文書化された状態を実行します。
3. クリック、入力、キー、スクロール、ドラッグ、サイズ変更、またはナビゲーションを使用して実際の UI を操作します。
4. 状態を変更せずに検査します。
5. スクリーンショットをキャプチャします。
6. 画面録画を開始および停止します。
7. プロセス、セッション、プロファイル、一時データをクリーンアップします。

アダプターが存在しない場合、または必要な機能が欠落している場合は、操作ステータスをブロックとしてマークし、停止します。スクリーンショット、単体テスト、状態の変更、またはソースの読み取りを UI の再現であるかのように装わないでください。

<a id="6-study-the-report"></a>

## 6. レポートを検討する

完全なソース スレッドとトラッカーの問題 (存在する場合) を読みます。

収集:

- 正確なアクション パス
- 予期される動作
- 観察された動作
- 分岐する状態の判別
- 周波数
- バージョン、環境、プラットフォーム
- 添付ファイルとエラー署名
- 候補コード領域

スクリーンショットとビデオを検査します。必要に応じて、コード履歴、テストのアイデア、ブラスト半径マッピング、およびメディア レビューに読み取り専用の並列ワーカーを使用します。各従業員には限定的な質問が与えられ、Slack への書き込みは禁止されます。

pstack の `how` スキルを使用して、リポジトリを通じてアクションをトレースします。回帰履歴と防御コードには `why` を使用します。競合する原因仮説を立て、それらを区別する証拠を特定します。

<a id="7-reproduce"></a>

## 7. 再現

コントロール アダプターを介してターゲット アプリを起動します。

操作を行う前に、アプリ、ワークスペース、アカウント、データ セット、機能の状態が正しいことを確認してください。安定したアプリ マーカーを使用します。ウィンドウの順序や見慣れたタイトルだけに依存しないでください。

実際の UI アクションを通じて、報告されたパスを駆動します。

呼び出す前に再現しました:

1. 正しい最終状態に名前を付けます。
2. 壊れた最終状態に名前を付けます。
3. 分岐点に到達します。
4. 壊れた状態を観察します。
5. 2 回目の試行を独立させるのに十分な状態をリセットします。
6. 同じパスを繰り返し、同じ壊れた状態を再度観察します。
7. 可能な場合は、実際の状態の値をクロスチェックします。

予期されるダイアログ、読み込み状態、またはセットアップ手順はバグではありません。正しい動作と壊れた動作を区別する最終状態をキャプチャします。

構成された再現バジェットを使用します。症状が再現しない場合は、正常な `Could not reproduce` 結果を報告してください。環境が必要な機能を提供できない場合は、`Blocked` を報告し、何が不足しているかを述べてください。

<a id="8-capture-and-review-evidence"></a>

## 8. 証拠を取得して確認する

再現を成功させるには:

- 症状の完全なパスを記録します。
- 壊れた最終状態のスクリーンショットをキャプチャします。
- 正確な手順と観察された状態を記載した短いメモを保存します。
- 構成された一時アーティファクト ディレクトリにアーティファクトを保存します。

読み取り専用のメディア評論家に 1 つの質問に答えてもらいます。証拠は、識別可能な壊れた状態を視覚的に示していますか?

答えが「いいえ」または不確かな場合、再現は確認されません。より良い証拠をキャプチャするか、`Could not reproduce` を使用してください。

構成されている場合は、操作スレッドにのみ詳細な証拠を投稿します。ソースの更新は簡潔にしてください。

<a id="9-report-the-repro-outcome"></a>

## 9. 再現結果を報告する

まず操作ステータスを更新します。

`Could not reproduce` または `Blocked` については、ソース スレッドには何も投稿しません。操作スレッドまたは実行出力には結果が含まれます。

確認済みの再現の場合は、ソース プリフライトを実行し、プロンプトなしのソース応答を最大 1 つ投稿します。

- 問題が再現されたと伝えます。
- 操作証拠スレッドが存在する場合は、それをリンクします。
- 短い調査結果を最大 3 つ含めます。
- トラッカーの問題が存在する場合は、それをリンクします。
- デフォルトでは所有者に ping を送信しません。

設定された Slack アクションによって証拠が同じソース スレッド内に保持され、組織の保持ポリシーで許可されている場合にのみ証拠を添付してください。

設定された拒否ウィンドウが終わるまで待ちます。設定や解釈が間違っていたという人がいたら、一度再現を修正します。有効な拒否がない限りウィンドウが閉じるまで、修正フェーズを開始しないでください。

<a id="10-verify-an-existing-fix"></a>

## 10. 既存の修正を確認する

修正アーティファクトが存在する場合は、`references/verify-existing-fix.md` に従ってください。

検証では、ベースラインで症状が示され、パッチ適用されたビルドでは症状が存在しないことが示される必要があります。どちらのパスも実際の UI を 2 回使用します。

既存の修正を編集したり、競合するパッチを追加したり、置換プル リクエストを開いたりしないでください。

<a id="11-qualify-a-bounded-fix"></a>

## 11. 制限付き修正の認定

以下のすべてが当てはまる場合にのみ、修正を試みてください。

- 結果は地味に確認済みの再現です。
- メディアのレビューにより、最終状態が壊れていることが確認されました。
- 既存の修正アーティファクトは表示されませんでした。
- 拒否期間中に修正を要求した人はいませんでした。
- 実行時の証拠により根本原因が特定されます。
- おそらく変更は、設定された修正予算とリポジトリの範囲に適合します。
- コントロール アダプターは、ベースライン ビルドとパッチ適用済みビルドの両方を実行できます。

いずれかの条件が失敗した場合は、再現レポートを保持し、プル リクエストを行わずに停止します。

ゲートを通過すると、操作ステータスを `Attempting bounded fix` に更新します。

<a id="12-root-cause-and-implement"></a>

## 12. 根本原因と実装

コーディネーターは、すべての Slack 投稿、最終的な差分レビュー、コミット、プル リクエストを所有します。

読み取り専用ワーカーは次のことを行うことができます。

- トレース コードと履歴
- テストの提案
- マップの爆発半径
- 差分を確認する
- メディアのレビュー

彼らは修正を編集したり、外部書き込みを実行したり、ステータスを投稿したり、所有したりすることはありません。

このフェーズでは、ツールの分離によって Slack 資格情報とそのワーカーからすべての Slack 書き込みアクションが削除される場合にのみ、スコープが狭いコード編集を委任できます。そのプロンプトには、引き続き明示的な Slack 書き込み禁止を含める必要があります。コーディネーターは編集をレビューし、必要なテストを実行または検証します。ツールの分離が不確かな場合は、コーディネーターで編集を続けてください。

実行時の証拠でメカニズムを確認します。編集する前に競合する仮説を削除します。

正当な最小限の変更で根本原因を修正します。

- 安価なローカル テスト ターゲットがある場合に pstack の `tdd` スキルを呼び出し、修正の前に失敗したテストを作成します。
- パスが高価である、不明瞭である、または統合が多い場合に TDD がスキップされた理由を説明します。
- 無関係なクリーンアップを排除します。
- 変更が設定された労力またはリスク予算を超えた場合は停止します。

<a id="13-prove-the-fix"></a>

## 13. 修正を証明する

元のベースライン証拠を保管してください。

パッチ適用済みビルド:

1. 同じ実際の UI パスを実行します。
2. これを 2 回繰り返します。
3. 壊れた状態がなくなったことを示します。
4. 予想される状態をその場所に表示します。
5. 録画後のスクリーンショットをキャプチャします。
6. ベースラインに使用された同じ実際の状態の値をクロスチェックします。

コンパイル、単体テスト、コード レビュー、または妥当な差分は証拠を求めていません。

集中的なテストを実行し、変更された動作の周囲に爆発範囲を広げます。変更が影響する可能性のある近くの状態、入力、権限、プラットフォーム、障害パスをカバーします。リグレッションが残っている場合は、プル リクエストを行わずに停止します。

<a id="14-open-a-draft-pull-request"></a>

## 14. ドラフトプルリクエストを開く

前後証明後のみ:

- 無関係な変更と秘密については、最終的な差分を確認してください。
- リポジトリの必要なチェックを実行します。
- リポジトリ ワークフローで許可されている場合は、小さい順序付けされたコミットを作成します。
- ドラフトのプル リクエストを開きます。このワークフローからマージまたはデプロイを行わないでください。
- トラッカーでサポートされているプル リクエスト構文を使用して、構成されたトラッカーの問題をリンクします。
- 構成されたパブリック URL フォーム (通常は `https://github.com/{owner}/{repo}/pull/{number}`) を使用します。
- 再現手順、根本原因、テスト結果、前後の証拠、爆発半径のチェックを含めます。
- pstack の `unslop` スキルを通じてプル リクエスト テキストとすべての Slack 更新を実行します。

プル リクエストの作成が失敗した場合は、成功を主張しません。コミットまたはブランチの状態を実行出力に保持し、操作ステータス `Fix did not land` をマークします。

成功したら、操作ステータス `Draft pull request opened` をマークし、リンクされたプル リクエストとともに操作スレッドに 1 つの簡潔な応答を投稿します。 2 番目のソース チャネル ルートまたはプロンプトなしのソース応答を作成しないでください。

<a id="15-follow-ups-and-cleanup"></a>

## 15. フォローアップとクリーンアップ

1 つのフォローアップ ウィンドウで、設定された操作スレッドを監視します。

- すでに収集された証拠から直接の質問に答えます。
- 具体的な修正を 1 つ適用し、セットアップが無効になった場合は再現を 1 回再実行します。
